\chapter{有类型的 IR：值、操作数与指令}
\label{chap:typed-ir}
\section*{本章导读}
抽象语法树保留表达式的嵌套结构，而程序执行还需要明确每一步计算使用哪些值、产生哪个结果。中间表示，即 IR，承担这种重新组织的任务。本章从一段算术表达式出发，阅读当前 Rustless 的 IR 类型、操作数、指令与访问接口。学习重点是理解这些对象之间的关系，以及为什么计算身份不能与语法身份、声明身份混用。本章介绍的是已有表示；将完整源程序转换为这些指令的过程将在后续章节中推导。

\section{表达式树变为定义与使用}
考虑以下 Rustless 函数：
\begin{lstlisting}[language=Rustless,caption={嵌套表达式中的计算依赖}]
fn calculate(a: i32, b: i32, c: i32) -> i32 {
    a + b * c
}
\end{lstlisting}
语法树的根是加法，右子树是乘法。这里的父子关系同时隐含了一项计算依赖：必须先取得乘法的结果，才能完成加法。IR 将这个依赖写成两个显式步骤：先定义乘积，再将乘积作为加法的操作数。中间结果的名称可以任意选择，其意义来自定义与使用关系。

下图把上述嵌套算术展开为中间结果及其使用，呈现语法树的父子关系如何转成计算的定义与使用关系。

\node[irbox,text width=12mm,below right=of add] (mul) {$\times$};

这一转换没有要求每个 AST 节点对应一条指令。括号只影响语法结构，通常不需要独立指令；结构体构造可能产生多个字段写入；短路表达式可能产生多个基本块。建立两种表示，使语法上的准确性和计算上的显式性分别得到适当的表达。若强求二者一一对应，语法树容易混入机器细节，IR 也会保留不必要的语法层次。

显式结果还有维护上的价值。某项分析若要寻找乘积的所有使用，可以围绕其值身份工作，而不必在每个语法形状中重新寻找嵌套位置。相应代价是需要维护定义、使用与类型的一致性；SSA 验证器将在下一章承担这一职责。

\section{语义类型投影到 IR 类型}
当前 \texttt{include/rx/ir.hpp} 中的机器值类型集合很小：
\begin{lstlisting}[language=C++,caption={当前 IR 的类型集合}]
enum class Type { Void, I1, I8, I32, Ptr };
\end{lstlisting}
小集合并不表示源语言类型也只有五种。语义类型描述程序中的整数、引用、数组和结构体；IR 类型描述某一步计算所需的表示。\texttt{i32} 与 \texttt{u32} 都占三十二位，但除法、比较和右移必须保留有符号性。因而当前桥接将二者投影到 \texttt{I32}，再分别选择有符号或无符号指令。
\begin{lstlisting}[language=Rustless,caption={同一位宽上的不同语义}]
let signed: i32 = -8;
let unsigned: u32 = 8;
let a = signed / 2;
let b = unsigned / 2;
let c = signed >> 1;
let d = unsigned >> 1;
\end{lstlisting}
四个结果不能仅凭 IR 类型区分含义。前两项需要 \texttt{SDiv} 与 \texttt{UDiv}，后两项需要算术右移 \texttt{AShr} 与逻辑右移 \texttt{LShr}。这种设计把位宽和运算解释分开，避免为每一种整数符号性重复定义整套指令。

下图呈现多个语义类型投影到同一 IR 类型的关系，同时标出投影之后仍由操作保存的信息。
\begin{figure}[htbp]\centering

\end{tikzpicture}
\caption{语义分类与计算表示的分离}

\texttt{Ptr} 与 \texttt{I32} 在 RV32 上同为四字节，也仍然是不同类型。地址可以用于读取对象，整数可以用于算术；将二者区分，可以在指令构造时排除许多错误组合。\texttt{I1} 表示布尔值的一位逻辑结果，而布尔对象在内存中占一个字节。\texttt{I8} 为字节级存储及转换提供表示，不能据此推断 Rustless 已经支持完整的源语言八位整数体系。

\texttt{Void} 表示指令或函数不产生机器值。Unit 与 Never 都可能不产生机器值，但前者正常继续，后者没有正常续行。这个语义区别必须在控制流转换中保留，不能因机器类型相同而消失。

\section{值身份、基本块身份与来源}
语法节点回答“这段写法是哪一个节点”，符号回答“这个名字指向哪一项声明”，IR 值回答“这次计算的结果是哪一个值”。当前实现使用不同的 ID 类型表达这些问题。\texttt{ir\_ids.hpp} 中的节选为：
\begin{lstlisting}[language=C++,caption={计算身份与语法来源}]
struct ValueTag;
struct BlockTag;
using ValueId = ast::Id<ValueTag>;
using BlockId = ast::Id<BlockTag>;
struct Origin {
  ast::NodeId node;
  Span span;
};
\end{lstlisting}
即使某个 NodeId 和 ValueId 的整数部分碰巧相等，也不能互换。一个语法表达式可能产生多个值，一个源变量可能经历多次赋值，而每次赋值产生的值可以具有不同的 ValueId。显示名称只帮助阅读，不负责建立这些关系。

指令的可选 \texttt{Origin} 将计算重新连接到源程序。当验证器发现一个使用不受定义支配，除了指出函数与基本块，也可以保留产生这条指令的源码范围。这种元信息不改变计算结果，却避免后续诊断只能报告难以理解的内部编号。

ValueId 还不是物理寄存器编号。它在一个函数的中间表示中标识计算值；后端可以把若干不同时活跃的值安排到同一物理寄存器，也可以把值保存到栈上。过早把 ValueId 理解为寄存器，会使前端承担不属于它的机器约束。

\section{三种操作数及其构造规则}
当前操作数由常量、局部值和全局地址三种载荷组成：
\begin{lstlisting}[language=C++,caption={当前操作数的具体载荷}]
struct ConstantOperand { std::uint32_t bits; };
struct LocalOperand { ValueId id; };
struct GlobalOperand { std::string symbol; };
struct Operand {
  using Data = std::variant<ConstantOperand,
                            LocalOperand, GlobalOperand>;
  Operand(Type type, Data data)
      : type(type), data(std::move(data)) {}
  Type type;
  Data data;
  static Operand constant(Type type, std::uint32_t bits);
  static Operand local(Type type, ValueId id);
  static Operand global(std::string name);
};
\end{lstlisting}
常量保存位模式，而符号解释由类型检查与具体运算决定。三十二位全一既可以解释为有符号的负一，也可以解释为无符号的最大值。局部操作数只引用一个 ValueId，定义本身位于参数或某条指令中。全局操作数在当前 IR 中表示已命名函数的地址，模块验证还会检查该符号是否存在。

工厂排除明显的无效输入：例如 I1 常量不能保存数值二，局部值不能使用保留的零编号。这样的局部检查不能证明局部值已经被定义，也不能证明定义位于合法路径上，后两项需要函数级验证。将不同范围的约束放到适当层次，既能及时发现错误，也避免让单个操作数对象承担整个程序分析。

操作数没有默认的“空值”。若某条指令不需要操作数，载荷就不提供该字段；若返回值可以缺失，使用 optional。这样可避免一项通用的空操作数约定在多个消费者之间传播。

\section{十三种指令载荷}
当前 IR 的指令形状由 \texttt{Instruction::Data} 集中列出：
\begin{lstlisting}[language=C++,caption={当前指令的闭合集合}]
using Data = std::variant<Alloca, Load, Store, Gep,
                          Binary, Compare, Cast, Call,
                          Phi, Branch, CondBranch,
                          Return, Unreachable>;
\end{lstlisting}
这些载荷可分为五组。Alloca、Load、Store、Gep 表达存储与地址；Binary、Compare、Cast 表达标量计算；Call 表达函数调用；Phi 表达路径合流；其余四种表达控制转移。此处的 Gep 采用字节偏移，它并不隐式承担源语言数组或字段的类型推断。

下图对照 Binary、Store 与 CondBranch 的字段，呈现具体载荷怎样限制没有含义的字段组合。

\texttt{Result} 同时保存结果身份和类型。Compare 的结果类型固定为 I1，Alloca 和 Gep 的结果类型固定为 Ptr，因此它们只需保存结果身份。Store 不产生结果；Call 用 \texttt{optional<Result>} 区分有结果与无结果调用。不同指令能够共享访问过程，同时各自保留明确的数据形状。

与早期“一个 op 加若干通用 vector”的表示相比，具体载荷使读取哪一个字段成为可检查的 C++ 操作。它仍允许存在类型不相容的 Binary，因而还需要验证器。类型安全在这里首先保证形状安全；跨操作数的关系由另一层约束完成。

\section{模块、函数、基本块与声明}
模块保存函数声明与函数定义。声明描述外部或尚无函数体的调用接口；定义包含参数和基本块；每个基本块包含顺序排列的指令。参数与普通指令结果共同构成函数中的值定义。

这种层次不是目录结构的映射，而是作用域和验证范围的映射。ValueId 在函数内解释，BlockId 在函数内定位，调用名称在模块的签名集合中解释。把这些范围分清，可以让验证器准确说明“缺失的是一个块”还是“缺失的是一个被调用的函数”。

函数与参数还可以连接到 SymbolId。一个源语言参数被转换成机器参数后，其来源仍可以查询；聚合返回引入的隐藏参数则需要单独标明其用途，不能伪造一个源语言声明。在后续 ABI 设计中，源参数数量与机器参数数量可能不同。

\section{IR Visitor 与集中关系枚举}
IR 使用与 AST 相同的访问形式：访问者同时收到具有身份与来源的外层对象，以及具体载荷。\texttt{ir\_visit.hpp} 中的覆盖概念要求所有载荷均可调用，并要求返回类型一致：
\begin{lstlisting}[language=C++,caption={当前 IR 访问入口的节选}]
template <class V, class T>
concept ExhaustiveVisitor =
    (std::same_as<T, Instruction> || std::same_as<T, Operand>) &&
    detail::Coverage<V, T, typename T::Data>::value;

template <class T, class V>
  requires ExhaustiveVisitor<V, T>
decltype(auto) visit(const T &node, V &&visitor) {
  return std::visit(
      [&](const auto &p) -> decltype(auto) {
        return std::invoke(visitor, node, p);
      }, node.data);
}
\end{lstlisting}
访问者不必再把外层对象重新解包才能取得载荷。新增一种指令时，严格访问者会指出缺失分支，这有助于维护打印、验证和属性查询的一致性。它并不保证处理分支内部的算法正确，也不排除访问者用通用分支主动选择默认行为。

\texttt{for\_each\_operand} 集中描述一条指令使用哪些值；\texttt{for\_each\_successor} 集中描述控制流后继。定义查询由载荷推导，不另维护容易与载荷矛盾的结果标签。后续分析可以利用这些关系，不必各自重写十三种指令的字段枚举。

当前 variant 是闭合集合，适合指令种类由语言实现统一控制的情形。虚函数继承同样可以表达具体指令，两者的性能差异必须由对象大小、分配和分派方式测量。优雅设计的重点在于关系集中表达，而不是先验地宣称某一种 C++ 机制更快。

\section{文本输出是表示的展示}
当前打印器把项目 IR 转换为 LLVM 文本，并在输出前调用模块验证。函数名称若包含冒号等特殊字符，会被引用和转义，因此 \texttt{Packet::get} 可以稳定显示为 LLVM 可接受的符号形式。

文本是可阅读的结果，而内存中的 typed IR 才是构造和分析的对象。字符串拼接不能替代结果类型、操作数身份或控制流目标。相应地，一份看似整齐的文本也不能证明程序执行含义正确。

打印器从 TargetLayout 取得目标三元组与数据布局。它描述当前 RV32IM、ILP32 输出方向；修改文本中的目标名称并不能自动改变指针大小或函数 ABI。下一章先解决函数内部的值流和控制流合法性，第十六章再解释数据布局。

\chapter{控制流、SSA、Builder 与验证器}
\label{chap:cfg-ssa}
\section*{本章导读}
计算有时沿不同分支继续，有时返回循环起点。单条指令的字段正确，还不足以说明这些路径上的使用都有定义。本章先建立基本块和控制流图，再解释 SSA 和 Phi，最后将局部构造与整体验证联系起来。学习者应能判断一条使用为什么合法，并能说明 Builder 与 Verifier 各自检查的范围。

\section{基本块与终结指令}
基本块是从一个入口顺序执行到终结指令的指令序列。普通指令可以产生值或修改内存，终结指令决定是否继续以及沿哪条路径继续。当前 Branch 有一个后继，CondBranch 有两个，Return 离开函数，Unreachable 表示该位置不能正常执行。
\begin{lstlisting}[language=Rustless,caption={产生结果的条件表达式}]
fn choose(flag: bool) -> i32 {
    if flag { 10 } else { 20 }
}
\end{lstlisting}
这个函数可以由入口、两个分支和一个合流块组成。if 在语法上只有一个节点，在控制流上却需要几个块。终结指令把这些块连接成图。

下图将上述 if 展开为条件、两个分支与合流块，显示终结指令怎样确定执行路径。

终结之后不得在同一块追加普通指令。否则这些指令没有明确的执行位置，也会使后继关系含糊。源程序在 return 后可能仍包含需要诊断的语法，但诊断继续分析与当前块继续生成指令是两个不同问题。

\section{SSA 与源语言可变变量}
SSA 的核心约定是每个值身份只定义一次。它不要求源程序的变量不可变，也不意味着一个变量只能赋值一次：
\begin{lstlisting}[language=Rustless,caption={一个可变变量的多次赋值}]
let mut x = 1;
x = x + 2;
printInt(x);
\end{lstlisting}
一种直接表示是给 x 分配存储位置，先 store 1，再 load 旧值，计算并 store 新值。另一种表示使用值版本：初始值为 $x_0$，计算结果为 $x_1=x_0+2$，输出使用 $x_1$。后者每个值只定义一次，却保留了源变量的赋值含义。

下图对照位置保持不变与值版本不断产生的关系，说明变量身份和计算值身份各自保持什么。

\node[irbox,right=of slot] (old) {$x_0=1$};
\node[irbox,below=of old] (new) {$x_1=x_0+2$};

SSA 使使用可以直接连接到定义，减少分析时反复追踪“这个名字最近在哪里被赋值”的工作。分支和循环带来的多个可能定义则通过 Phi 处理。若先采用存储位置表示，后续还可以在满足条件时将栈槽提升到 SSA；这种顺序适合把正确 lowering 与优化复杂度分开。

\section{Phi 的边语义}
当前 Phi 将结果与若干 incoming 对联系起来：
\begin{lstlisting}[language=C++,caption={当前 Phi 的数据形状}]
struct PhiIncoming {
  Operand value;
  BlockId predecessor;
};
struct Phi {
  Result result;
  std::vector<PhiIncoming> incoming;
};
\end{lstlisting}
在 choose 中，Phi 的结果取决于刚刚到达 join 的路径：从 then 到达时取 10，从 else 到达时取 20。它不是先执行一项比较再按顺序读取两个操作数，而是描述到达边上的值选择。

输入的使用被视为发生在对应边上。因此，在 then 中定义的一个值，可以成为 then 到 join 的 incoming，却不能直接成为 join 中普通加法的操作数，因为 else 路径没有经过该定义。

多个 Phi 在逻辑上同时选择各自的 incoming。不能将它们解释为串行赋值，否则交换两个旧值时会覆盖其中一个。它们还必须出现在块的普通指令之前，以保持入口选择与块内计算的区分。后端将 Phi 消除为边上的并行复制，这一过程在第二十章继续展开。

\section{支配关系}
若从函数入口到某个使用的所有路径都经过某个定义所在块，就称该块支配使用所在块。同块中还需要定义位于使用之前。这个条件把“先定义后使用”从一条线推广到了控制流图。

参数在进入函数时已经定义，可以被后续块使用。一个条件分支中的定义通常不能支配合流块，因为另一条路径绕过它；入口中的定义通常可以支配两个分支。Phi 的 incoming 则在相应前驱边的位置检查。

当前验证器先收集参数和指令的定义，再检查每个 LocalOperand 是否存在、类型是否相同，以及定义是否支配使用。它还区分同块的指令位置，避免接受一条指令引用自己的结果。检查不是只比较编号大小：编号由构造过程分配，不构成控制流证明。

支配集合通过迭代交集得到。对一个可达非入口块，其严格前驱支配集合的交集，加上块自身，形成新的支配集合。规模较小时，集合版本清楚且便于检查；若分析成为性能热点，再考虑更高效的支配算法，而不必在最初就引入难以阅读的实现。

前驱块集合与前驱边集合不是同一概念。一个 CondBranch 的两个目标可能恰好相同。这时只有一个不同的前驱块，却有两条到达边。

当前验证器已经分别保存两种关系：
\begin{lstlisting}[language=C++,caption={当前前驱与到达边的不同表示}]
using Predecessors = std::map<BlockId, std::set<BlockId>>;
using IncomingEdges =
    std::map<BlockId, std::multiset<BlockId>>;
\end{lstlisting}
支配分析只关心是否存在绕过定义的路径，唯一前驱足够；Phi 核对需要保留边重数。重复来源的 incoming 必须携带相同值，且数量与实际到达边一致。另一种可能设计是构造时把同目标条件分支规范化为普通分支，但必须同步改变 Phi，不能只修改图的一侧。

不可达块也需要明确策略。当前验证器对入口可达部分计算通常的支配集合，对不可达块采用保守的自支配集合。它仍检查基本结构和局部使用。这个策略可能拒绝某些在不可达区域中形式上更宽松的 IR；作为教学实现的明确限制，比偶然放过未定义关系更容易解释。

\section{Builder 的局部构造}
Builder 保存所借用的函数和当前 BlockId，不长期保存 vector 元素的引用。创建新块可能使 vector 扩容，而 BlockId 仍可以重新定位当前块。这个选择防止一个与编译原理无关的 C++ 对象失效问题污染 lowering。

以下是 \texttt{ir\_builder.cpp} 中追加流程的节选，省略了 Phi 排列检查：
\begin{lstlisting}[language=C++,caption={当前 Builder 的局部保护}]
void Builder::append(Instruction::Data data) {
  Instruction node{std::move(data), origin_};
  auto errors = verify_instruction(node);
  if (!errors.empty())
    throw std::invalid_argument(errors.front());
  auto &block = current();
  if (!block.instructions.empty() &&
      is_terminator(block.instructions.back()))
    throw std::logic_error("cannot append after a terminator");
  // The implementation also checks Phi placement here.
  block.instructions.push_back(std::move(node));
}
\end{lstlisting}
这是对当前流程的带省略摘录，注释只说明被省略的分支，不代表另一份可替代源码。Builder 在插入前检查单条指令的类型与结构，拒绝终结之后的追加，并保持 Phi 在前。固定大小 Alloca 被限制到入口，这是项目当前构造策略，有利于后续栈布局；它不是所有 LLVM IR 必须遵循的普遍规则。

Builder 还能把源节点设置为当前 Origin，随后生成的指令携带这一来源。值编号耗尽或没有选定插入块都会明确报错。失败的构造可能留下编号间隙，但间隙不改变值身份的含义；验证需要的是唯一与有效，而不是编号连续。

单条指令检查只认识自身载荷。完整模块还需核对块目标、函数声明、调用与返回类型、定义唯一性、类型一致性和支配关系。因而 Builder 与 Verifier 是互补的。

验证器先排除错误 CFG，再进行依赖合法后继的 SSA 检查。若缺失目标仍被当成存在的块访问，验证器自己反而会崩溃，无法给出原来的错误。按依赖顺序验证，同样体现了清楚的设计：后一个证明建立在前一个已确认的条件上。

验证器报告函数、可选块和可选来源。诊断范围与约束范围对应，使错误定位更有意义。它不会证明源码和 IR 等价；一份完全合法的 IR 仍可能使用了错误的算术操作。结构验证与 lowering 的语义正确性必须分开检验。

\section{构造中间状态与发布边界}
构造函数时，某个块可能暂时没有终结，Phi 的目标块也可能尚未写完。这些是受控的中间状态。模块最终交给打印器、优化器或后端时，则必须满足完整不变量。

将局部构造限制得过严，会迫使构造过程采用别扭的顺序；将最终验证完全取消，又会把错误推给后端。当前设计允许用明确载荷直接构造，再在模块边界验证，也提供 Builder 作为更便于使用的入口。

学习时可以故意制造错误 IR：将一个 I32 操作数替换为 I1，删除一个分支目标，在两个指令中重复定义同一 ValueId，或让 then 中的值出现在 join 的普通运算中。每个反例应违反一条可解释的关系，而不是只断言“验证器返回错误”。这样的练习能够检验不变量是否足够准确。

\section{内部验证与 LLVM 验证}
项目验证器保证项目 IR 的约定，外部 LLVM 验证器检查生成文本是否满足 LLVM 的结构与指令定义。二者一致并不自动证明源码语义正确，但不一致可以揭示映射或内部约束的缺口。

多重 Phi 边就是合适的独立检验：内部图保留两条同目标分支边，输出两个相同 incoming，外部验证应接受；只输出一次则应拒绝。期望来自边语义，而不是来自打印器当前恰好输出什么。关于 LLVM 的整体合法性与 Phi 定义，可以查阅其\href{https://llvm.org/docs/LangRef.html#well-formedness}{合法性说明}与\href{https://llvm.org/docs/LangRef.html#phi-instruction}{Phi 指令说明}。

本章建立了“计算发生在哪里、值从哪里来”的关系。下一章将补上另一项知识：一个对象占多少空间，以及函数边界如何安排这些值。

\chapter{数据布局与函数的内部 ABI}
\label{chap:layout-abi}
\section*{本章导读}
一个类型有明确含义，还不等于它已经有明确的存储方式。结构体的字段偏移、数组的元素间距、函数的参数与返回值，都需要把类型知识落实到具体机器。本章阅读当前 TargetLayout 与 SemanticBridge，逐步推导大小、对齐和内部调用约定。学习者应能手工计算一个小结构的布局，并能解释通过地址传递一个值为什么没有把它变成源语言引用。

\section{大小、对齐与补齐}
使用以下结构作为本章的贯穿例子：
\begin{lstlisting}[language=Rustless,caption={包含不同对齐要求的 Packet}]
struct Packet {
    flag: bool,
    count: i32,
    bits: [bool; 3]
}
\end{lstlisting}
当前内部布局保持声明字段顺序。flag 的大小和对齐均为一，因此位于偏移零。count 需要四字节对齐，下一个满足条件的偏移是四。bits 需要三个字节，位于偏移八。字段最后结束于偏移十一，但整个结构需要满足最大字段对齐四，因此总大小补齐到十二。

若已使用空间为 $s$，下一字段对齐为 $a$，其偏移为
\[
  \operatorname{align}(s,a)=\left\lceil\frac{s}{a}\right\rceil a.
\]
字段放置后更新已使用空间，所有字段完成后再按结构对齐补齐。尾部补齐的意义在数组中尤其明确：第二个 Packet 的起点若是十一，其 count 就不再处于四字节对齐位置。

下图把这些计算落实到 Packet 的十二个字节，标出字段、内部补齐和尾部补齐。

补齐区域不属于源语言字段。布局保持源码顺序是当前 Rustless 的内部选择，不能借用这一例子宣称完整 Rust 的默认结构布局也固定如此。将内部选择准确陈述出来，才能知道以后改变布局时会影响哪些接口。

\section{RV32 的标量与容器布局}
\texttt{target\_layout.hpp} 集中描述当前目标。整数和指针的存储大小与对齐均为四，布尔存储为一，Unit 为大小零、对齐一。Vec 的对象描述包含数据地址、长度和容量三项，当前占十二字节。
\begin{lstlisting}[language=C++,caption={当前目标布局的代表性方法}]
constexpr unsigned integer_bits() const { return 32; }
constexpr Layout integer() const {
  return {integer_bits() / 8, integer_bits() / 8};
}
constexpr Layout pointer() const { return integer(); }
constexpr Layout boolean() const { return {1, 1}; }
constexpr Layout unit() const { return {0, 1}; }
constexpr std::uint32_t shift_count_mask() const {
  return integer_bits() - 1;
}
\end{lstlisting}
同一目标描述还提供 LLVM 数据布局和目标三元组，避免打印器和语义桥接分别写入互不相符的常数。Vec 字段偏移由 pointer 与 integer 的布局计算，而不是在多个消费者中重复写零、四、八。

这样的集中描述改善维护，也明确了目前的范围：TargetLayout 只提供 RV32 实例，IR 的指针转换也受三十二位约束。它不是已经支持任意目标的通用框架。若以后增加 RV64，应同时检查源整数宽度、指针运算、布局、调用分类与输出信息，不能只将一个常数改成六十四。

\section{数组与嵌套结构}
数组元素连续存储。若元素大小已经包含其尾部补齐，则元素间距就是该大小，数组大小为元素大小乘长度，数组对齐继承元素对齐。
\begin{lstlisting}[language=Rustless,caption={数组、零长度数组与间接递归}]
let values: [i32; 3] = [1, 2, 3];
let empty: [i32; 0] = [];
struct Link { next: Box<Link> }
\end{lstlisting}
前两个声明用于讨论数组；Link 用于讨论类型布局，并不是可凭此构造一个有限终止链的完整程序。内嵌递归 \texttt{struct Bad \{ next: Bad \}} 会要求无限展开，必须拒绝；Box 提供固定大小的指针表示，因此布局不需要展开其指向对象。

布局计算还要防止算术溢出。当前实现先比较长度与允许最大对象大小除以元素大小，再执行乘法。零大小元素要单独处理，否则除以零；它们的数组即使长度很大，存储大小仍可为零。零长度数组同样不能因为没有元素就丢失其类型和对齐知识。

对嵌套结构，计算沿内嵌字段递归，并用正在解析的符号集合检测环。大小错误属于表示边界的错误，不应等到生成一个截断的偏移后才发现。缓存已完成布局还避免对相同字段类型反复展开。

\section{SemanticBridge 怎样取得布局}
布局消费已检查的字段类型和声明顺序。当前结构体类型携带 SymbolId，桥接按该身份取得结构体语义，再按字段 SymbolId 查询类型。显示名称不承担布局索引的职责。
\begin{lstlisting}[language=C++,caption={当前结构体布局计算的核心节选}]
StructLayout result{symbol, target_.unit(), {}};
for (auto field : semantic_.structure(symbol).fields) {
  auto value = compute_layout(semantic_.symbol_type(field));
  auto offset = align_size(result.layout.bytes,
                           value.alignment, target_);
  result.fields.push_back({field, offset, value});
  result.layout.bytes =
      checked_size(std::uint64_t{offset} + value.bytes, target_);
  result.layout.alignment =
      std::max(result.layout.alignment, value.alignment);
}
\end{lstlisting}
这段来自 \texttt{ir\_semantic.cpp}，前后还有缓存、递归检测与最终补齐。每个 FieldLayout 保存字段身份、偏移及布局，使后续 \texttt{packet.count} 可以通过已经解析的字段查找存储信息，而不重新在源码名称列表中猜测位置。

完整字段导出是这一算法的前提。若两字段结构只导出一个字段，循环本身仍可得到一个看似合理的大小，但含义已经错误。因此前一篇讲述的完整对应验证，是布局正确性的一部分。下游不宜在每次访问时重新遍历 AST 核对；受控发布一次验证，随后使用冻结事实，既清楚又降低重复成本。

\section{直接与间接传递}
ABI 约定函数边界上的值如何表示。当前内部约定直接传递标量，把数组、结构体和 Vec 作为间接聚合传递。\texttt{AbiValue} 保留机器类型、传递类别和存储布局：
\begin{lstlisting}[language=C++,caption={当前内部 ABI 的值描述}]
enum class Passing { Direct, Indirect };
struct AbiValue {
  Type type;
  Passing passing;
  Layout layout;
};
\end{lstlisting}
Indirect 表示聚合值的存储地址，不等同于源语言的引用类型。两者可能使用同一种机器 Ptr，但一个负责实现值传递，一个表达程序显式借用。它们的可变性、别名和复制要求需要继续保留在语义描述中。

Unit 参数在语义签名中仍然存在，可以要求调用者提供对应的表达式；该表达式还可能包含副作用。但 Unit 不需要机器值，因此不会占据机器参数位置。省略机器参数绝不能顺便省略参数表达式的求值。

\section{隐藏返回缓冲区}
以以下函数为例：
\begin{lstlisting}[language=Rustless,caption={包含 Unit 参数的聚合返回}]
fn take(unit: (), value: Packet) -> Packet {
    value
}
\end{lstlisting}
其当前内部声明是一个返回 Void 的函数，首先接收输出地址，随后接收 Packet 参数的地址。Unit 的源参数位置仍由语义签名保留，但机器参数列表中省略它。

下图按位置展示源签名怎样变成内部签名，说明隐藏返回参数、接收者和普通参数为何需要明确排序。
\begin{figure}[htbp]\centering

\node[irbox,below=of s,text width=104mm] (d) {内部签名：\texttt{take(output: Ptr, value: Ptr) -> Void}};
\draw[irarrow] (s)--node[right,font=\small]{分类与重排}(d);

当前 \texttt{declaration()} 将间接结果改为 Void，并将 Ptr 加入参数开头；若存在接收者，再加入接收者，最后加入普通参数。它使用已解析的 FunctionSemantics，而不是再次解析 AST 中的类型写法。方法和关联函数的名称也来自语义符号。

隐藏参数是表示转换产生的知识，需要在调试输出和调用构造中可识别。它不改变源语言函数有几个参数，却改变机器接口如何传递结果。把这两层数量分开，是避免调用签名错位的关键。

\section{间接参数仍需遵循值语义}
若调用 \texttt{take((), packet)}，把 packet 地址交给被调用者，并不自动证明按值调用已正确实现。被调用者若修改其参数，是否应影响调用者对象，取决于源语言值语义；需要复制时，调用转换必须创建适当的副本或快照。

\section{内部 ABI 与平台 ABI}
内部 ABI 可以选择简单、一致的聚合规则；平台 ABI 则决定与其他编译器、运行时和系统函数的互操作。当前“全部聚合间接传递”是内部约定。RISC-V 平台整数调用规则会按大小和分类处理聚合，不能将二者直接等同。

同一源程序可能同时调用内部 Rustless 函数和外部运行时函数。前者遵守内部声明，后者必须有明确外部签名和必要适配。将平台 ABI 规则混入源语义类型，会让同一类型因调用对象不同而难以解释；将其放在函数边界分类中，则能保持源类型稳定。

平台调用细节以 \href{https://riscv-non-isa.github.io/riscv-elf-psabi-doc/}{RISC-V ABI 规范}为准。本章只建立分离原则，具体寄存器和栈规则在第二十一章展开。

\section{目标布局与调用分类的分离}
目前 TargetLayout 已经集中机器宽度、存储对齐、Vec 字段和移位计数掩码。SemanticBridge 在其上计算具体类型的布局和内部函数 ABI。两个对象分别回答“机器怎样存储”与“这个函数怎样传递”。

后续若出现多目标、外部聚合调用或不同调用约定，可进一步引入专门的 ABI 分类对象。它可以把一个语义参数分解为多个机器位置，或者明确输出缓冲区属性。增加这一层应由真实的分类差异推动，而不是为了模仿大型编译器的类名。

本章给出了地址计算与调用所需的存储知识。下一章将结合已检查的语法，推导如何生成显式指令、位置操作和控制流。

\chapter{lowering：值、位置与控制流}
\label{chap:lowering}
\section*{本章导读}
已有 IR 可以容纳计算，语义结果可以解释语法，布局可以确定地址。本章把三者连接起来，推导 lowering，即向较低层表示的转换。学习重点是区分计算值、存储位置和是否正常继续，避免让一个 Operand 配合几个含糊标志承担所有含义。当前项目已经提供运算描述和桥接；完整表达式与语句 lowering 尚未完成，本章的转换算法属于设计推导。

转换需要 AST 的具体载荷，以及已成功发布的语义事实。AST 告诉转换器一个节点是 BinaryExpr 还是 FieldExpr；语义事实告诉它操作数的有效类型、需要哪些转换、名字指向哪个符号；布局告诉它字段偏移和元素间距。

\section{Value、Place 与转换结果}
\texttt{packet.count} 可以表示可写位置，也可以在算术中读取成一个值；\texttt{packet.count + 1} 只能表示计算结果。二者若都返回 Ptr，再由一个 bool 解释“是不是地址”，后续每个消费者都会重复辨认其含义。

建议采用下列教学接口。它尚未加入当前项目，用于展示结果类别怎样表达：
\begin{lstlisting}[language=C++,caption={设计推导：值、位置与发散结果}]
struct ScalarValue { ir::Operand value; };
struct Place {
  ir::Operand address;
  SemanticTypePtr type;
  ir::Layout layout;
};
struct AggregateValue { Place storage; };
struct UnitValue {};
struct Diverged {};
using Lowered = std::variant<ScalarValue, AggregateValue,
                             UnitValue, Diverged>;
// lower_place(...) returns Place only for a valid place expression.
\end{lstlisting}
Place 和 ScalarValue 分开，使读取成为显式操作；AggregateValue 表示一个源语言聚合值由某处存储承载，并不表示它是引用。Diverged 说明该路径已经终止。一个专门的 lower-place 入口只接受语义上确认的位置，减少“请求一个值却意外得到地址”的情况。

表示不必一次容纳完整语言。最初可以只支持标量、Unit 和简单聚合存储，逐步增加对象寿命知识。但应从开始就避免把结果类型、表示类别和控制流状态压缩成同一个空 Operand。

\section{标量读取与写入}
路径表达式已经绑定 SymbolId，转换器可维护 SymbolId 到本地存储或参数值的映射。读取一个存储变量产生 load，赋值产生 store，借用位置取得地址，显式解引用则从引用值得到新的 Place。
\begin{lstlisting}[language=Rustless,caption={读取、借用、解引用与写入}]
let mut x = 1;
let r = &mut x;
*r = 2;
let result = x + 3;
\end{lstlisting}
这里 r 的机器值是地址；读取 r 取得该地址，并不会立刻读取 x。\texttt{*r} 将地址解释为 x 的位置；作为赋值目标时使用 store，作为算术操作数时才进一步 load。清楚区分这些步骤，可以避免多读一次引用或少读一次引用。

bool 读取的逻辑结果为 I1，内存布局为一字节，对齐为一。Builder 的 load/store 默认对齐是四，lowering 必须依据实际 Layout 显式传入正确对齐。一个方便的默认值不能替代对象知识。

\section{字段与索引投影}
沿用 Packet，考虑：

packet.bits[1] = true;
\end{lstlisting}
count 地址为 Packet 基址加四。bits 的基址为 Packet 基址加八；第二个 bool 的地址再加一个元素间距。当前 Gep 接收字节偏移，因此字段和元素的语义计算必须在 lowering 中完成。

Field 和 Index 的 receiver 可能需要自动解引用。当前语义结果把接收对象的转换单独保存在 receiver 用途中，不能把这些转换误用到字段或索引的最终值上。例如对一个含整数元素的共享引用数组，先解引用数组得到元素位置；最终整数仍是整数，不能继续把它当成引用。

索引越界的行为属于语言约定。转换器应据此生成检查或依赖已经证明的条件，不能只因为地址计算能够完成就默认为访问合法。LLVM 指针指令的属性也必须有对应证明，不能任意加入更强的 inbounds 等承诺。

\section{一元、二元、cast 与有序转换}
当前语义事实把每次使用保存为 \texttt{OperandSemantics}，包含节点身份、有效类型和有序 adjustments。以下是实际类型：
\begin{lstlisting}[language=C++,caption={当前操作数使用事实}]
struct OperandSemantics {
  ast::NodeId node;
  SemanticTypePtr effective_type;
  std::vector<Adjustment> adjustments;
};
\end{lstlisting}
对于 \texttt{\&x + \&x}，表达式本身是引用，使用时的有效操作数是整数。转换器先计算两个操作数表达式，再按照规定的使用顺序执行解引用等转换。原始类型不被覆盖，因而同一个事实仍可说明“值从何种对象得到”。

当前 UnaryLowering 已区分标量运算与解引用位置：负号描述为零减操作数；bool 取反描述为 I1 与一异或；整数取反描述为 I32 与全一异或；显式解引用描述为 DereferencePlace，保留元素类型和布局。\texttt{*boxed} 即使得到结构体，也不需要伪装成普通指针比较值。

二元描述区分 ScalarArithmetic、ScalarComparison、ShortCircuit 和 StructuralEquality，并保留两侧使用事实。桥接只把语义层已经选择的运算类别映射到机器操作，不再用 AST 运算符独立解释类型规则。

源语言 cast 当前接受整数间转换与 bool 到整数转换。RV32 整数间三十二位 cast 常只改变语义解释；bool 到整数需要扩展。IR 还提供 PtrToInt 与 IntToPtr，但它们属于底层指令能力，不意味着源语言已允许任意指针 cast。

\section{运算映射必须保留语言语义}
三十二位移位需要按当前子集的低五位计数规则处理。例如计数三十二经掩码后为零。若直接输出超出位宽的 LLVM 移位，会得到不符合这一约定的 poison 行为。桥接因此不仅返回 Shl、AShr 或 LShr，还携带 shift-count-mask 意图。

\begin{lstlisting}[language=C++,caption={当前标量运算描述中的移位意图}]
struct ScalarArithmetic {

这项描述已经实现；自动生成掩码指令的完整表达式 lowering 尚未实现。未来转换器应在输出移位前发出 And，不能只读取 op 而忽略 optional。复合移位使用同一描述，常量求值也必须遵守同一计数规则。

除零、最小有符号整数除以负一、算术溢出等边界也需要明确语言预期。不能通过“后端提供这条指令”推导源程序的规定行为。若规定运行时错误，就需要检查与错误路径；若规定位模式运算，就不能任意加入不溢出标志。\href{https://llvm.org/docs/LangRef.html#shl-instruction}{LLVM 移位定义}可以用于核对目标操作的具体边界，而语言预期仍须由 Rustless 规则和独立测试确定。

\section{赋值与复合赋值的求值}
目标只应定位一次。例如 \texttt{a[index()] += value} 若调用 index 两次，可能修改副作用或得到不同位置。转换器应保存目标 Place，读旧值，进行已解析运算，再写回同一 Place。

普通赋值还需要处理左右两侧的执行次序。现有测试材料明确检验普通赋值右侧先执行，因此 \texttt{*destination(\&mut x) = mark()} 应先调用 mark，再定位 destination。语法中的“目标在左、值在右”不等于运行顺序。

参考 Rx-Compiler 将普通与复合赋值放在一个旧分支中，并选择先右侧后目标。现有相关测试没有锁定复合两操作数的相对次序，不能从这一测试空白推出任意重排合法。新 lowering 应按明确的子集约定选择顺序，并为带副作用情形建立独立预期。

赋值表达式的结果为 Unit。复合赋值的内部算术结果用于写回，不能误当成整个表达式的结果。当前 ResolvedBinary 作为 compound 事实保存写回类型，而 ExpressionSemantics 的表达式类型仍为 Unit；这种区分防止二者在返回或参数上下文中混用。

\section{短路逻辑与条件结果}
\begin{lstlisting}[language=Rustless,caption={不能用 eager 位运算代替的逻辑式}]
fn check() -> bool { printInt(1); true }
fn main() {
    let valid = false;
    let ready = valid && check();
}
\end{lstlisting}
valid 为假时 check 不应执行。转换器先判断左侧，再决定是否进入右侧块，最后合流产生 bool。若用普通 And 同时计算两个操作数，结果可能相同，输出却已经不同。

\section{循环与跳转上下文}
\begin{lstlisting}[language=Rustless,caption={两种循环的不同结果与目标}]
let answer: i32 = loop {
    break 7;
};
let mut i = 0;
while i < 3 {
    i += 1;
    if i == 2 { continue; }
}
\end{lstlisting}
loop 的 break 值可以形成表达式结果；while 的结果为 Unit。转换器需要保存当前循环的继续目标、退出目标和结果收集方式。嵌套循环用栈保存这些上下文，break 和 continue 使用最近一层，不能只维护一个全局 exit 编号。

\section{Never 与终结之后的转换}
Never 描述没有正常完成的表达式，例如 return、continue 或不退出的循环。转换器遇到 Diverged 后应停止当前路径的普通指令构造。它不应把 Never 替换为一个随意常量，再继续执行后面的加法。

源语义检查可能继续访问后续语法，以发现未定义名字或错误类型；lowering 则不为不存在的正常路径生成执行步骤。两个阶段遍历同一 AST，却有不同目标，这也说明通用树 walk 不能代替每个阶段的上下文算法。

至此，标量计算、位置投影和控制转移已经有清楚的转换方向。下一章把聚合构造、内容语义和调用放回这一框架，并讨论它们怎样连接到运行时。

\chapter{聚合值、调用与运行时操作的转换}
\label{chap:aggregate-calls}
\section*{本章导读}
数组和结构体包含多个组成部分，Box 与 Vec 又把对象分布到不同存储位置。理解这些值时，需要同时回答两个问题：对象放在哪里，以及语言规定对其内容做什么。本章先从初始化推导存储操作，再讨论复制、相等和调用。读者将看到，地址可以帮助实现一个值，却不能代替这个值的语义。

本章使用的布局、内部 ABI、运算描述和调用描述已经存在于 Rustless。由这些描述生成完整函数体、容器操作及运行时调用，仍属于后续设计推导。以下执行步骤用来说明应当如何实现，不能视为当前编译器已经生成的可执行程序。

\section{在目标位置构造聚合值}
\begin{lstlisting}[language=Rustless,caption={聚合初始化与聚合返回共用的构造问题}]
#[derive(Clone, Copy, PartialEq, Eq)]
struct Pair { left: i32, right: i32 }
fn pair(x: i32) -> Pair {
    Pair { left: x, right: x + 1 }
}
fn main() {
    let p = pair(10);
    printInt(p.right);
}
\end{lstlisting}
最直接的转换方案先为结构体表达式分配临时存储，把两个字段写入其中，然后复制到返回缓冲区。调用者接着把返回缓冲区复制到局部变量 p。这条路线容易说明，但中间存储及复制可能多于语言语义所需。

另一种方案让聚合转换函数接收一个目标 Place。当 pair 构造其结果时，直接把字段写入调用者提供的返回缓冲区；当局部变量初始化时，也可以直接使用该变量的存储。第十七章所建议的值、位置与控制流接口因此可以补充一个“写入目标”的操作，而不必要求所有聚合表达式先返回一个独立临时地址。

这种做法常称为面向目标的构造。它的正确性依赖目标空间尚未包含需要保留的旧值、目标不与仍需读取的输入发生有害重叠，以及字段求值顺序保持不变。例如把一个对象赋值给它自己的某个组成部分，不能简单套用初始化规则。借用检查、移动规则和存储寿命以后若变得更完整，这些条件也需要更精确的表达。

\section{列表数组与重复数组：复制不是重复求值}
\begin{lstlisting}[language=Rustless,caption={三种数组初始化形成不同的执行要求}]
fn next() -> i32 { getInt() }
fn main() {
    let listed = [next(), next(), next()];
    let repeated = [next(); 3];
    let empty: [i32; 0] = [next(); 0];
}
\end{lstlisting}
列表数组包含三个不同的元素表达式，应按数组元素的源码顺序分别求值。重复数组只有一个元素表达式和一个次数表达式。次数在语义阶段确定为常量长度，元素先求值，再把所得值用于每个数组位置。因此 repeated 的含义不能通过展开成三个 next 调用来实现。

当前语义实现 \texttt{check\_repeat\_array} 在长度大于一时要求元素支持 Copy；长度为一不需要重复复制。它先检查元素表达式，再确定数组类型。语义检查本身并不执行函数，因此零长度例子的输入行为必须由后续 lowering 明确规定并检验。参考 Rx-Compiler 的数组转换会先求值元素，再执行长度次写入；沿用这条路线时，empty 仍会调用一次 next。若语言规范另作规定，应先统一语义和测试预期，再选择转换算法。

对于已有数组类型，元素地址由“数组基址加索引乘 stride”得到。静态长度较小时可以逐项展开，长度较大时可以生成循环；两者必须实现相同的求值次数和复制含义。零长度需要避免实际元素读写，也需要保留元素表达式中规定发生的行为。对象字节数为零并不意味着整个初始化表达式没有行为。

下面是当前重复数组检查中决定能力要求的真实片段，来自 \texttt{src/semantic.cpp} 的 \texttt{check\_repeat\_array}。它说明 Copy 是语言条件，而不是由 \texttt{memcpy} 的可用性推出的条件。
\begin{lstlisting}[language=C++,caption={当前重复数组的能力条件}]
auto result = types_.array(first.type, length.value_or(0));
if (result->length() > 1 && !supports(first.type, "Copy", "", {}))
  report(node.span, "array repetition requires Copy");
\end{lstlisting}

\section{字段初始化：求值顺序与布局顺序}
\begin{lstlisting}[language=Rustless,caption={源码字段顺序与声明字段顺序可以不同}]
#[derive(Clone, Copy, PartialEq, Eq)]
struct Pair { left: i32, right: i32 }
fn main() {
    let p = Pair { right: getInt(), left: getInt() };
    printInt(p.left);
}
\end{lstlisting}
声明顺序决定当前内部布局中的字段偏移；初始化顺序决定上述两个输入调用的先后。转换器应先找到 right 的字段身份及偏移，再把第一次输入写到对应位置，然后处理 left。把初始化列表按偏移排序再求值，会改变程序读取输入的顺序。

这里有三种不能合并的顺序：源码初始化顺序、声明字段顺序和机器访存指令顺序。前两种是输入信息，第三种可以在满足语言规则和内存约束的条件下调整。当前 AST 用有序 FieldInit 保存第一种顺序，语义事实把每个初始化关联到声明字段，布局按 SymbolId 提供第二种顺序对应的偏移。三个阶段共同完成一项明确的关系，而不是各自重新按字符串猜测字段。

缺失字段、重复字段与不相容类型应在语义阶段拒绝。lowering 只消费已经确认完整的初始化，并检查查询接口的完整性。若缺失字段偷偷被零填充，程序虽然可能形成某种字节序列，却违背前端已经规定的语言。

\section{Copy、Clone 与内容相等}
Copy 表示语言允许复制值；Clone 表示一种显式的复制操作；内容相等则产生布尔结果。三者都可能递归访问组成部分，但它们的结果、资源要求和控制流不同。为一个整数执行 Copy 可以只是复制位；为 Box 执行 clone 通常需要新对象，并递归克隆内容。当前语义能力规则不会把 Box 自动判定为 Copy。

\begin{lstlisting}[language=Rustless,caption={标量成员的结构体可以组合复制与相等能力}]
#[derive(Clone, Copy, PartialEq, Eq)]
struct Pair { left: i32, right: i32 }
fn main() {
    let p = Pair { left: 1, right: 2 };
    let q = p.clone();
    let same = p == q;
    printInt(if same { 1 } else { 0 });
}
\end{lstlisting}
对于 Pair，克隆可以按字段复制，比较可以先比较 left，只有需要时再比较 right。对于含有 Box 的结构体，按字段克隆需要调用对应元素的克隆规则；复制结构体所占的字节会复制指针，却不会产生新的 Box 内容对象。因此字节复制只能作为实现某种已确认语义的工具。

第十六章 Packet 的填充字节进一步说明这个区别。两个对象的所有字段相等，填充字节仍可能不同。直接用整个对象的字节比较代替字段比较，可能把语义相等的值判为不相等，也可能读取未经初始化的填充。应当根据字段类型比较有效内容；只有在确实证明表示没有这些差异时，才可引入整块比较优化。

维护上的收益来自把能力分析和操作实现连接起来：前端说明该类型是否具备 Clone 或 Eq，转换阶段根据同一类型描述选择字段算法，目标布局只回答字节位置。任一层都不需要把另两层的信息硬编码成特例。

\section{Box 与 Vec：对象表示和资源行为}
Box 的直接表示可以是一个指针，但构造操作还需要知道被装入值的大小、对齐和初始化方式。\texttt{Box::<Pair>::new(p)} 的设计步骤是请求适当存储，再按 Pair 的值语义把 p 放到其中。分配失败怎样处理、零大小对象是否需要独特地址、何时释放，都应成为运行时契约的组成部分。

Vec 的当前 RV32 布局是数据指针、长度、容量三个字段，偏移由 \texttt{TargetLayout::vector()} 提供。长度是已经初始化的元素数量，容量是可容纳的元素数量，二者不能混为一个计数。Vec::new 可以形成零长度、零容量和空数据指针，但 push 需要检查空间、必要时扩容，并在正确的元素位置构造新值。

\begin{lstlisting}[language=Rustless,caption={Vec 操作既访问描述符，也访问元素存储}]
fn main() {
    let mut values = Vec::<i32>::new();
    values.push(10);
    values.push(20);
    let first = values.remove(0);
    printInt(first);
    printInt(values.len() as i32);
}
\end{lstlisting}
remove 既返回被移除元素，又使后续元素前移并减少长度。移动区域可能重叠，因此若选择运行时的字节移动操作，要使用支持重叠的契约；不能把一般 \texttt{memcpy} 当成同样的操作。对于复杂元素，字节移动是否符合语言的移动规则，也需要由元素能力和所有权规则决定。

未来若提供释放与析构，Vec 只销毁长度范围内已初始化的元素，然后释放容量对应的存储。当前前端和布局基础尚未建立完整资源管理执行流程，因此本节将这些要求作为运行时设计边界。清楚记录这条边界，有助于防止“有一个指针表示”被误读为“生命周期已经实现”。

\section{辅助函数的生成与复用}
给每个表达式展开一份完整结构比较，会在大类型上造成重复代码。另一条路线为具体类型生成辅助函数，例如 \texttt{eq\_Pair}、\texttt{clone\_Pair}，所有相关使用共享它们。缓存的键应包含具体语义类型和操作种类；仅使用类型显示名字，会把不同声明身份混在一起。

下面是 Rx-Compiler 参考实现 \texttt{src/llvm/lower.cpp} 中辅助函数体生成的真实循环。该实现只作为算法参照，其旧表示无需原样保留。
\begin{lstlisting}[language=C++,caption={参考实现允许构造辅助函数时登记新的依赖}]
// Recursive concrete helpers are registered before their bodies are built.
for (std::size_t i = 0; i < helpers.size(); ++i) {
  auto h = helpers[i];
  FunctionBuilder b(*this, h.name,
                    h.kind == Helper::Kind::Equal ? Type::I1 : Type::Void);
  b.helper(h);
  module.functions.push_back(std::move(b.function));
}
\end{lstlisting}

先登记函数身份，再生成函数体，是处理递归依赖的关键。如果 \texttt{Link} 通过 Box 间接包含另一个 Link，比较 Link 时会需要比较 Box<Link>，后者又需要 Link 比较。若每次遇到类型都立即递归生成新函数体，就会无限展开；若查询到已登记身份便生成调用，则依赖可以有限地表示。

\section{从已解析调用到 ABI 参数}
\begin{lstlisting}[language=Rustless,caption={函数别名和方法调用必须使用已解析目标}]
#[derive(Clone, Copy, PartialEq, Eq)]
struct Pair { left: i32, right: i32 }
impl Pair { fn first(&self) -> i32 { self.left } }
fn copy_pair(value: Pair) -> Pair { value }
fn main() {
    let p = Pair { left: 3, right: 4 };
    let alias = copy_pair;
    let q = alias(p);
    printInt(q.first());
}
\end{lstlisting}
alias 是使用处的名字，实际调用目标仍是 copy\_pair 的声明身份。桥接必须消费语义检查已经解析出的 FunctionTarget，不能用字符串 alias 再查找一个函数。方法的 receiver 同样已有调整序列，例如为 q.first() 形成共享借用；转换器不应另行猜测要自动解引用多少层。

当前 \texttt{include/rx/ir\_semantic.hpp} 提供以下调用描述。
\begin{lstlisting}[language=C++,caption={已经实现的调用转换计划}]
struct FunctionCall { FunctionAbi signature; };
struct BuiltinCall { BuiltinId builtin; };
struct CallLowering {
  std::variant<FunctionCall, BuiltinCall> target;
  std::optional<OperandSemantics> receiver;
  std::vector<OperandSemantics> arguments;
  SemanticTypePtr result;
};
\end{lstlisting}
普通调用携带内部 ABI，内建调用携带专门身份。receiver 与普通参数分离，参数 vector 保持源码次序。对于上述 copy\_pair，内部参数和结果都是间接聚合：后续转换需要准备参数副本和结果缓冲区，再发出调用；对于 first，receiver 的借用可以映射为对象地址，返回整数则直接映射为标量结果。

下面摘自 \texttt{src/llvm/ir\_call.cpp} 的 \texttt{lower\_call}；目标分派与 receiver 取值展示了它消费事实的方式。
\begin{lstlisting}[language=C++,caption={当前调用桥接依据具体身份选择目标}]
const auto &fact = semantic_.expression(node);
if (!fact.callable)
  throw std::invalid_argument("call expression lacks a resolved target");
auto target = std::visit(
    ast::Overloaded{
        [&](const FunctionTarget &value) -> decltype(CallLowering::target) {
          return FunctionCall{function(value.symbol)};
        },
        [](const BuiltinTarget &value) -> decltype(CallLowering::target) {
          return BuiltinCall{value.builtin};
        }},
    *fact.callable);
CallLowering result{std::move(target), fact.receiver, {}, fact.type};
\end{lstlisting}

参数的有效类型由其检查结果及最后一个 adjustment 的目标确定，全部有序 adjustments 仍被保留。当前描述没有生成参数存储、实际借用指令或调用指令；这些是此后 lowering 的职责。使用函数对象和载荷对象的桥接入口还检查它们确实属于同一个 AST owner，以阻止从别的节点借来一个形状相同的载荷。

\section{内建操作需要一致的身份和契约}
内建函数可以拥有多种源拼写，例如已有输入输出别名。拼写适合诊断，BuiltinId 适合后续分派。当前 \texttt{include/rx/builtin.hpp} 的独立枚举覆盖输入输出、Box::new、Vec::new、clone、len、is\_empty、push 和 remove；它们不是用户声明的 SymbolId，也不应伪造用户函数身份。

这项集中身份已经实现，但身份表并不等于完整运行时说明。后续可以为每个 BuiltinId 建立一致描述：语义参数规则、receiver 能力、返回规则、内存效果、实现符号以及机器 ABI。有些操作通过普通运行时函数实现，有些要按具体元素类型生成辅助函数，还有些可以直接生成少量 IR。表中应表达这些区别，而不是强迫所有内建都使用同一个字符串调用方案。

\begin{lstlisting}[language=C++,caption={教学建议：将运行时效果作为明确契约}]
// Proposed interface, not an existing Rustless definition.
struct RuntimeEffect {
  bool reads_memory;
  bool writes_memory;
  bool performs_io;
  bool may_fail;
};
struct RuntimeDeclaration {
  std::string symbol;
  ir::Declaration signature;
  RuntimeEffect effect;
};
\end{lstlisting}
独立声明使 verifier 能检查参数和结果类型，也使优化器有依据判断调用能否移动或删除。能力与资源行为变化时，维护者可以沿着 BuiltinId 找到相关规则，减少分散字符串约定带来的遗漏。

\section{何时需要另一层有类型的中间表示}
本章的构造、借用、聚合复制和容器操作若全部直接展开为 load/store/call，机器 IR 将很快失去“这是一次结构体克隆”的概念。若后续分析需要反复回答这个问题，可以先保留一个较高层的有类型表示，再统一展开到当前 IR。

例如教学上的中层操作可以包括聚合构造、Place 投影、显式调整、内容比较和已解析调用。它们的操作数已指向具体声明和具体语义类型，摆脱语法细节，同时尚未抹去语言关系。\href{https://rustc-dev-guide.rust-lang.org/mir/index.html}{rustc 的 MIR 介绍}展示了以基本块及位置为中心的中间表示，这为“让值与存储关系明确”提供一种经典参照。

新增层次也带来成本：每个操作需要定义不变量、来源、访问接口、验证器和转换路径。若当前目标只是把一个较小的已检查 AST 转成机器 IR，直接消费 SemanticIndex 与桥接描述可以更简洁。只有明确分析或优化需要反复使用某项被展开后丢失的信息，才有充分理由增加表示层。

现在，语法树中的聚合和调用已经可以被分解成明确的计算、位置及运行时要求。下一章研究怎样调整这些计算，同时保持它们所规定的行为。

\chapter{优化为何正确：行为、分析与变换}
\label{chap:optimization}
\section*{本章导读}
一条指令的结果没有被使用，并不说明这条指令可以删除；两条指令看起来互不相关，也不说明可以交换顺序。本章从可观察行为出发，讨论简单优化的证明依据，再介绍分析信息与变换之间的关系。读者不必先实现大型优化器，也可以学会为每一次改写提出准确的理由。

当前 Rustless 提供 IR、操作数和后继枚举、效果的基本分类及 verifier；本章的优化算法与 pass 接口属于后续设计。教程中的“变换之后”是推导结果，不代表当前项目已具备所示优化流程。

\section{可观察行为规定优化的边界}
\begin{lstlisting}[language=Rustless,caption={没有使用的结果与必须发生的输入行为}]
fn main() {
    let x = getInt();
    let y = x * 0;
    printInt(7);
}
\end{lstlisting}
y 从未被使用，所以乘法可能删除；getInt 则会读取输入，删除它会改变程序消费输入的行为。即使本例最后仍打印 7，外部交互已不同。对于函数，返回结果、内存中仍能被观察的变化、输入输出，以及语言规定的失败行为，共同形成优化必须保持的对象。

等价不要求两份程序执行相同数量的步骤，也不要求临时地址相同。它要求在语言允许的输入和环境下，规定的可观察行为保持一致。这个定义应当由语言语义及运行时契约建立，不能由优化器为了方便而临时缩小。

\section{源运算与 IR 运算的语义必须衔接}
\begin{lstlisting}[language=Rustless,caption={边界值需要由语言规则解释}]
fn main() {
    let shifted = 1u32 << 32;
    let quotient = 20i32 / getInt();
    printInt(shifted as i32);
    printInt(quotient);
}
\end{lstlisting}
第十七章已经解释当前移位描述中的低五位掩码。计数 32 必须先转换为 0，再发出适当移位；优化器若直接把未掩码的 LLVM shift 当成源运算，就会使用错误的前提。类似地，除数为零、有符号最小值除以负一、整数溢出等情况，都需要逐项确定语言边界行为。

LLVM 的 poison 是一种特殊值传播规则，与立即未定义行为不同。给整数运算添加无溢出标志，或者把某个分支上的潜在错误提前执行，可能引入原程序没有的限制。\href{https://llvm.org/docs/UndefinedBehavior.html}{LLVM 的未定义行为说明}明确区分这些情况；在本项目中，应先以语言要求为准，再选择能准确表达它的 IR 操作和必要检查。

不要用宿主 C++ 的带符号溢出或移位表达式直接计算常量折叠结果。教学实现可以使用明确位宽的无符号位模式、单独处理有符号比较和除法边界，并检查所有目标类型的范围。常量折叠是运行运算规则的另一个实现，必须与正常执行具有同样的结果及失败条件。

\section{先选择能够说明清楚的优化}
\begin{lstlisting}[language=Rustless,caption={常量折叠、分支简化与无用值删除可以相互配合}]
fn main() {
    let x = 1 + 2;
    let unused = x + 10;
    if x == 3 { printInt(x); }
    else { printInt(0); }
}
\end{lstlisting}
常量折叠把 1+2 替换为 3；使用替换使比较也成为常量；分支简化只保留确定会进入的路径；不可达块删除移除另一分支；无用值删除移除 unused 的计算。各步骤的依据不同，适合分别实现为小变换，再按需要重复执行至没有变化。

无用值删除需要定义与使用关系。若一个指令定义的结果没有使用，而且该操作可以安全删除，才可删除它。删除后，其输入也可能变得无用，因此可以使用工作表传播，而不必每次扫描整份模块。

冗余复制消除同样需要精确条件。对纯标量的相同值转交可能只需替换使用；对聚合的字节复制则需要证明目标没有被观察、源和目标的别名关系允许改写、复制不含资源语义。把两种情况放在同一个“move”字符串之下，会让证明条件变得含混。

选择少量优化有助于学习，因为每一项都有可手算的前后表示和反例。先处理常量与清楚的控制流，再讨论内存变换，可以让复杂性逐步来自真实需求。

\section{内存效果、别名与可能失败的操作}
当前 \texttt{src/llvm/ir.cpp} 的基本效果分类如下。
\begin{lstlisting}[language=C++,caption={当前效果查询适合保守的基本分类}]
bool has_side_effects(const Instruction &instruction) {
  auto op = opcode(instruction);
  return op == Op::Store || op == Op::Call || is_terminator(op);
}
\end{lstlisting}
这段代码说明 store、调用和控制转移不能被当作普通无用算术删除，但它不是任意代码移动的完整依据。load 会读内存，不能跨越可能改写同一位置的 store；除法可能遇到错误条件；一个未被执行分支上的内存访问也不能无条件提到分支之前。

别名分析回答两个地址是否可能指向重叠存储。没有证明不重叠时，优化器应保持可能相关的读写顺序。Place 投影及已知对象身份可以为这种分析提供信息，但当前扁平 Ptr IR 不会自动保留全部来源关系。如果内存优化成为主要目标，就需要选择保留来源、建立分析或使用既有框架中的哪一条路线。

效果至少可以从读内存、写内存、输入输出、可能失败以及是否可投机执行几个方面描述。后者表示操作能否在原本不执行的路径上提前执行；它不能仅从“没有写内存”推出。更准确的效果模型使删除、移动和公共子表达式消除分别使用正确条件，也让未来运行时声明具备可供优化使用的意义。

\section{分析信息与变换分别负责什么}
def/use 回答值在哪里定义、在哪里使用；CFG 回答块之间的后继关系；支配关系回答某个定义是否必然先于使用；活跃性则回答值是否还会在某条未来路径被需要。这些信息可以被多个变换共享，没有必要让每个变换重新隐式计算一套。

\texttt{ir\_visit.hpp} 的 \texttt{for\_each\_operand} 与后继枚举已经把基础关系集中起来。分析器应通过这些接口读取图，而不是在各个算法中分别维护指令类别列表。新增指令时，关系枚举的穷尽性检查帮助发现遗漏；算法还需为新的内存或控制语义补充相应规则。

教学上的小型 pass 可以返回“是否改写了指令、是否改写了控制流”的结果。调度者据此保守地重算分析；以后确实观察到重算代价较高，再引入更细粒度的保留说明和增量更新。过早宣称某分析仍有效，会导致难以定位的旧信息使用错误。

\section{从栈槽提升到 SSA}
\begin{lstlisting}[language=Rustless,caption={一个可由值版本替代存储的局部变量}]
fn choose(flag: bool) -> i32 {
    let mut value = 0;
    if flag { value = 10; } else { value = 20; }
    value
}
\end{lstlisting}
清楚的初始转换可以为 value 分配一个局部栈槽，让赋值成为 store，最后的读取成为 load。若地址没有逃逸，且所有使用都能由分析理解，就可以把该槽的读写提升为 SSA 值：两个分支分别产生 10 和 20，合流处产生 Phi，返回 Phi 结果。

下图将分支中的存储操作转换为值版本与 Phi，呈现提升如何利用合流关系。

借用会改变适用条件。如果把 \texttt{\&mut value} 传给一个可能写入的调用，地址与存储已形成语言关系，不能随意删除槽。即使地址没有逃逸，复杂索引或部分聚合写入也需要比标量槽更强的分析。

直接构造 SSA 可以避免初始 load/store，但需要在每次分支、循环及未完成前驱处维护值版本，算法复杂度更早进入 lowering。先生成简单存储，再借助 \href{https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/LangImpl07.html}{LLVM 关于可变局部变量的教程}所示提升路线，是一种经典选择。两条路线都可以优雅，关键在于构造算法和不变量是否匹配学习目标。

\section{变换还必须保持表示不变量}
分支简化若删除一条到达 join 的边，就必须同步删除每个 Phi 中对应的 incoming。对多重边，还需要按边的重数处理，不能只按唯一前驱集合删除一次。块合并、拆边和重定向同样影响 Phi 的前驱身份。

删除值定义之前需要替换或删除所有使用；新使用需要满足类型和支配条件。当前 verifier 能发现许多这类错误，因此优化前后都进行验证，有助于把问题定位到引入错误的变换。验证通过只能说明结构合法，不能证明行为等价；独立输入输出对照或解释执行仍然需要。

对短路表达式的变换尤其有教育意义：把 RHS 从条件块移入入口块，可能仍有合法类型和 SSA，却使原本不会发生的 printInt 执行。结构验证与语义预期各自检查不同承诺，不能让其中一项替代另一项。

\section{根据学习目标决定优化范围}
若主要目标是理解数据流，可以实现常量传播、基本无用值删除和栈槽提升，逐项推导并保留反例。若主要目标是学习语言前端，就可以优先产生正确 LLVM IR，把更广泛的目标优化交给 LLVM。使用成熟框架仍要求输入 IR 精确表达源语义；框架无法猜出遗漏的移位掩码或 Box 内容规则。

一个优化器的价值可以从正确性条件、可观察改进和维护成本共同评价。算法数量、框架层数和遍历抽象数量并不直接说明设计更好。当前 IR 的明确指令形状、统一关系枚举和验证边界，为小规模优化提供了合适起点；更复杂的分析应随真实需求增长。

下一章把这种仍可拥有任意多个值的表示，放到有限寄存器和具体机器指令之中。

\chapter{机器表示、Phi 消除与寄存器分配}
\label{chap:machine}
\section*{本章导读}
IR 中的每个结果都可以获得一个独立 ValueId，机器却只有有限寄存器；一条抽象操作也可能需要多条具体指令。本章由这些差异推导机器表示，然后解释 Phi 如何变为边上的复制，值又如何获得物理位置。重点在于各项约束如何逐步进入设计，而不是记忆某个寄存器分配算法的名称。

Rustless 当前尚无本章描述的直接机器后端。真实 C++ 摘录来自 Rx-Compiler 参考项目，并明确标注；建议接口用于展示怎样延续当前有类型表示的原则。理解这些算法以后，才能在新表示上逐项实现并验证它们。

\section{从抽象操作到具体机器操作}
\begin{lstlisting}[language=Rustless,caption={立即数大小影响机器实现路径}]
fn small(x: i32) -> i32 { x + 7 }
fn large(x: i32) -> i32 { x + 100000 }
fn main() { printInt(large(small(getInt()))); }
\end{lstlisting}
两个加法在当前 IR 中都可以表示为一个 Binary，但目标指令允许的操作数不同。RV32I 的 addi 使用带符号十二位立即数；7 可以直接放入指令，100000 则需要先形成寄存器中的常量，再执行寄存器加法。具体编码条件可查阅 \href{https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html}{RISC-V 的 RV32I 规范}。因此 IR 指令数量不能直接当作机器指令数量。

下图比较小立即数与大立即数的两条实现路径，呈现目标操作数限制如何改变指令选择。

\node[irbox,below=of small] (large) {IR：x + 100000};

同样，大栈偏移可能超出 load/store 的立即数字段，需要额外计算地址；有些比较可以用一条机器比较形成结果，有些需要组合比较和取反。RV32IM 表示还选择了乘除扩展，若改为 RV32I，则乘除要走另一条实现路线。目标扩展集合必须与输出工具链和执行环境一致。

机器中所有整数寄存器具有相同位宽，bool 仍要保持语言的零或一表示。比较结果通常天然符合这一条件；外部返回值或内存读取得到怎样的位模式，则需要在明确契约下规范化。把一个任意整数截取最低位与判断是否非零是两种不同操作，不能因二者都“得到 bool”就相互替换。

\section{机器操作数也需要具体类型}
虚拟寄存器是编译器尚未分配位置的值，物理寄存器是目标硬件中的位置；立即数是指令编码的一部分，栈槽是将来获得字节偏移的存储对象。函数符号和块标签又承担不同重定位与跳转角色。这些概念应在类型中区分。

\begin{lstlisting}[language=C++,caption={教学建议：机器操作数避免混用多种编号}]
// Proposed machine representation, not existing Rustless code.
struct VirtualRegister { std::uint32_t value; };
struct StackSlotId { std::uint32_t value; };
struct MachineBlockId { std::uint32_t value; };
struct Immediate { std::int32_t value; };
enum class PhysicalRegister { Zero, Ra, Sp, A0, A1, S0, S1, T0, T1 };
struct SymbolOperand { std::string name; };
using MachineOperand = std::variant<VirtualRegister, PhysicalRegister,
                                    Immediate, StackSlotId,
                                    MachineBlockId, SymbolOperand>;
\end{lstlisting}
完整实现还需要列全寄存器、描述寄存器类及每条指令允许的操作数。上述枚举只是说明分类方法。位置编号不能被当成立即数，ValueId 不能被当作物理寄存器号，属于类型层应尽早排除的错误。

Rx-Compiler 的 \texttt{src/backend/machine.hpp} 使用以下真实结构保存选择之后的附加信息。
\begin{lstlisting}[language=C++,caption={参考机器表示集中记录复制、使用和定义}]
struct MachineInstruction {
  ir::Instruction instruction;
  std::vector<Copy> copies;
  std::set<ir::ValueId> uses;
  std::set<ir::ValueId> definitions;
  // a0-a7, t0-t6 and ra are reserved; calls never destroy an allocated
  // register.
  bool call_clobbers{};
};
\end{lstlisting}
它适合阅读边复制和活跃性算法，但仍把原 IR 指令放在机器记录中。Rustless 若建立直接后端，可以让指令选择真正产生有目标约束的载荷，并由统一接口枚举使用、定义和调用破坏。这样不会要求汇编打印器临时承担全部选择规则。

选择之后未必仍保持原 IR 的 SSA。例如 Phi 消除给同一目标位置在不同边上赋值，已经引入机器层的多处定义。此时应明确新阶段的不变量，不能继续假定原来的“一个 ValueId 只定义一次”规则未经变化。

\section{Phi 成为到达边上的复制}
回到 choose：合流块的结果从 then 取得 10，从 else 取得 20。机器没有必须在块开头执行的 Phi 指令，可以在 then 到 join 的边上把 10 写入结果位置，在 else 到 join 的边上写入 20。Phi 的输入是边使用，第十五章的这项定义正好指导转换。

如果前驱只有这一个后继，复制可以放在其终结指令之前；如果后继只有这一个前驱，也可能放在后继开头。若前驱有多个后继且后继有多个前驱，这条边称为关键边。放在前驱会使复制在其他离开路径上也执行，放在后继会使复制在其他到达路径上也执行。拆出一个专用边块能准确限定执行条件。

当前 Rustless 允许到同一后继的多重边，Phi 验证按边重数检查，并要求同一前驱的重复输入一致。新机器层若把边映射为一个 pair，需要考虑是否合并了重复边、跳转目标怎样重写及复制怎样保留。显式边身份或者保留重复后继记录，都应与转换约定一致。参考项目的旧算法不能在未核对这些条件时直接搬入。

\section{并行复制不能依次覆盖旧值}
一个合流块可能有多个 Phi，它们在一条到达边上的赋值是同时选择各自的旧输入。假设分配后的两个位置需要交换：位置 r1 的新值来自旧 r2，位置 r2 的新值来自旧 r1。这不是 Rustless 新增的并行赋值语法，而是多个 Phi 共同推导出的机器复制要求。

若直接先执行 r1:=r2，再执行 r2:=r1，旧 r1 已经丢失。应先保存旧 r1 到临时位置，再写 r1，最后把保存值写入 r2。独立复制可按依赖安全地排序；出现循环时则需要打破循环。

复制合并让两个可兼容值获得同一物理位置，可以省去部分 move，但不能让彼此干涉的值共享位置。分配前保留“偏好的相同位置”与分配后消除已满足的复制，是两种可组合策略。为了便于推理，教学实现可以先保留并行复制集合，完成位置分配后再把它调度成顺序指令。

\section{活跃性通过控制流达到固定点}
\begin{lstlisting}[language=Rustless,caption={回边使未来使用不能按单次源码扫描判断}]
fn sum(limit: i32) -> i32 {
    let mut i = 0;
    let mut total = 0;
    while i < limit {
        total += i;
        i += 1;
    }
    total
}
\end{lstlisting}
一个值若从某位置出发存在一条路径会在被重新定义之前使用它，就在该位置活跃。对每个块，use 包含块中先于定义的使用，def 包含块内定义。块出口的活跃值来自所有后继入口；入口活跃值则包括本块 use，以及出口中没有被本块定义覆盖的部分。
\[
\begin{array}{l}
\mathrm{out}(B)=\displaystyle\bigcup_{S\in\mathrm{succ}(B)}\mathrm{in}(S),\\[3pt]
\mathrm{in}(B)=\mathrm{use}(B)\cup
                 \bigl(\mathrm{out}(B)\setminus\mathrm{def}(B)\bigr).
\end{array}
\]
循环的 body 把新的 i 和 total 传回 header，header 又决定是否进入下一轮。第一次计算后继集合时，回边另一端的结论可能尚未完整，因此需要重复更新直到没有集合变化。有限值集合上从空集开始单调增加，能够得到固定点；反向遍历常有利于更快传播，但遍历一次并不足以构成证明。

下列真实片段来自参考 \texttt{machine.cpp} 的 \texttt{liveness}，对应上述两个方程。
\begin{lstlisting}[language=C++,caption={参考实现以集合变化驱动活跃性迭代}]
std::set<ir::ValueId> out;
for (auto successor : block.successors) {
  const auto &next = function.blocks.at(indices.at(successor)).live_in;
  out.insert(next.begin(), next.end());
}
auto in = difference(out, definitions[index]);
in.insert(uses[index].begin(), uses[index].end());
changed |= in != block.live_in || out != block.live_out;
block.live_in = std::move(in);
block.live_out = std::move(out);
\end{lstlisting}

该参考算法先把 Phi 输入放入显式边块，因而能直接使用普通方程。若在带 Phi 的 SSA 上分析，必须把 incoming 的使用放在对应边上；把所有输入算成 join 的普通使用，会制造并不存在的同时活跃关系。算法正确性始终依赖所分析表示的含义。

\section{从活跃关系到寄存器约束}
\begin{lstlisting}[language=Rustless,caption={两个输入必须在最终加法之前同时保留}]
fn combine(a: i32, b: i32) -> i32 {
    let x = a + 1;
    let y = b + 2;
    x + y
}
\end{lstlisting}
x 形成以后，在 y 的计算及最后加法之前仍被需要；y 形成以后也要保留。若在 y 的结果写入时覆盖 x，最终结果就错误。因此 x 与 y 的活跃范围重叠，构成干涉，不能共享同一个位置。

\section{spill 改变存放位置，不改变值}
当同时活跃的值多于可用寄存器时，某些值必须暂存在栈槽。spill 不是丢弃值，而是在定义后保存，使用前读取，并给这些额外机器步骤分配所需临时位置。

若一个值在循环体中频繁使用，spill 会在每轮增加访问；另一个很少使用的值即使活跃范围很长，也可能更适合放到栈上。使用频率、循环深度、复制收益和读取代价可以参与启发式。代价模型只决定优先选择谁，不能放宽保留值的正确性条件。

插入 spill 指令还会产生新临时值和新干涉。有些简单后端预留少数临时寄存器，统一用于读取、计算和写回；更一般的分配器会重新处理新值及分裂后的区间。预留策略降低算法负担，但减少可长期保存值的寄存器数量。这个运行代价应当被清楚说明。

\section{调用给寄存器分配带来额外约束}
\begin{lstlisting}[language=Rustless,caption={局部值需要跨越输出调用继续存在}]
fn preserve() -> i32 {
    let x = getInt();
    printInt(7);
    x + 1
}
\end{lstlisting}
x 在 printInt 之前形成，之后仍会使用。若将 x 放在调用允许破坏的寄存器里，又没有保存与恢复，调用后读取到的就不是原值。机器层需描述调用破坏哪些物理位置，参数必须进入哪些位置，以及返回值从哪些位置形成。

参考后端采取较容易说明的策略：长期分配只使用需要被调用者保存的 s 类寄存器，将参数、返回值及临时寄存器留给边界和局部计算。该策略简化跨调用约束，却可能产生保存寄存器的栈空间和序言尾声开销。更充分的分配器可以让不跨调用的短期值使用更多寄存器，在调用处施加精确限制。

预分配参数寄存器也不能破坏并行传参。例如两个已有参数的物理位置互换时，准备新调用参数与 Phi 的并行复制会遇到同类循环问题。将调用边界的复制交给一致调度机制，有助于避免分散实现交换特例。

\section{机器验证应先于汇编打印}
机器 verifier 可以检查每条指令的操作数形状、立即数范围、可用寄存器、块目标、栈槽边界、干涉关系和调用约束。它检查的表示已经区别于 SSA IR，因此需要独立说明允许哪些定义和复制形态。

若汇编打印器同时决定寄存器、补 spill、拆边并选择大立即数路径，测试很难判断是哪一步破坏了关系。较清楚的路线让每次转换产生可观察的机器表示，再让输出只负责指令语法、符号和编码工具所需形式。小规模项目可以合并某些实现函数，但不应因此混淆概念上的职责。

\href{https://llvm.org/docs/CodeGenerator.html}{LLVM 的代码生成器文档}也按机器表示、指令选择和寄存器相关阶段解释后端。这些阶段的共同依据是逐步满足目标约束。下一章把寄存器和对象位置组织成函数栈帧，并解释它们怎样与调用者合作。

\chapter{栈帧、平台 ABI、运行时与输出路线}
\label{chap:backend-routes}
\section*{本章导读}
给值分配了位置，还没有完成一个可调用函数：它必须让调用者知道参数在哪里、结果在哪里，并在退出时恢复应该保留的状态。本章把这些要求组织为栈帧和平台 ABI，再说明运行时、链接及两种输出路线。读者将理解从“合法 IR”走到“可执行程序”之间还有哪些明确的约定。

当前 Rustless 已实现 RV32 目标布局、内部函数分类以及验证后的 LLVM 风格文本输出。本章完整机器生成、运行时连接及可执行程序路线是设计方向。参考源码来自 Rx-Compiler，不代表这些模块已经存在于 Rustless。

\section{栈帧容纳不同来源的存储需求}

\section{RISC-V 整数调用约定}
针对标准 RV32 整数 ABI，a0 至 a7 用于参数，前两个也用于返回值；本教程的单字标量结果使用 a0。s0 至 s11 要跨调用保留，参数和 t 类临时寄存器不承担这种保留义务。ra 保存返回地址，sp 表示栈位置；gp、tp 不作为普通可分配寄存器。标准栈对齐为十六字节，进入函数时的首个栈参数位于入口 sp 的零偏移。规则依据 \href{https://riscv-non-isa.github.io/riscv-elf-psabi-doc/}{RISC-V ABI 规范的整数约定}。

\begin{lstlisting}[language=Rustless,caption={九个单字参数需要使用寄存器之外的位置}]
fn ninth(a: i32, b: i32, c: i32, d: i32,
         e: i32, f: i32, g: i32, h: i32, i: i32) -> i32 {
    a + i
}
fn main() { printInt(ninth(1, 2, 3, 4, 5, 6, 7, 8, 9)); }
\end{lstlisting}
本例前八个参数进入 a0 至 a7，第九个由调用者放在栈参数位置。若被调用者分配了大小 F 的帧，原入口 sp 等于当前 sp 加 F，因此它读取第九参数的偏移要包含 F。把该参数直接从当前 sp 的零偏移读取，会读到被调用者自己的帧内容。

这些规则约束所有相互合作的函数。caller-saved 表示调用者若需要跨调用保留某值，就应采取措施；callee-saved 表示被调用者使用这些位置时，要在退出前恢复入口内容。名字只是描述责任的简写，算法仍需基于活跃关系和实际使用决定何时保存。

\section{序言与尾声是一对状态转换}
序言向低地址调整 sp，保存将使用的被调用者保存寄存器，并在必要时保存 ra。若函数内发出普通调用，新的返回地址会覆盖 ra，所以当前函数必须保留自己的返回路径。叶函数若不进行调用，可能避免这项保存；是否仍需要帧则取决于局部对象和 spill。

尾声需要恢复保存寄存器和 ra，然后把 sp 调回入口值，再返回。所有正常 return 应遵循同一恢复规则，可以跳到共享退出块。源程序里有多个 return，不应导致部分路径漏掉恢复。

以下真实片段来自参考 \texttt{src/backend/riscv.cpp} 的输出函数；它把相同布局记录用于保存与恢复。
\begin{lstlisting}[language=C++,caption={参考序言与尾声使用同一帧记录}]
if (function_->has_calls)
  memory("sw", "ra", "sp", function_->return_address_offset);
for (const auto &[reg, offset] : function_->saved_registers)
  memory("sw", saved(reg), "sp", offset);
// Function body and shared return label are omitted here.
for (const auto &[reg, offset] : function_->saved_registers)
  memory("lw", saved(reg), "sp", offset);
if (function_->has_calls)
  memory("lw", "ra", "sp", function_->return_address_offset);
\end{lstlisting}
其中删节注释是为讲解添加，保存和恢复语句保持参考源码原样。实际输出还要在前后调整 sp；偏移过大时需要合法的地址形成路径。序言不能偷偷使用一个仍保存调用者有用值的临时寄存器，又没有遵守约定。

\section{内部聚合约定与平台适配}
\begin{lstlisting}[language=Rustless,caption={方法的聚合结果与标量参数需要共同分类}]
#[derive(Clone, Copy, PartialEq, Eq)]
struct Packet { ready: bool, count: i32, bits: [bool; 3] }
impl Packet {
    fn with_count(&self, count: i32) -> Packet {
        Packet { ready: self.ready, count: count, bits: self.bits }
    }
}
fn main() {
    let p = Packet { ready: true, count: 1, bits: [true; 3] };
    let q = p.with_count(7);
    printInt(q.count);
}
\end{lstlisting}
第十六章内部 ABI 为所有按值聚合使用地址，并将聚合结果改为隐藏输出地址。按该内部参数顺序，本例的实际调用可以先传结果缓冲区，再传共享 receiver 地址和 count。机器层再给这些已经分类的参数安排寄存器或栈位置。

这份约定使项目内所有函数遵循简单一致规则，却不宣称实现了平台对任意 C 聚合的分类。外部函数可能按平台规则把小聚合拆到寄存器中，或使用其他参数安排。连接外部库时需要单独的适配器，把内部值和外部表示相互转换；不能让内部结构体名字相同就自动认为二进制接口相容。

为避免混淆，可把接口分类拆为两步：源函数类型到 InternalFunctionAbi，外部声明类型到 PlatformFunctionAbi；它们再各自得到机器参数位置。这样增加新目标时，不需要把内部按值语义全部改写，也不会把源引用与“聚合副本地址”混在一起。

\section{运行时应是明确声明的接口}
输入输出、分配、容器扩容、元素移动、复制与失败处理，都可能通过运行时实现。每个调用必须有与生成代码一致的参数类型、结果类型、符号和约定。一个已有 BuiltinId 只回答操作身份，不能单独保证链接时存在对应函数。

Box 分配需要大小和对齐；Vec 扩容需要字节数溢出检查以及元素迁移规则；remove 需要索引边界和重叠移动处理。若选择通用运行时函数，复杂元素的克隆或释放可以通过类型专用辅助函数连接。若选择为每种类型生成操作函数，也要复用一致分配和失败契约。

当前完整生命周期执行尚未建立，未来加入释放时应说明谁拥有对象、何时转移所有权、离开作用域时哪些已初始化元素需要处理。简单地在每个块末尾插入 free，会在 return、break、部分初始化失败和移动之后产生错误。资源清理往往需要和控制流共同设计。

\section{程序入口、目标文件与链接}
源语言 main 是一个语言函数，启动入口则由执行环境决定。操作系统、裸机和模拟器可能采用不同启动代码和退出机制。启动过程负责建立所需状态，调用语言入口，并把结果交给环境。当前示例中的 main 不足以说明一份裸 RV32 程序如何启动。

汇编器把指令与数据写入目标文件，并为尚未确定的符号地址保留重定位信息；链接器把生成函数、运行时和启动代码组合，解析符号并安排地址。符号名称、可见性和目标文件格式因此也是后端的外部边界。非法字符需要合法转义或名字编码，不能把任意源名字直接拼进汇编。

目标三元组描述目标体系结构及环境，数据布局描述机器表示约束；它们不代替链接脚本、运行时和入口选择。一个指令集相容的文件仍可能因 ABI、库或入口不匹配而不能执行。教学实验应把这些配置固定下来，再研究生成代码自身的行为。

\section{LLVM 输出路线}
当前 \texttt{ir\_print.cpp} 在验证模块后输出 LLVM 风格文本，使用 TargetLayout 提供的 triple 和 datalayout，并处理符号拼写。这已经为 LLVM 路线建立了表示输出边界，但它还缺少完整源函数 lowering 和运行时连接。

完整路线应先产生合法且准确表达语言规则的 IR，再使用匹配版本的 LLVM 工具验证、优化和生成目标代码。运行时声明与定义需要一致，目标扩展与 ABI 也需明确。LLVM 可以完成机器指令选择、寄存器分配和许多优化，并不承担重建前端漏掉的求值顺序、聚合复制或结构比较规则。

这条路线有利于集中学习语法、类型、语义事实和 lowering。运行效率的改进可以从较准确的 IR 以及既有优化流程获得；教学代价是部分机器算法被成熟框架封装。读者仍应理解边界，才能解释为何某份 IR 合法却没有实现预期语言。

\section{直接 RV32 输出路线}
直接路线在当前 IR 之后建立机器表示，完成指令选择、Phi 边复制、活跃性、寄存器分配、spill、帧布局和汇编输出。每项算法都需要自己的检查条件与可观察例子。若以后扩展目标，不同寄存器类、指令约束和调用规则会进入这层，而不是散落到源语义检查中。

这条路线适合研究后端算法及其运行代价。小型实现可以先采用保守寄存器策略、统一边块和简单帧布局，以清楚不变量为先，再用测量结果改进代码大小和访存次数。保守并不等于省略边界：大立即数、大帧、超过寄存器数量的参数和复制循环，都需要正确实现。

\section{按学习目标作出选择}
如果首先希望研究前端设计和语言语义，LLVM 路线能让学习精力较快集中于已检查 AST 到正确 IR 的转换。如果希望亲自推导活跃性、分配与 ABI，直接 RV32 路线能提供更完整的机器学习过程。两条路线可以共用前端及转换契约，逐步建设，不必为了增加后端而复制语义规则。

比较两条路线时，应该固定同一份源程序、同一输入和预期行为。不同输出的指令数量可以不同，但内容相等、短路调用、移位计数和聚合按值参数不能不同。若双方行为不一致，先回到语言契约和阶段边界寻找原因，再判断优化和机器实现。

至此，教程已经从源码、类型与访问走到计算图和机器约束。最后一章把这些设计转化为可检验的承诺，并讨论新增能力需要怎样的信息。

\chapter{检验设计承诺，并有依据地扩展}
\label{chap:design-evidence}
\section*{本章导读}
清楚的设计应当能够解释正常程序，也能够指出不合法的结构，并为新增能力提供准确位置。本章将全书的关系转成可以观察的承诺，再用一个小扩展追踪修改范围。读者将学会区分“输入被接受”“表示正确”和“执行行为符合语言”这几种证据，同时依据实际需要讨论维护与性能。

测试在这里是理解设计的方法。我们不以测试数量说明优雅，也不把实现自己的计算结果重新抄入预期。每个例子都应当来自要检验的语言规则或表示不变量。

\section{每个阶段承诺什么}
词法分析承诺正确识别词法单元及非法输入；语法分析承诺按入口规则判断接受；AST 构造承诺节点形状、子节点关系、身份及范围；语义分析承诺名字、类型、转换及上下文规则；IR 构造承诺具体指令和图的不变量；完整执行还要承诺源程序规定的行为。后一个承诺不能仅由前一个阶段成功推出。

下图将各层承诺连接到能够检验它的观察，呈现一种测试为什么不能替代全部其他证据。

例如 1+2*3 被 parser 接受，尚未说明乘法是加法的右子节点；树的形状正确，尚未说明类型推导正确；IR 的类型和支配正确，也尚未说明输入输出顺序正确。分别观察这些关系，能使失败定位更直接，也能发现层次之间漏掉的契约。

\section{parser 测试与 AST 结构测试}
\begin{lstlisting}[language=Rustless,caption={同一次语法接受还需要核对正确的树结构}]
fn calculate(a: i32, b: i32, c: i32) -> i32 { a + b * c }
\end{lstlisting}
对此输入，结构预期是函数体的 tail 为 BinaryExpr(Add)，left 指向 a，right 为 BinaryExpr(Mul)，其两个子节点分别指向 b 和 c。还应核对各次出现有不同身份，以及范围能切出对应源文本。只核对 dump 中出现了加法和乘法，会遗漏两者的父子关系。

dump 便于人观察，但直接载荷断言更适合检验精确关系。当前 \texttt{tests/frontend\_ast\_structure.cpp} 对导入组、别名、类型和表达式形状作独立断言；其中如下片段直接根据示例检查组内数量及别名类别。
\begin{lstlisting}[language=C++,caption={当前结构测试根据输入建立独立预期}]
const auto &use = std::get<ast::Use>(crate.items[0]);
assert(use.tree.prefix.root == ast::PathRoot::Absolute);
const auto &group = std::get<ast::GroupImport>(use.tree.target);
assert(group.children.size() == 4);
const auto &rename = std::get<ast::NameImport>(group.children[0].target);
assert(std::get<ast::Identifier>(*rename.alias).text == "r");
\end{lstlisting}

范围检查需要具体预期。把打印器返回的范围再与同一打印器结果比较，不能证明坐标转换正确。可以在小输入中手工确定字节区间，包含注释、括号和 UTF-8 注释等有区分力的情形；语言不支持的 Unicode 标识符不应被偷换成范围测试的正例。

\section{Visitor 的编译期承诺与运行期关系}
Visitor 的覆盖约束检查是否能处理每个载荷、owner 是否合适、返回类型是否一致，以及只读入口是否拒绝可变载荷参数。当前 \texttt{tests/ast\_visitor.cpp} 有如下真实断言。
\begin{lstlisting}[language=C++,caption={当前访问接口对不合适处理者给出编译期否定}]
static_assert(!ast::ExhaustiveVisitor<OnlyBinary, ast::Expr>);
static_assert(!ast::ExhaustiveVisitor<DifferentReturns, ast::Expr>);
static_assert(!ast::ExhaustiveVisitor<MutablePayload, ast::Expr>);
static_assert(!ast::ExhaustiveVisitor<IdentityVisitor, int>);
static_assert(!ast::ExhaustiveVisitor<WrongOwner, ast::Expr>);
\end{lstlisting}
这些断言检验接口，不检查每个处理者的算法内容。一个覆盖全部载荷却把左右操作数打印反的 Visitor，仍会满足覆盖约束。因此还要检查进入及离开次序、直接子节点顺序、Skip 的范围、Stop 后的退出行为，以及每个 owner 与载荷确实属于同一次访问。

通用 catch-all 也会让新增节点继续通过覆盖检查。若处理过程需要为每个种类定义特殊语义，应使用具体重载，避免一个默认分支掩盖缺失规则；若过程只收集所有 owner 身份，通用分支则是合理选择。是否穷尽应与处理目的联系起来。

寿命约束也可以用构造能力检查。当前 SemanticIndex 拒绝 const 和非 const 的临时 Crate，SemanticBridge 同样拒绝两种临时 SemanticIndex。这能排除直接借用临时对象的常见错误；一般 C++ 引用仍不能自动证明借用期间对象永远存在，所以文档和拥有关系仍需明确。

\section{语义规则与事实完整性}
语义测试应给规则建立正例和有区分力的反例。例如相同整数类型相加是正例，整数与 bool 相加是反例；可写位置可赋值是正例，共享借用后的不可写位置是反例。变换一个条件，观察是否正好改变应当改变的判断，比重复多个形式相同的程序更有解释力。

\begin{lstlisting}[language=Rustless,caption={调用使用处的调整需要与表达式结果转换区分}]
fn read(value: &i32) -> i32 { *value }
fn main() {
    let mut x = 3;
    let mutable = &mut x;
    let alias = read;
    printInt(alias((mutable)));
}
\end{lstlisting}
此例的调用目标应指向 read 声明，参数使用需要从可变引用转为共享引用；加上的括号不应让目标身份或调整丢失。独立预期应核对 FunctionTarget、实际声明 SymbolId、参数的有效类型和调整顺序，而不只核对程序成功。

事实完整性也是设计承诺。所有可查询表达式、类型语法、字段和参数是否有对应记录，引用的声明是否存在，字段集合是否覆盖声明，这些可以通过 SemanticIndex 的验证检查。对象重载还核对原 AST 地址，拒绝另一棵树中碰巧具有相同 NodeId 的对象；按编号查询则要求调用者清楚编号所属的上下文。

这些验证让 lowering 能放心消费已确定关系，但不能替代语言规则测试。一个完整且内部相容的错误类型结果，仍可能通过结构验证。事实的覆盖、链接和含义需要分别检验。

\section{IR 与后端需要独立预期}
IR 测试可以手工构造不合法表示：重复值定义、错误类型的操作数、不存在的分支目标、终结指令之后的普通指令、不受定义支配的使用，以及 Phi 输入与边不一致。确认 verifier 拒绝它们，能够直接检验前章的不变量。

当前 \texttt{tests/ir\_alignment.cpp} 对多重边使用独立修改。下面片段把两条到达边的 Phi 少留一个输入，检查它不能覆盖两条边。
\begin{lstlisting}[language=C++,caption={当前 Phi 回归直接检验边重数规则}]
auto second = phi.incoming.back();
phi.incoming.pop_back();
assert(!ir::verify(module).empty()); // One incoming cannot cover two edges.
phi.incoming.push_back(second);
phi.incoming.back().value = ir::Operand::constant(ir::Type::I32, 8);
assert(
    !ir::verify(module).empty()); // Duplicate edges cannot select two values.
\end{lstlisting}

布局测试应使用手算结果，例如 Packet 的 count 偏移为四、总大小为十二；相同名字的不同结构体身份应得到各自布局。运算桥接应检查有符号与无符号谓词、移位描述中的 mask、Box 的 StructuralEquality，以及调用别名指向原函数 ABI。这些都是当前接口能够提供的证据。

完整 lowering 以后还要进行执行实验：计数三十二的移位、短路 RHS 输出、两个不同 Box 的相同内容、聚合参数副本、超过八个参数的调用和复制循环。独立解释器或参考实现可以作为行为对照，外部 LLVM verifier 则检查输出的结构。LLVM 接受一份文本不能证明内容相等或求值顺序符合源语言；描述中存在 mask 也不能证明可执行指令实际执行了掩码。

\section{怎样使用 rx-compiler-testcases}
外部测试集的 manifest 指定源文件、测试阶段和编译成功预期；执行类测试还记录输入输出文件。lex 检验词法，parser 检验指定入口的语法接受，semantic 检验语言规则，codegen 和 optimization 则需要实际执行及输出对照。读取每项的 stage，比根据目录名字猜测试意图更准确。

当前命令行支持 lex、parse、semantic 及相应观察选项。parser 测试可先用于检查语法接受，再对 crate 入口使用 AST dump 观察建树；非 crate 入口的解析不一定产生完整 Crate，因此不能要求同样的 dump。AST 结构正确性还应由上一节的载荷、顺序及范围检查补充。

codegen 的移位 manifest 包含不同输入条件与对应输出，适合在完整 lowering 后检验真实掩码行为。现在可以根据它建立转换计划的预期，却不能把仅通过 semantic 的结果计为 codegen 执行成功。optimization 测试也需要语言行为与目标指标的明确约定，不能仅比较优化前后字符串不同。

附录列出本地命令与路径，正文关注观察方法：先确定这项输入要检验什么，再选择相应阶段和独立预期，最后区分失败是语言拒绝、表示不合法还是行为不一致。

\section{贯穿扩展练习：布尔匹配表达式}
本节假设新增一种只允许匹配 bool、恰好包含 true 和 false 两个分支的表达式。它是教学练习，当前 Rustless 不支持以下 match 写法；本节不修改项目语法或代码，也不将这些输入当作当前正例。

\begin{lstlisting}[language=Rustless,caption={教学扩展的正确示例：当前尚不支持此语法}]
fn choose(flag: bool) -> i32 {
    match flag { true => 10, false => 20, }
}
\end{lstlisting}
首先，grammar 需要确定分支界定、逗号、表达式优先级和允许出现的上下文。其次，AST 需要一个具体载荷，保存 scrutinee 以及按源码顺序排列的两项分支。模式真假可以用精确 bool 字段表示；匹配整体、各分支范围和身份如何保存，应与已有 owner 原则一致。

\begin{lstlisting}[language=C++,caption={教学扩展的结构建议，当前没有这些定义}]
struct BooleanMatchArm : Node {
  bool pattern;
  ExprPtr body;
};
struct BooleanMatchExpr {
  ExprPtr scrutinee;
  std::array<BooleanMatchArm, 2> arms; // Source order.
};
\end{lstlisting}
这个建议把“恰好两项”放入结构，真假是否重复则仍由语义判断。直接保存 on\\_true 和 on\\_false 虽便于查找，却会丢掉两分支的源码顺序；若选择这种表示，就需要额外保存来源顺序，不能让后续遍历按猜测排列。

children 枚举先访问 scrutinee，再按源码顺序访问分支及各自 body；Visitor 为新载荷补充规则；语义检查要求 scrutinee 为 bool、模式不重复且完整覆盖、两个正常完成分支获得共同结果类型。Never 分支按既有结果规则处理。事实可以记录分支对应真假及共同结果，lowering 只读取一次 scrutinee，形成条件分支并在正常到达边上汇集结果。

}
\end{lstlisting}
\begin{lstlisting}[language=Rustless,caption={教学扩展的类型错误：分支结果不相容}]
fn bad(flag: bool) -> i32 {
    match flag { true => 10, false => false, }
}
\end{lstlisting}
\begin{lstlisting}[language=Rustless,caption={教学扩展的控制流上下文错误：break 没有循环目标}]
fn bad(flag: bool) -> i32 {
    match flag { true => { break 10; }, false => 20, }
}
\end{lstlisting}
另一个转换反例是在 join 中保留两个正常前驱，却只给结果 Phi 一项 incoming。这份图即使来源于正确匹配输入，也必须被 IR verifier 拒绝。它说明新增语法和转换图各自需要证据。

如果只新增一种分析，例如统计所有表达式深度，则节点形状、grammar 和原语义通常无需改变；新处理者可以使用现有 visit 与 children。新增节点影响多个过程，新增过程解释既有节点，这正是前文讨论的两种扩展方向。优雅表示让变化沿真实依赖发生，不许诺任何扩展都只改一个文件。

\section{较大扩展需要哪些新信息}
多文件模块需要拥有多个源文件的 SourceManager，以及在文件、模块和导入之间稳定的声明身份。当前 Crate 拥有一个 SourceFile，适合单个输入；若多个 Crate 产生相同 NodeId，跨文件查询还需上下文区分。单纯拼接源码会破坏来源与作用域关系。

通用类型泛型需要明确类型参数、替换规则及实例身份。已有生命周期参数与 Box、Vec 的具体类型参数支持，不等于任意用户类型泛型已经实现。单态化可为具体实参生成具体函数或布局，参数化执行则需另一套运行时表示；选择取决于语言目标。

流敏感借用需要在控制流中追踪位置、访问权限及借用存续范围。AST 上的局部可写条件能检查部分规则，却不能自动描述不同路径中的借用变化。一个保留 Place 及类型的 CFG 可以成为这类分析的输入，但首先要确定究竟实现哪些借用规则。

\section{性能改进需要可区分的测量}
节点对象大小与分配次数影响前端内存和缓存访问，类型重复影响存储与比较，查询热点影响分析时间，Visitor 模板实例化影响编译器自身的编译耗时。生成程序的指令数量、访存、调用和运行时间则属于另一组代价。测量时应先区分编译时间与被编译程序的运行时间。

arena 可以减少逐节点分配并集中寿命管理，但可能使删除和独立拥有变复杂；类型 interning 减少相同类型的重复构造，却需要稳定键、身份和缓存寿命；索引提高热点查询速度，同时维护覆盖及链接规则。当前不可变类型和名义身份已经为统一类型工厂提供基础，仍应根据实际重复和查询数据评价收益。

variant 的最大载荷决定 owner 内部联合空间，虚函数层次则有虚表指针、独立分配和间接调用等代价；实际布局与优化结果受编译器影响。仅因为访问函数模板可以内联，并不能断言总体性能必然更高。可以分别测量对象尺寸、分配数、访问耗时及实例化代价，再解释结果来自哪项表示选择。

优化器也需区分自身耗时与生成程序收益。一个昂贵分析若只省掉极少执行步骤，未必适合快速教学编译；一个循环内的 spill 改进则可能有明显运行价值。清楚的阶段表示让这些代价容易定位，证据再决定是否值得增加复杂度。

\section{重新评价全书的设计}
第一章从结构、决定归属、扩展与代价提出评价方向。现在可以把它们归纳成五个具体问题：表示明确保存了什么关系；对象由谁拥有且身份属于哪个上下文；语义决定在哪一阶段完成；新增节点或过程会沿哪些依赖变化；维护与运行代价如何得到证据。

当前 AST 的 owner 与具体载荷让形状和身份分开，非空拥有使必需子节点可依赖，显式 children 把结构关系集中；Visitor 将每次访问的 owner、载荷和返回约束表达出来。语义类型与语法类型分离，不可变结果和索引保留稳定查询，运算与调用事实让后续阶段消费决定。IR 的具体指令、值身份、边关系和 verifier 再把计算图的规则落为结构。

这些设计仍有明确边界：完整 lowering 要实现描述承诺，聚合与容器要连接运行时，优化要证明行为保持，机器后端要满足有限位置及 ABI。未来增加层次时，应能指出现有表示丢失了哪项必要信息；未来改善性能时，应能指出测量揭示了哪项具体成本。

全书所说的优雅，是让语法结构、语义决定、计算关系和机器约束分别得到准确表达，并通过明确接口连接。这样的设计既可以解释每一个合法例子，也可以说明反例为何失败；既让变化有可追踪范围，也让代价有可验证依据。读者据此能够评价当前实现，并提出理由清楚、边界明确的下一步设计。
