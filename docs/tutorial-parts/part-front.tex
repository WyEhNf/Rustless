\chapter{同一个程序，为什么需要不同表示}
\label{chap:front-representations}

\section*{导读}
阅读程序时，我们会同时关注它的写法、含义和执行过程。编译器也需要这些视角，但它不能像读者一样依靠经验补足缺失的信息：一个名字指向什么声明，一次运算使用什么类型，一条分支通往哪里，都必须有明确的表示。本章从一个简单的计算开始，说明编译器为什么逐步改变程序的表示，以及每次改变应当解决什么问题。后续章节中的 AST、Visitor 和语义类型，都可以放回这条主线来理解。

\section{从一个计算开始}
考虑下面的 Rustless 函数。Rustless 是本教程讨论的语言子集；它采用若干 Rust 风格的语法，但不具有完整 Rust 的所有语言能力。
\begin{lstlisting}[language=Rustless]
fn calculate(a: i32, b: i32, c: i32) -> i32 {
    a + b * c
}
\end{lstlisting}
源文本按字符从左到右排列。理解这个函数时，我们却不会把这种排列直接当作计算顺序：乘法属于加法的右操作数，整个表达式又是函数体的结果。文本顺序、结构上的包含关系和计算上的依赖关系，已经是三种不同的关系。

如果只保存字符串 \texttt{a + b * c}，每一个使用者都需要重新识别运算符、判断优先级并找到操作数。若编译器首先把乘法与加法的父子关系建立起来，打印器、类型检查器和代码生成器就可以共享这份解释。这是引入程序表示的第一个理由：\emph{已经确定的关系应当成为可以读取的数据，而不应反复隐藏在文本中等待重新解释。}

我们暂时将运算理解为一张依赖图。乘法的结果必须存在，加法才能使用它；参数的名字如何找到声明，则是另一项尚未展开的任务。这样分开观察，可以避免在介绍 AST 时过早讨论寄存器，也避免在讨论机器指令时重新处理括号。

\section{词法、语法与语义}
词法分析首先确定程序由哪些词法单元组成。在上例中，\texttt{fn} 是关键字，\texttt{calculate} 是标识符，\texttt{->} 是标点组合，\texttt{i32} 的拼写可以作为路径中的名字出现。词法单元带有类别和位置，因此下一阶段不必逐个字符重新辨认这些单元。

语法分析确定这些单元如何组成语言允许的结构。它能够判断参数列表是否闭合、函数体是否由大括号界定，以及乘法如何嵌入加法。然而，满足语法规则还没有说明名字是否存在，也没有说明两个操作数是否支持同一个运算。
\begin{lstlisting}[language=Rustless]
fn main() {
    let value = 1 + true;
}
\end{lstlisting}
这段代码包含合法的整数、布尔值和加法写法，能够形成一个二元表达式结构。它的问题出现在语义层面：加法需要适合该运算的操作数。类似地，\texttt{unknown + 1} 可以具有清楚的语法结构，但仍需要名字解析来判断 \texttt{unknown} 指向什么。

这里形成了三个逐步增加的判断：字符能否形成词法单元，单元能否形成语法结构，结构能否获得合法的语言含义。将它们分开，使诊断能够指出错误所属的层次，也使某一层的修改不必连带改变所有层。例如，增加一种整数进制主要影响字面量识别与解释；它不应迫使二元表达式改变左右子节点的结构。

真实前端的入口定义位于 \path{E:/RComplier/Rustless/include/rx/frontend.hpp}。下列摘录保留原有接口；阅读时关注返回结果，而不必立即了解 ANTLR 的类。
\begin{lstlisting}[language=C++]
struct FrontendResult {
  std::unique_ptr<const ast::Crate> crate;
  // False means the generated parser rejected the token stream.
  bool syntax_ok{};
};

FrontendResult parse_source(std::string_view source,
                            DiagnosticEngine &diagnostics);
\end{lstlisting}
\texttt{syntax\_ok} 说明解析是否成功；\texttt{crate} 是已建立的语法树。该结果没有把语法成功表述为整个程序已经通过类型检查。后续阶段仍有独立的任务和独立的输入要求。

\section{AST、语义事实、IR 与机器代码}
抽象语法树，即 AST，按语言概念组织程序。一个函数有签名和函数体，一个二元表达式有运算符和两个操作数，一个条件表达式有条件与分支。AST 的首要目的，是让这些语法关系成为明确的结构。

语义分析在这份结构上确定含义。例如，上例中三个参数的类型都是 \texttt{i32}；\texttt{a} 这一次出现与参数声明之间存在引用关系；乘法和加法得到相应的运算规则。语义事实可以与 AST 分开保存，因为同一棵树的结构没有因类型判断而改变。把事实按节点身份组织起来，也便于下一个阶段直接查询已知的结论。

中间表示，即 IR，进一步显式表达计算、数据流、控制流与内存操作。表达式树中隐含的依赖，在 IR 中通常体现为值被哪条指令定义、又被哪些指令使用。以下是解释依赖的教学记法，并非从当前 Rustless 完整 lowering 得到的输出：
\begin{lstlisting}
t1 = multiply(b, c)
t2 = add(a, t1)
return t2
\end{lstlisting}
一个语法节点不必对应恰好一条 IR 指令。结构体构造可能涉及存储分配与多个字段写入；短路逻辑可能形成多个基本块；方法调用还可能需要接收者转换。机器表示随后继续引入目标平台的寄存器、栈槽和调用约定。因此，要求所有阶段共享一套通用节点，往往会把不同阶段的关系混杂在一起。

\section{阶段之间需要传递什么}
当语义分析指出右操作数类型错误时，它需要找到相应的源文本；当 lowering 查询一个表达式时，它需要知道正在查询哪一次出现；当调用已经解析时，它需要知道目标是哪一个声明。这三种需求分别引出源码范围、节点身份和声明身份。

源码范围回答“这一结构来自哪里”。节点身份回答“这一条事实属于哪一次语法出现”。声明身份回答“这个名字或调用最终指向哪个声明”。同样的拼写可以出现在不同范围中，也可以因作用域不同而指向不同声明。若把三者都用一个字符串代替，后续阶段便会丢失必要的区分。

类型与转换也需要分开。一段表达式可以本来具有引用类型，却在某个操作数位置被隐式解引用。语义阶段应当记录该使用位置所需要的转换，后端按记录实施，而不必重新猜测语言规则。源码来源则可以继续伴随生成指令，以服务诊断与观察；来源身份与 IR 值身份仍是不同的概念。

这些信息不能只留在产生它们的局部函数中。清楚的阶段接口，应当使消费者得到完成任务所需的信息，并且能够说明哪些关系已经检查、哪些仍需要处理。后续的具体载荷和语义结果设计，都是这项原则的应用。

\section{用什么评价一种设计}
评价一种表示，可以从结构、决定的归属、扩展方向和代价四方面展开。结构方面，询问字段是否直接表达语言概念：\texttt{left} 与 \texttt{right} 是否比没有角色说明的数组更容易阅读。决定的归属方面，询问同一规则是否在多个阶段重复实现：后端是否还在按字符串猜测操作数类型。

扩展有不同方向。增加一种表达式，需要补充它的数据结构及相关处理规则；增加一种分析过程，则需要解释已有节点的新用途。这两种变化不应混为同一个“可扩展性”问题。第七章讨论 Visitor 时，将用节点与过程的矩阵具体说明这一区别。

运行代价同样需要具体观察。逐节点分配会产生分配和指针访问成本；较大的联合会增大某些节点的对象尺寸；模板可以提供静态检查，也可能增加实例化和编译时间。清楚的数据结构使这些成本更容易分析，但不能替代实际测量。教程中的“优雅”因此不是对一种技术的赞美，而是对关系是否明确、责任是否一致、变化是否可追踪的判断。

本章建立了表示之间的主线。接下来先处理所有表示都可能需要的基础信息：源文本如何保存，以及一个结构怎样准确地指回文本中的位置。

\chapter{源文本、词法单元与诊断位置}
\label{chap:front-source}

\section*{导读}
编译器不仅需要理解程序，还需要把理解结果解释给编写程序的人。错误位置、运算符位置以及保留的字面量拼写，都依赖可靠的源码表示。本章先讨论文本的寿命，再说明词法类别与非法输入，最后联系字符坐标、字节范围和生成代码。学习本章之后，读者应能够解释一个 AST 节点的范围来自哪里，以及为什么词法识别不能包办字面量的全部含义。

\section{SourceFile 与源码寿命}
一个源码切片只有在原文本仍然存在时才有意义。当前 \texttt{Crate} 拥有 \texttt{SourceFile}，而 \texttt{SourceFile} 拥有一个 \texttt{std::string}。AST 的范围因而可以在语法分析器对象销毁之后继续用于诊断与打印。

下面是 \path{E:/RComplier/Rustless/include/rx/ast/item.hpp} 的真实摘录：
\begin{lstlisting}[language=C++]
struct Crate : Node {
  explicit Crate(std::string source) : source(std::move(source)) {}
  SourceFile source;
  std::vector<Item> items;
};
\end{lstlisting}
这里的拥有关系比“AST 临时借用 parser 输入缓冲区”更容易说明。读者可以沿着 \texttt{Crate} 找到文本所有者；使用者只要维持整棵树的寿命，便可以读取其源码。\texttt{SourceFile::slice} 返回视图，而不是再次复制字节，因此每次诊断切片不需要建立新的字符串。

真实的切片函数位于 \path{E:/RComplier/Rustless/include/rx/ast/source.hpp}：
\begin{lstlisting}[language=C++]
std::string_view slice(Span span) const {
  if (span.begin > span.end || span.end > text.size())
    throw std::out_of_range("invalid source span");
  return std::string_view(text).substr(span.begin, span.end - span.begin);
}
\end{lstlisting}
范围检查使越界使用能够被发现。但视图仍然借用 \texttt{text}：销毁拥有它的 \texttt{Crate} 之后，保留这个视图是不安全的。返回视图的低复制成本与寿命约束，是同一个接口的两个方面。

当前设计还保存标识符和整数的独立拼写，构树器与最终 \texttt{Crate} 也会各自建立源码对象。因此，它并非整个过程零复制的设计。将来若处理许多文件，可以由 SourceManager 统一拥有文本，节点仅保存文件身份和范围，并在必要处采用字符串唯一化。这样的扩展首先要明确多文件身份和寿命，再讨论减少复制；单文件实现尚不能被直接描述为完整的多文件源码管理器。

\section{标识符、关键字与字面量}
观察下面的程序：
\begin{lstlisting}[language=Rustless]
fn main() {
    let mut value_1: i32 = 0x2a_i32;
    let binary = 0b1010u32;
    let octal = 0o12usize;
    let decimal = 10isize;
    let ready = true;
}
\end{lstlisting}
\texttt{value\_1} 是普通标识符。\texttt{fn}、\texttt{let} 与 \texttt{mut} 具有各自的词法类别，不应被混入普通名字。\texttt{true} 和 \texttt{false} 表示布尔字面量。整数的进制前缀、下划线分隔和后缀，则共同组成一个完整词法单元。

\path{E:/RComplier/Rustless/grammar/Lexer.g4} 中使用 ASCII 起始字符与后续字符规则；单独的 \texttt{\_} 有专门类别。由此可见，\texttt{\_} 与 \texttt{\_value} 的角色不同。生命周期名又有前置单引号，例如 \texttt{'a}。它不是字符字面量，也不是一个普通变量名字；AST 使用 \texttt{LifetimeName} 保留这一差别。

词法规则同时保留了一组暂未在子集中实现的保留关键字。例如 \texttt{match} 已被识别为保留词，却没有相应的匹配表达式 grammar。这能防止它被当成普通标识符使用，也提醒我们区分“能识别一种词”与“已经实现对应语法”。

整数识别只回答拼写是否合法。它尚未回答数值是否适合目标位宽、无后缀整数应当采用什么类型，或者一元负号怎样与整数范围共同解释。\texttt{-1} 也不是一个包含负号的整数 token：负号形成单目运算，整数载荷保存幅值的拼写。这样的划分让词法结构、语法结构和数值判断各有归属。

下面是 Lexer 中真实的整数规则摘录。它保留错误的长数字拼写，防止 \texttt{123abc} 被轻易拆成一个整数与一个标识符。
\begin{lstlisting}
INTEGER_LITERAL
    : (DECIMAL | BINARY | OCTAL | HEXADECIMAL) INTEGER_SUFFIX?
    ;
INVALID_NUMBER
    : [0-9] ASCII_CONTINUE*
    ;
fragment INTEGER_SUFFIX: 'i32' | 'u32' | 'isize' | 'usize';
\end{lstlisting}
这类规则的价值，在于错误输入仍然保有连续的范围与可解释的类别。后续诊断能够指出完整的非法数字，而不必根据偶然产生的多个 token 猜测用户原来的输入。

\section{空白、注释与非法词法单元}
空白和注释不改变这个程序的主要 AST 形状：
\begin{lstlisting}[language=Rustless]
fn main() {
    // A line comment.
    let value = 1 /* outer /* inner */ outer */ + 2;
}
\end{lstlisting}
当前 Lexer 将正常空白、单行注释和块注释放在隐藏通道中。token stream 仍能保存它们，parser 读取通常语法通道时则无需把每个空白加入产生式。AST 构造器从范围访问原文，因此即使语法结构不保存每条注释，原始文本也仍然保存在源码对象中。

嵌套块注释需要正确配对内部的开始与结束标记。当前规则通过递归的注释片段表达嵌套，且单独识别未闭合注释。它不能在遇到内部 \texttt{/*} 后，随意把这个开始标记退回成普通注释文本，否则错误的嵌套输入可能被误接受。

下列规则来自同一 Lexer 文件：
\begin{lstlisting}
WHITESPACE: SPACE_TEXT -> channel(HIDDEN);
LINE_COMMENT: LINE_COMMENT_TEXT -> channel(HIDDEN);
BLOCK_COMMENT: BLOCK_COMMENT_TEXT -> channel(HIDDEN);
UNTERMINATED_BLOCK_COMMENT: UNTERMINATED_COMMENT_TEXT;
ERROR_CHAR: .;
\end{lstlisting}
非法单元留在正常通道，正常注释进入隐藏通道。二者需要不同的安排：正常注释可以不参与语法判断，非法字符却不能静默消失。\texttt{lex\_source} 还会检查非法生命周期、非法字符字面量、非法数字、未闭合注释和未知字符类别，并产生诊断。

这并不意味着当前前端具有任意错误恢复能力。生成 parser 可以尝试恢复以继续报告错误，但 \texttt{parse\_source} 在存在诊断时停止发布 AST。消费者得到的树来自没有报告解析错误的路径，因此不必把 parser 的临时恢复节点当成可靠语法结构。

\section{FileId、Span 与半开区间}
范围采用半开区间 $[\mathrm{begin},\mathrm{end})$：包含起点，不包含终点。长度可以直接计算为终点减起点，相邻的两个范围也可以在同一终点和起点处连接。空范围自然表示为起点等于终点，而不必引入特殊负数。

实际定义位于 \path{E:/RComplier/Rustless/include/rx/diagnostic.hpp}：
\begin{lstlisting}[language=C++]
struct FileId {
  std::uint32_t value{};
  auto operator<=>(const FileId &) const = default;
};
struct Span {
  std::size_t begin{};
  std::size_t end{};
  std::size_t line{1};
  std::size_t column{};
  FileId file{};
};

\chapter{从语法分析树到 AST}
\label{chap:front-builder}

\section*{导读}
语法分析树记录一段输入怎样满足 grammar，AST 则记录这段程序由哪些语言结构组成。二者可以描述同一个输入，却不需要有相同的节点层次。本章从两种树的差别出发，沿着优先级、结合性、后缀链和语法上下文阅读构造器。重点是理解一个结构怎样被建立，以及哪些依赖应当留在解析边界。掌握这种阅读方法以后，读者可以在不运行整个编译器的情况下推导一段代码的 AST 形状。

\section{Parse tree 与 AST}
在 grammar 中，加法规则引用乘法规则，乘法规则引用转换规则，转换规则继续引用单目和后缀规则。这些层次很适合表达优先级，因为每一层限制自己可以包含哪些更紧密结合的表达式。但同一个整数也会通过这些中间规则向上到达 \texttt{expression}。

后续分析通常不需要逐层回答“这是 additiveExpression，还是 multiplicativeExpression 的一条通过路径”。它需要知道当前节点是整数、路径、二元运算还是调用。因此，构造器越过仅用于组织 grammar 的中间层，把真正有意义的结构保存为 AST 载荷。

抽象并不意味着删除一切与拼写有关的信息。当前 AST 保留 \texttt{ParenExpr} 与 \texttt{ParenType}，也保存整数原拼写。这些信息可以服务源码观察和精确诊断。需要忽略括号的处理过程通过专门接口展开；它不必迫使其他使用者失去括号的存在信息。

这种分离还有一项重要结果：AST 的公开定义不包含 ANTLR 上下文类型。若调整 grammar 的表达式分层，许多变化只发生在构造器；二元表达式的左右字段及其使用者可以保持稳定。稳定的基础应当是语言结构，而不是生成器当前产生的某个类名。

\section{优先级如何形成父子关系}
\begin{lstlisting}[language=Rustless]
fn main() {
    let first = 1 + 2 * 3;
    let second = (1 + 2) * 3;
    let test = 1 + 2 < 4 && true;
}
\end{lstlisting}
乘法比加法结合得紧密，因此第一条初始化的根是加法，右子节点是乘法。第二条初始化的根是乘法，其左子节点保留括号，括号中再包含加法。第三条初始化先形成整数计算和比较，再把比较结果作为逻辑运算的输入。

\path{E:/RComplier/Rustless/grammar/Parser.g4} 的以下真实产生式说明了这项层次关系：
\begin{lstlisting}
additiveExpression
    : multiplicativeExpression (additiveOperator multiplicativeExpression)*
    ;
multiplicativeExpression
    : castExpression (multiplicativeOperator castExpression)*
    ;
castExpression
    : unaryExpression (AS typeRef)*
    ;
\end{lstlisting}
加法的每个操作数首先是一个完整的乘法表达式，而乘法的每个操作数又首先是一个完整的转换表达式。构造器按该结构读取子上下文，便不必另写一份优先级数值表来重新分析相同输入。

从紧密到松散，当前表达式 grammar 依次组织后缀、单目、转换、乘除余数、加减、移位、按位与、按位异或、按位或、比较、逻辑与、逻辑或和赋值。这个顺序是语言规则，不是 Visitor 重载的先后顺序。即使 C++ 处理函数的排列发生变化，只要 AST 已正确建立，优先级也不会随之改变。

这样的设计使一个重要决定只有一个主要来源。grammar 确定结合关系，构造器保存它，后续过程读取它。若后端再用运算符文本重新判断优先级，就会制造两份需要同时维护的解释。

\section{结合性与左折叠}
优先级说明不同运算之间怎样嵌套，结合性则说明同一层重复运算怎样组成树。对 \texttt{10 - 3 - 2}，左结合产生 \texttt{(10 - 3) - 2}；若错误地右结合，结果结构会变为 \texttt{10 - (3 - 2)}，语义也随之改变。

构造器用一个逐步累积的结果实现左折叠。它先接收第一个操作数，然后每遇到下一个操作数，就把已经建立的结果作为新节点的左孩子。以下是 \path{E:/RComplier/Rustless/src/frontend.cpp} 中 \texttt{fold\_binary} 的真实删节摘录；省去了 token 与规则上下文识别，只保留建立关系的部分。
\begin{lstlisting}[language=C++]
auto operand = build_expression(part);
if (!result) {
  result.emplace(std::move(operand));
  continue;
}
auto span = merge((*result)->span, operand->span);
auto binary = make_expr(
    context,
    ast::BinaryExpr{ast::binary_operator(operator_text), operator_span,
                    std::move(*result), std::move(operand)});
binary->span = span;
result = std::move(binary);
\end{lstlisting}
\texttt{std::move} 在这里转移已经建立的子树拥有关系。它没有深复制整个左子树；新二元节点接管旧结果，随后累积变量接管新节点。这样，构树步骤与最后的树形一致，且不会因反复复制已有前缀而增加不必要的工作。

赋值 grammar 采用另一种结构：右侧递归到整个表达式，所以 \texttt{a = b = 1} 的语法树按右侧嵌套。本例仅用于说明构树，不能据此断言赋值链通过语义检查。转换链 \texttt{x as u32 as i32} 则逐步包裹前一个结果：先形成转换到 \texttt{u32} 的节点，再以它为输入形成转换到 \texttt{i32} 的节点。

这几种构造方式不应被统一成没有说明的“不断添加操作数”。每一步到底是在左侧累积、递归右侧，还是包裹先前结果，是语言结构必须保留的差别。

\section{后缀链怎样包裹已有表达式}
下例使用具有实际声明的字段与方法：
\begin{lstlisting}[language=Rustless]
struct Pair { values: [i32; 2] }
impl Pair {
    fn get(&self) -> i32 { self.values[0] }
}
fn main() {
    let p = Pair { values: [1, 2] };
    let a = p.values[0];
    let b = p.get();
}
\end{lstlisting}
\texttt{p.values[0]} 的起点是路径 \texttt{p}。读取点号后，构造器建立字段节点，把 \texttt{p} 放入 \texttt{base}。读取方括号后，又建立索引节点，把整个字段节点放入新的 \texttt{base}。最终根节点是 IndexExpr，而不是一条平铺的“路径及附件”记录。

方法调用 \texttt{p.get()} 则把 \texttt{p} 作为 \texttt{receiver}，将方法名字与普通参数分开保存。普通调用的起点是 \texttt{callee}；它可以本身是一个表达式，例如局部变量所持有的函数项。相似的表面标点因此并不意味着所有后缀都应使用同一个字段集合。

\section{块、分号和尾表达式}
块包含语句序列，也可以有一个没有分号的尾表达式。
\begin{lstlisting}[language=Rustless]

}

    let x = 1;
    x + 2;

\end{lstlisting}

对于 grammar 已形成的语句，构造器逐项建立 Stmt；对于明确的尾表达式，构造器建立可选 tail。某些无分号的块类表达式先经语句规则识别，随后在构造阶段从最后一条语句移入 tail。真实的相关代码如下：
\begin{lstlisting}[language=C++]

  block->tail.emplace(build_expression(context->statementExpression()));
} else if (!block->statements.empty()) {
  auto *last = std::get_if<ast::ExprStmt>(&block->statements.back()->data);
  if (last && last->termination == ast::Termination::Omitted) {
    block->tail.emplace(std::move(last->expression));
    block->statements.pop_back();
  }
}
\end{lstlisting}
这是 \texttt{build\_block} 的删节摘录，来源仍是 \path{E:/RComplier/Rustless/src/frontend.cpp}。它解释的是 AST 的归属整理，尚未决定整个块的类型。块值与函数返回值是否匹配，需要后面的语义判断。

\section{类型与词法歧义的构造边界}
某些标点在不同上下文中有不同用途。\texttt{Vec::<Vec<i32>>::new()} 含有两层泛型闭合符；\texttt{x >> 1} 含有一个右移运算；\texttt{x >>= 1} 又是复合赋值。把所有相邻的 \texttt{>} 随意拼成右移，会破坏嵌套类型；无条件拆分右移也会使运算规则难以识别原来的整体 token。

当前 Lexer 在读取 \texttt{>} 后进入专门模式，用不同 token 类型保留一个最大标点组合中的后续部分。parser 的 \texttt{genericClose} 读取单个闭合部分，\texttt{shiftRight} 与赋值规则则读取相应完整组合。来自两个不同 token 的部分不能仅凭相邻位置重新组成一个运算符。这项细节被限制在 Lexer 与 grammar 中；AST 保存的仍然是 \texttt{BinaryOp::Shr} 或 \texttt{CompoundAssignOp::Shr}。

引用类型中的 \texttt{\&\&} 也需要展开为两层，而不是一种新的“二重引用”节点。对语法片段 \texttt{\&\&'a mut i32}，外层是不可变引用，生命周期和可变性属于内层。构造器首先建立内层，再用外层包裹它，并调整内层的源码起点。这样，嵌套引用直接复用 ReferenceType，不需要让语义阶段再解释一个特殊旗标。

转换后的 \texttt{<} 同样可能被看作类型参数的开始。写为 \texttt{x as (i32) < y} 时，括号明确界定转换类型；grammar 中的 closed 类型和表达式规则负责表达这类边界。教读者理解这些规则，比让后续阶段看到“含糊的转换字符串”后再猜测意图更清晰。

\section{普通、条件与语句表达式}
条件中的 \texttt{if value \{ ... \}} 需要区分条件路径与随后分支块。若无界定地允许 \texttt{value \{ ... \}} 在该处成为结构体构造，parser 就可能把分支大括号吞进条件。当前 condition 规则因此限制未加界定的结构体构造，而括号、数组、调用参数等界定结构中的表达式可以使用普通规则。

条件中的 break 操作数还有相似问题：若它以一个裸块开始，块可能与正在寻找的分支边界混淆。因此 grammar 对该起点作出限制，同时保持后续操作数的正常结合。这些规则是为消除具体语法歧义而设，不应被推广成“条件表达式的语义总是不同”。

语句开头也有自己的限制。一个块类表达式可以直接组成语句；若它还要继续形成后缀表达式，当前 grammar 要求先经过点号后缀。用括号界定的表达式则有更清楚的起点。这些选择说明了为什么 Parser.g4 同时存在普通、条件和语句表达式家族。

构造器根据规则名称识别这些家族，却把相同的实际结构转成同一套 AST 载荷。条件中的加法、语句中的加法与普通加法都成为 BinaryExpr。于是语义规则只需要处理“加法表达式”，不必复制三套以 parser 上下文命名的类型。

这一点体现了抽象边界的作用：grammar 可以因识别需求更细分，AST 则按已确定的语言形状汇合。若让三个语法上下文变成三个语义节点，每当修改整数运算规则，就必须重复修改原本相同的判断。

\section{构树成功与错误处理}
\texttt{AstBuilder} 只在 parser 没有报告错误时建立并发布树。节点身份和源码范围由 \texttt{stamp} 统一填写，表达式的具体载荷则由 \texttt{make\_expr} 装入 variant。真实摘录来自 \path{E:/RComplier/Rustless/src/frontend.cpp}：
\begin{lstlisting}[language=C++]
template <typename Node> void stamp(Node &node, ParseContext *context) {
  node.id = ast::NodeId{next_id_++};
  node.span = source_span(context);
}
template <class Payload>
ast::ExprPtr make_expr(ParseContext *context, Payload payload) {
  auto expression = ast::box<ast::Expr>(ast::Expr::Data{std::move(payload)});
  stamp(*expression, context);
  return expression;
}
\end{lstlisting}
集中处理共同信息能够减少遗漏，但它不代替各载荷的构造责任。二元载荷仍需要明确提供两个子节点，函数仍需要提供函数体。构造器遇到已经假定存在却找不到的操作数时，抛出内部逻辑错误；这种错误说明手写构造逻辑或 grammar 适配出了问题，与用户程序的正常语法诊断不同。

生成 parser 的类在输入流、token stream 和 parser 对象的寿命范围内使用。构树器把语言所需的数据移入自己的 AST，\texttt{parse\_source} 最后返回拥有树的结果。后续使用者不需要保存 parser 来读取表达式。下一章将从这些构造要求出发，研究 AST 的类型和拥有关系。

\chapter{节点身份、具体载荷与所有权}
\label{chap:front-ownership}

\section*{导读}
二元表达式需要左右两个操作数，返回表达式可以没有返回值，函数调用则需要一个有序参数序列。让这些差别停留在注释和约定中，处理过程就必须反复检查它们。本章讨论如何把结构要求写入 C++ 类型，并解释节点身份、活动载荷和子节点拥有关系各自承担的职责。这里的类型安全首先指语法结构的可表达性；表达式的语言类型仍由语义阶段判断。

\section{相同拼写与不同出现}
\begin{lstlisting}[language=Rustless]
fn main() {
    let first = 1 + 2;
    let second = 1 + 2;
}
\end{lstlisting}
两次加法有相同运算符和相同字面量，却位于不同源码范围中，也属于不同变量的初始化。若一条语义事实只用字符串 \texttt{1 + 2} 作为键，便无法确定它属于哪一次出现。\texttt{NodeId} 为节点提供身份，使位置相同与结构相同不必被误认为同一节点。

项目使用带标签的整数包装，而非把每种身份都声明为普通 \texttt{uint32\_t}。来自 \path{E:/RComplier/Rustless/include/rx/ast/node.hpp} 的摘录如下：
\begin{lstlisting}[language=C++]
template <class Tag> struct Id {
  std::uint32_t value{};
  auto operator<=>(const Id &) const = default;
};
struct NodeTag;
using NodeId = Id<NodeTag>;
\end{lstlisting}
标签参与 C++ 类型，因此节点身份与使用另一个标签的声明身份不能无意互换。它们可能使用相同的数值表示，却不是相同的概念。源码范围也不适合充当唯一身份：不同层次节点的范围可以重叠，括号包装与内部表达式还可能具有紧密相邻的范围。

当前身份在一次构树过程中分配，零通常表示尚未设置。它不是跨编译持久编号，也不保证按源位置排序；某些外层节点是在子结构完成后才分配。若未来支持增量分析，需要另行设计版本与持久关联，不能仅凭当前递增整数推导出这些能力。

\section{Node 与承载节点}
\texttt{Node} 保存各类有身份节点共同需要的信息：
\begin{lstlisting}[language=C++]
struct Node {
  NodeId id{};
  Span span{};
};
\end{lstlisting}
\texttt{Expr : Node} 继承这两项信息，但一个 Expr 的具体形状由其 \texttt{Data} 决定。我们把有身份的外层称为承载节点，即 owner，把描述形状的数据称为具体载荷，即 payload。例如，BinaryExpr 保存运算和左右孩子；它本身没有继承 Expr。

\section{从通用字段集合到 variant}
早期 AST 常采用一个枚举标签和一组通用字段。下面是这种方式的教学缩略示意，不是当前项目定义：
\begin{lstlisting}[language=C++]
struct OldExpr {
  Kind kind;
  std::string text;
  std::vector<ExprPtr> operands;
  TypePtr cast_type;
  bool flag;
};
\end{lstlisting}
这种结构允许表示整数，却同时携带转换类型；也允许把 kind 设为 Binary 后仍不给两个操作数。\texttt{text} 与 \texttt{flag} 的含义随种类变化，读者必须查找外部约定才能理解字段。每个消费者又都需要自行确认这些约定。

具体载荷将关系改写为命名字段。真实 BinaryExpr 定义如下，来自 \path{E:/RComplier/Rustless/include/rx/ast/expr.hpp}：
\begin{lstlisting}[language=C++]
struct BinaryExpr {
  BinaryOp op;
  Span operator_span;
  ExprPtr left;
  ExprPtr right;
};
\end{lstlisting}
二元表达式不会额外拥有 callee 或字段初始化列表。Expr 的 variant 在同一时刻保存一种载荷，并管理相应对象的构造与析构。kind 与数据形状不再是两份手工维护的声明：当前活动的 C++ 类型就说明形状。

这项约束并不检查 \texttt{left} 的语言类型是否支持 \texttt{op}。\texttt{1 + true} 依然可以建立 BinaryExpr，因为它确实具有两个操作数和一个加法运算符。结构安全使语义检查面对清楚的输入，语义检查再判断这些输入能否组合。让两层承担各自能够表达的关系，比用一个“合法”标志概括全部判断更容易维护。

\section{必需、可选与有序子结构}
一个二元表达式缺少右操作数，通常没有合理的完整 AST 含义。一个 \texttt{return} 没有返回值，却可能是合法的写法。一个调用没有参数，还应有被调用表达式。这几种情况应当分别表示。

必需孩子使用 \texttt{Box<T>}；可选孩子使用 \texttt{optional<Box<T>>}；有序序列使用 \texttt{vector<Box<T>>}。下面的真实载荷定义显示区别：
\begin{lstlisting}[language=C++]
struct CallExpr {
  ExprPtr callee;
  std::vector<ExprPtr> arguments;
};
struct ReturnExpr {
  std::optional<ExprPtr> value;
};
\end{lstlisting}
\begin{lstlisting}[language=Rustless]
fn zero() {}
fn add(a: i32, b: i32) -> i32 { a + b }
fn main() {
    zero();
    let result = add(1, 2);
    return;
}
\end{lstlisting}
空参数序列是调用的一个普通状态，空 callee 却不是。没有返回值由 optional 的缺席表示；\texttt{return ()} 则有一个实际 UnitExpr。二者可以在语义上产生相关结果，但在语法结构上仍有区别。

\section{递归类型与移动所有权}
Expr 的载荷可以拥有其他 Expr；TypeSyntax 的数组长度又可以拥有 Expr。这形成递归定义。直接把所有孩子按值嵌入对象会导致无法确定有限的对象大小，因此孩子需要间接存储。

当前 Box 使用独占指针，禁止复制，并在构造时拒绝空指针。以下为 \path{E:/RComplier/Rustless/include/rx/ast/node.hpp} 的真实删节摘录：
\begin{lstlisting}[language=C++]
template <class T> class Box {
public:
  explicit Box(std::unique_ptr<T> value)
      : value_(value.release(), [](T *pointer) { delete pointer; }) {
    if (!value_)
      throw std::invalid_argument("a required AST child cannot be null");
  }
  Box(Box &&) noexcept = default;
  Box &operator=(Box &&) noexcept = default;
  Box(const Box &) = delete;
  Box &operator=(const Box &) = delete;
  const T *operator->() const { return value_.get(); }
private:
  std::unique_ptr<T, void (*)(T *)> value_;
};
\end{lstlisting}
独占拥有使树的销毁路径明确：父节点销毁时，其孩子也沿拥有边销毁。构造时移动子树，则把责任交给新的父节点。它不会使两个父节点同时负责删除同一个孩子。若需要跨树共享结构，必须另行选择相应的拥有模型，而不能随意复制 Box。

递归头文件还存在不完整类型问题。某个头文件可能只知道 \texttt{struct Block;}，却需要保存 \texttt{Box<Block>}。当前删除器在 T 已完整的位置创建，并以函数指针保存，销毁持有者时不要求每个递归头文件都包含全部节点定义。这帮助将语法族分开，但通常增加一个删除器指针和间接删除调用的成本。

构造时非空并不意味着任意时刻的任意 Box 都可解引用。移动后原对象可能为空；它应被销毁或重新赋值，不应再被当作有效孩子读取。完整 AST 的必需孩子应处在有效拥有状态。理解 moved-from 对象的限制，才能准确说明这项类型约束。

\section{只读发布与可构造性}
前端发布 \texttt{unique\_ptr<const Crate>}，正常读取路径因此获得 const 树。Box 的 const 解引用返回 const 子节点，vector 中的载荷与子结构也通过 const 路径观察。Visitor 接口进一步只接收 const owner 和 const payload。

只读发布让多种分析过程可以共享结构，而不必担心某个打印步骤顺手改写运算符或移动孩子。语义事实独立保存，也便于描述“读树并建立结论”这一过程。若某个后续变换需要改写程序，宜为它明确选择修改接口或新的表示，而不是让普通查询隐含修改能力。

不过，节点字段仍可在手工构造时被赋值，id 和 span 也不是构造参数中的强制条件。类型系统已经排除了一部分非法形状，构树器和一致性检查仍负责其他关系，例如身份唯一、范围有效和来源归属。这种分层约束应当如实说明；不能因为接口只读，就推导出每一个手工构造的对象都已经正确。

\section{存储方案的取舍}
variant 对象需要足够的空间容纳最大的活动载荷，并保存判别信息。它通常不为自己的活动载荷单独申请堆空间，但载荷中的 string、vector 以及 Box 孩子仍可能分配。因而“使用 variant”与“所有节点紧凑连续”之间没有必然关系。

逐节点 Box 分配容易表达树拥有关系，却带来分配次数和间接访问。arena 可以把一批节点放入集中管理的存储区域，用整体寿命减少个别删除操作；索引式节点可以把边表示为编号，并使用数组管理对象。但这些方式还需要回答地址稳定、不同载荷尺寸、容器内部分配和对象析构的问题。

本章明确了所有节点共同遵守的原则。下一章将阅读名字、类型语法和声明，观察这些原则怎样落到完整语言子集中的具体字段。

\chapter{名字、类型语法与声明的组织}
\label{chap:front-declarations}

\section*{导读}
名字既出现在变量绑定中，也出现在路径、类型和导入中；相似的拼写并不保证相同的用途。本章先阅读名字与路径，再进入类型语法、函数、结构体和实现块，最后讨论导入树与生命周期约束。各节都以“这项信息属于哪一层结构”为线索，说明为什么名字、可变性、类型实参和接收者不能被平铺在一个通用记录中。语义分析将以这些清楚的结构为输入，进一步确定声明与类型的含义。

\section{Identifier、Binding 与 Mutability}
\begin{lstlisting}[language=Rustless]
fn main() {
    let value = 1;
    let mut counter = value;
    counter += 1;
}
\end{lstlisting}
\texttt{value} 和 \texttt{counter} 的声明包含名字与绑定可变性，但表达式中的 \texttt{value} 只是一次名字引用。名字本身不应永久带有“可变变量”的意义：同一个拼写可以在别的作用域中绑定不同声明，字段与函数也有名字。可变性应属于当前绑定的语法位置。

\path{E:/RComplier/Rustless/include/rx/ast/names.hpp} 使用下列真实定义：
\begin{lstlisting}[language=C++]
struct Identifier {
  std::string text;
  Span span;
};
struct LifetimeName {
  std::string text;
  Span span;
};
enum class Mutability { Immutable, Mutable };
struct Binding {
  Identifier name;
  Mutability mutability;
};
\end{lstlisting}
Identifier 与 LifetimeName 可以采用相似的存储，却以不同 C++ 类型表达用途。Mutability 使用枚举，使调用者写出 Immutable 或 Mutable，而不用解释某个通用 bool 在此处是否表示“可变”“取反”或“省略”。专业而清楚的数据结构，常常由这种局部区分积累而成。

这些值记录保存范围，却不都具有 NodeId。每个字符名字都分配独立身份未必必要；只有需要独立事实与结构遍历的承载节点才进入统一 owner 集合。选择身份粒度时，需要考察后续查询的对象，而不应机械地令所有 struct 都继承 Node。

\section{路径按段保存}
\begin{lstlisting}[language=Rustless]
fn main() {
    let values = Vec::<i32>::new();
}
\end{lstlisting}
路径由多个段组成。这里的类型实参 \texttt{i32} 属于 \texttt{Vec} 段，\texttt{new} 是随后的一段。若只保存一个名字数组和一个总类型实参数组，便难以知道参数原来附着在哪里。对语法观察片段 \texttt{Foo<'a, i32>::Bar<u32>}，这项问题尤其明显：两个段各有自己的实参。

真实路径定义位于 \path{E:/RComplier/Rustless/include/rx/ast/path.hpp}。下面的摘录把段级关系完整展示出来：
\begin{lstlisting}[language=C++]
struct SelfValue { Span span; };
struct SelfType { Span span; };
using PathName = std::variant<Identifier, SelfValue, SelfType>;
using GenericArgument = std::variant<TypePtr, LifetimeName>;
struct GenericArguments {
  Span span;
  std::vector<GenericArgument> values;
};
struct PathSegment {
  PathName name;
  std::optional<GenericArguments> arguments;
  Span span;
};
struct Path {
  Span span;
  std::vector<PathSegment> segments;
};
\end{lstlisting}
\texttt{self} 是值路径中的特殊名字，\texttt{Self} 则代表当前实现目标类型的语法写法。把它们作为 PathName 的分支，可以使语义分析按其角色解释，而不是在任意 Identifier 中反复比较特定字符串。

GenericArgument 又区分 TypePtr 与 LifetimeName。二者在语法上可以出现在同一个实参列表中，却不具有相同的子结构。类型实参可能继续包含引用或数组；生命周期名只是其专属记录。保留段序列与列表范围，还能精确指出错误实参所在的位置。

\section{五种类型语法}
类型语法描述程序怎样写出类型，尚不是语义类型本身。当前 TypeSyntax 的五个分支分别表达单位、路径、引用、数组和括号。
\begin{lstlisting}[language=Rustless]
const N: usize = 3;
fn read<'a>(x: &'a i32) -> i32 { *x }
fn change(x: &mut i32) { *x = 2; }
fn main() {
    let unit: () = ();
    let value: (i32) = 1;
    let values: [i32; N] = [1, 2, 3];
}
\end{lstlisting}
UnitType 没有孩子，因为 \texttt{()} 本身就确定这种写法。PathType 保存路径，使 \texttt{i32}、用户结构体名字及容器路径共用路径结构。ReferenceType 保存 referent、可变性与可选生命周期。ArrayType 同时有元素类型与长度表达式。ParenType 则拥有被括起来的类型语法。

下列真实摘录来自 \path{E:/RComplier/Rustless/include/rx/ast/type.hpp}：
\begin{lstlisting}[language=C++]
struct ReferenceType {
  std::optional<LifetimeName> lifetime;
  Mutability mutability;
  TypePtr referent;
};
struct ArrayType {
  TypePtr element;
  ExprPtr length;
};
struct ParenType { TypePtr inner; };
struct TypeSyntax : Node {
  using Data =
      std::variant<UnitType, PathType, ReferenceType, ArrayType, ParenType>;
  explicit TypeSyntax(Data value) : data(std::move(value)) {}
  Data data;
};
\end{lstlisting}
\texttt{[i32; N]} 的 length 没有被提前压缩成一个数字。构树器只知道它是一段允许的常量语法，语义阶段才解析 N 的声明并得到长度。若 AST 在尚未完成名字解析时就强迫保存最终长度，构树器便会承担另一阶段的责任。

嵌套引用也应逐层阅读。语法片段 \texttt{\&\&'a mut i32} 的外层不可变，内层具有生命周期 \texttt{'a} 与 Mutable。每层是一个 ReferenceType，因此任意深度可以沿 referent 继续表达，不需要额外的“引用层数”字段。

\section{函数签名与接收者}
\begin{lstlisting}[language=Rustless]
struct Counter { value: i32 }

    fn read(&self) -> i32 { self.value }
    fn set(&mut self, next: i32) { self.value = next; }

普通参数写出绑定和类型。接收者则使用 self 的专门语法：值接收者与引用接收者可以各自可变，引用接收者还可以带生命周期。这几种形式不应挤进一个“第零个普通参数”的特殊约定，因为其类型来自 impl 目标与接收方式，而不一定直接写在源码中。

\path{E:/RComplier/Rustless/include/rx/ast/item.hpp} 的真实定义如下：
\begin{lstlisting}[language=C++]

\section{结构体字段、常量与 derive}
\begin{lstlisting}[language=Rustless]

\end{lstlisting}

\begin{lstlisting}[language=C++]

  Identifier name;
  TypePtr type;
};

  Identifier name;
  ExprPtr value;
};

常量声明具有必需类型和常量语法值。当前 const 子集较有限，不能把任意加法表达式都当作已实现的常量初始化能力。数组长度可以引用常量，语义阶段按照依赖解释它们；AST 不提前执行这种解释。

derive 属性保存属性范围及有序 DeriveName 序列，每个名字记录 DeriveKind 和范围。支持的名字为 Copy、Clone、PartialEq、Eq。它们表达请求哪些语义能力，不意味着构树器已经产生复制或比较的机器代码。属性属于结构体的语法数据，能力检查和运行实现还有各自的阶段。

\chapter{表达式、语句与块：完整结构的阅读}
\label{chap:front-expressions}

\section*{导读}
表达式既包括数字和加法，也包括数组、调用、分支与跳转。它们共同属于表达式家族，却具有不同的子结构。本章按这些结构关系阅读全部载荷，再说明语句与块值。每次观察例子时，可以依次询问：哪些孩子必需，哪些可选，哪些构成有序序列，哪些只是名字或枚举？这种问题比记忆 operands 的下标约定更有助于建立可维护的 AST。

\section{原子与括号}
\begin{lstlisting}[language=Rustless]
fn main() {
    let number = 0b1_010u32;
    let flag = false;
    let unit = ();
    let name = number;
    let grouped = (number);
}
\end{lstlisting}
IntegerExpr、BooleanExpr 和 UnitExpr 不拥有表达式孩子。PathExpr 保存 Path；ParenExpr 则拥有一个必需 inner。单位值 \texttt{()} 与空 optional 不同：前者是一个明确表达式，后者说明源码没有提供表达式。

真实整数定义位于 \path{E:/RComplier/Rustless/include/rx/ast/literal.hpp}：
\begin{lstlisting}[language=C++]
struct IntegerLiteral {
  std::string spelling;
  IntegerBase base;
  std::optional<IntegerSuffix> suffix;
  // parse(...) identifies the base and optional suffix.
};
struct IntegerExpr { IntegerLiteral literal; };
struct BooleanExpr { bool value; };
struct UnitExpr {};
\end{lstlisting}
其中 parse 的实现被删去并以说明注释标记；其余字段与定义保持原样。spelling 用于保留原始写法，base 与 suffix 则供后续读取已识别的信息。幅值解码和目标范围检查不在这个记录中完成，因此消费者不应仅凭 IntegerLiteral 已建立，就假定数值一定适合目标整数类型。

保留 ParenExpr 使括号仍有身份和范围。某些分析只关心内部结构，可以使用 \texttt{unparen}，其真实代码位于 \path{E:/RComplier/Rustless/include/rx/ast/expr.hpp}：
\begin{lstlisting}[language=C++]
inline const ExprPtr &unparen(const ExprPtr &expr) {
  if (auto *paren = get_if<ParenExpr>(*expr))
    return unparen(paren->inner);
  return expr;
}
\end{lstlisting}
这个辅助函数返回现有子节点的引用，不建立一棵删掉括号的新树。选择忽略括号是处理过程的决定；其源码信息仍保留给其他过程。它也不自动解释括号内表达式的使用处转换，语义事实仍需要以明确节点和输入边为依据。

\section{运算符成为枚举}
二元运算有一个共同形状，却包含多种运算。当前 BinaryOp 明确列出十八种：加、减、乘、除、余数；按位与、或、异或；左移、右移；相等、不等与四种顺序比较；逻辑与、逻辑或。它们可以使用同一个 BinaryExpr，因为都需要左右表达式，同时通过枚举保留准确操作。

下例将全部二元家族放在合法类型的上下文中，目的是观察语法载荷；其中逻辑运算的短路执行将在 IR 章节继续解释。
\begin{lstlisting}[language=Rustless]
fn main() {
    let x: i32 = 8;
    let y: i32 = 2;
    let a = x + y; let b = x - y; let c = x * y;
    let d = x / y; let e = x % y;
    let f = x & y; let g = x | y; let h = x ^ y;
    let i = x << 1; let j = x >> 1;
    let k = x == y; let l = x != y;
    let m = x < y; let n = x <= y;
    let o = x > y; let p = x >= y;
    let q = true && false; let r = true || false;
}
\end{lstlisting}
UnaryOp 区分 Negate、Not 与 Dereference，分别对应 \texttt{-x}、\texttt{!x} 和 \texttt{*r}。BorrowExpr 则专门保存可变性和操作数；\texttt{\&x} 与 \texttt{\&mut x} 不依赖一个含义随种类改变的通用 flag。

AssignExpr 与 CompoundAssignExpr 也分开定义。普通赋值只有 target 和 value，复合赋值还拥有自己的操作枚举与操作符范围。两种枚举使用不同 C++ 类型，不能无意把 Eq 或 LogicalAnd 当成复合赋值操作。
\begin{lstlisting}[language=Rustless]
fn main() {
    let mut x: i32 = 8;
    x = 2;
    x += 1; x -= 1; x *= 2; x /= 2; x %= 3;
    x &= 7; x |= 1; x ^= 2; x <<= 1; x >>= 1;
    let shared = &x;
    let value = *shared;
    let negative = -value;
    let bits = !value;
    let changed = value as u32;
}
\end{lstlisting}
CastExpr 以 value 和 target\_type 保存转换。转换目标是类型语法，不能与另一个表达式孩子混在同一个操作数数组中。\texttt{as} 的合法性和具体转换规则仍需 semantic 决定。

\path{E:/RComplier/Rustless/include/rx/ast/operators.hpp} 将文字解析限制在 parser 边界，提供 binary\_operator、unary\_operator 和 compound\_operator。后续过程读取枚举，就不必每次比较 \texttt{"+"}、\texttt{"+="} 或 \texttt{"\&\&"}。这减少了字符串判定的重复，也使未知操作不能悄悄退入某个默认解释。

\section{数组与结构体构造}
\begin{lstlisting}[language=Rustless]
struct Pair { left: i32, right: i32 }

    let repeated = [0; 3usize];
    let empty: [i32; 0] = [];

\section{调用与投影}
\begin{lstlisting}[language=Rustless]
struct Pair { values: [i32; 2] }
impl Pair { fn get(&self) -> i32 { self.values[0] } }
fn echo(x: i32) -> i32 { x }
fn main() {
    let p = Pair { values: [1, 2] };
    let a = echo(p.get());
    let b = p.values[0];
}
\end{lstlisting}
CallExpr 的 callee 是表达式，arguments 是普通参数序列。MethodCallExpr 的 receiver 是接收者表达式，method 是名字，generic\_args 是可选的段级实参，arguments 仍只保存括号中的普通参数。接收者因此不会被误计入源码参数列表。
\begin{lstlisting}[language=C++]
struct MethodCallExpr {
  ExprPtr receiver;
  Identifier method;
  std::optional<GenericArguments> generic_args;
  std::vector<ExprPtr> arguments;
};
struct FieldExpr {
  ExprPtr base;
  Identifier field;
};
struct IndexExpr {
  ExprPtr base;
  ExprPtr index;
};
\end{lstlisting}
这些是 expr.hpp 中的真实定义。字段投影拥有名字，索引投影拥有一个表达式。\texttt{p.values} 和 \texttt{p.get()} 虽然都使用点号，却分别表示选择字段和调用方法；两种结构不能仅靠“是否有附件”的模糊约定区分。

AST 保存的 method 名字与最终函数目标也需要区分。\texttt{p.get()} 的语义可能要求接收者自动解引用和借用，最后调用某个关联声明。那些结论由语义事实保存，AST 继续忠实描述源码的 receiver 和参数。

当前 grammar 允许方法段保存类型实参，实际语义子集并不因此支持任意泛型方法。复杂链 \texttt{x.foo::<i32>(1).bar[0]} 可以用于检查 parser 与构树结果，但若没有相应声明，就只能标为语法观察例子。这是把语法结构与语言能力分开的又一处必要说明。

\section{块、if 与 else-if}
\begin{lstlisting}[language=Rustless]
fn choose(value: i32) -> i32 {
    let prepared = { let base = value + 1; base };
    if prepared < 0 { 0 }
    else if prepared < 10 { prepared }
    else { 10 }
}
\end{lstlisting}
BlockExpr 拥有一个 Block；IfExpr 拥有条件、then\_block 和可选 else\_branch。else 的内容既可能是最终 Block，也可能是下一层 IfBranch。后者保有自己的 NodeId 与范围，但不需要伪造一个只为了包装条件的额外普通块。

真实定义如下：
\begin{lstlisting}[language=C++]
using ElseBranch = std::variant<Box<Block>, Box<IfBranch>>;
struct IfExpr {
  ExprPtr condition;
  Box<Block> then_block;
  std::optional<ElseBranch> else_branch;
};
struct IfBranch : Node {
  explicit IfBranch(IfExpr value) : data(std::move(value)) {}
  IfExpr data;
};
\end{lstlisting}
IfBranch 复用 IfExpr 的结构，但提供有身份的承载层。这样，else-if 既不被错误地当成无身份普通记录，也不需要在 Expr::Data 中再增加一种与 IfExpr 几乎相同的载荷。统一访问接口可以读取其 owner 与 data。

\section{循环与跳转}
\begin{lstlisting}[language=Rustless]
fn search() -> i32 {
    let answer = loop {
        break 42;
    };
    let mut count = 0;
    while count < 3 {
        count += 1;
        if count == 2 { continue; }
        if count == 3 { break; }
    }
    return answer;
}
\end{lstlisting}
LoopExpr 只有 body，WhileExpr 则有 condition 与 body。BreakExpr 可以带值，ContinueExpr 没有值，ReturnExpr 也可以带值。这些差别由专属载荷表达：
\begin{lstlisting}[language=C++]
struct LoopExpr { Box<Block> body; };
struct WhileExpr {
  ExprPtr condition;
  Box<Block> body;
};
struct BreakExpr { std::optional<ExprPtr> value; };
struct ContinueExpr {};
struct ReturnExpr { std::optional<ExprPtr> value; };
\end{lstlisting}
这些定义来自 expr.hpp。树中的 break 并没有一条指向目标循环的拥有边，return 也没有拥有函数声明。控制目标由上下文解释，后续可以记录解析结果或直接在转换环境中维护目标。若将父节点反向指针随意加入拥有结构，便可能制造环和复杂寿命；应先判断需要的是查询关系还是拥有关系。

AST 允许描述 \texttt{break 42}，却不自动保证它位于允许值退出的循环。\texttt{continue} 的合法位置、while 中 break 是否允许值，以及返回值与签名的关系，都属于 semantic。结构完整与控制合法是两个需要分别检查的承诺。

\section{三种语句与块值}
\begin{lstlisting}[language=Rustless]
fn result() -> i32 {
    ;
    let x: i32 = 1;
    printInt(x);
    x + 2
}
\end{lstlisting}
EmptyStmt 表示源码中的单独分号。LetStmt 具有 Binding、可选注解与必需 initializer。ExprStmt 具有表达式及分号终止方式。Block 则在语句序列之外保存可选 tail。

\path{E:/RComplier/Rustless/include/rx/ast/stmt.hpp} 的真实摘录如下：
\begin{lstlisting}[language=C++]
enum class Termination { Semicolon, Omitted };
struct EmptyStmt {};
struct LetStmt {
  Binding binding;
  std::optional<TypePtr> annotation;
  ExprPtr initializer;
};
struct ExprStmt {
  ExprPtr expression;
  Termination termination;
};

  using Data = std::variant<EmptyStmt, LetStmt, ExprStmt>;
  explicit Stmt(Data value) : data(std::move(value)) {}

  std::vector<StmtPtr> statements;
  std::optional<ExprPtr> tail;

\section{完整结构与后续解释}
Expr::Data 完整列出了二十五种载荷。下面是 expr.hpp 中的真实全集定义：

      std::variant<IntegerExpr, BooleanExpr, UnitExpr, PathExpr, ParenExpr,

                   LoopExpr, WhileExpr, UnaryExpr, BorrowExpr, BinaryExpr,

结构性孩子通常按源码顺序枚举，便于确定的打印和观察。但树遍历不是程序执行：\texttt{false \&\& expensive()} 的右孩子仍存在于 AST 中，却不会在短路执行中总被计算；while 的 body 是一个孩子，运行时可以进入多次或零次。Visitor 负责选择处理规则，控制流则需要语义和 IR 的进一步表示。

下一章将使用这份完整节点集合，讨论同一棵树怎样服务于打印、类型检查和其他过程。专属载荷提供清楚的数据，Visitor 再提供按具体数据选择规则的方法。

\chapter{Visitor 与 variant：按具体结构选择处理规则}
\label{chap:front-visitor}

\section*{导读}
表达式 \texttt{1 + 2} 可以被打印，可以被检查类型，也可以被求出常量值或转换成 IR。它的语法结构不会随这些任务改变，而每种任务又需要区别整数、二元运算和其他节点。本章研究怎样让稳定的结构服务于不同处理过程。首先明确节点种类与处理过程这两个扩展方向，再阅读当前项目的 variant 分派，最后与经典虚函数 Visitor 作准确比较。理解这些关系以后，就能判断一种设计在新增语言结构、新增分析和发现遗漏时分别提供什么帮助。

\section{两条扩展方向}
考虑下面这个完整程序：
\begin{lstlisting}[language=Rustless]
fn sum() -> i32 {
    1 + 2
}
\end{lstlisting}
建树之后，整数载荷保存字面量，二元载荷保存 Add、左孩子与右孩子。打印过程需要输出这些结构；类型检查需要判断操作数与运算是否合法；常量求值需要对允许求值的操作计算结果。三者面对相同数据，却回答不同问题。

这自然形成两个方向：一个方向列出语言中的结构种类，另一个方向列出作用于结构的处理过程。增加一种节点，例如增加独立的重复数组表达式，会要求相关处理过程说明如何处理新结构。增加一种过程，例如增加只统计节点的观察器，则会要求它说明如何对待现有结构。

\section{当前实现的继承用于什么}
上一章的 Expr 继承 Node，因此每个表达式共有身份与源码范围。但 BinaryExpr、CallExpr 和 IntegerExpr 没有继承 Expr。它们是 Expr::Data 的可选载荷，而 Expr 是拥有该载荷的外层节点。

来自 \path{E:/RComplier/Rustless/include/rx/ast/expr.hpp} 的真实摘录能直接说明这一关系：
\begin{lstlisting}[language=C++]
struct BinaryExpr {
  BinaryOp op;
  Span operator_span;
  ExprPtr left;
  ExprPtr right;
};
struct CallExpr {
  ExprPtr callee;
  std::vector<ExprPtr> arguments;
};
\end{lstlisting}
两种载荷都没有虚析构函数，也没有虚 accept 函数。项目中的继承用于共享 Node 信息，不用于让具体表达式对象通过虚函数动态选择行为。读取一个 \texttt{const Node\&} 可以得到公共身份，却不能仅凭该引用恢复全部语法形状；具体形状仍由有类型的 owner 与活动载荷确定。

因此，当前实现应当称为基于 variant 的类型安全分派。它具有 Visitor 的组织作用，但不应被称为经典虚函数双分派。分派是怎样实现的，必须通过实际调用路径判断，不能仅因代码出现继承、重载或名为 Visitor 的类就作结论。

这一区分对于维护很重要。若误以为 BinaryExpr 是 Expr 的派生类，使用者可能尝试以 \texttt{dynamic\_cast} 找到它，或者把载荷当成独立拥有 NodeId 的节点。实际接口让使用者同时接收 owner 和 payload，避免这两种误读。

\section{variant、活动分支与重载}
先看一个仅供理解 C++ 机制的教学示例。它不替代项目的完整 AST：
\begin{lstlisting}[language=C++]
struct IntegerValue { int value; };
struct BooleanValue { bool value; };
using Value = std::variant<IntegerValue, BooleanValue>;

Value value = IntegerValue{3};
auto result = std::visit(
    rx::ast::Overloaded{
        [](const IntegerValue &p) { return p.value; },
        [](const BooleanValue &p) { return p.value ? 1 : 0; }},
    value);
\end{lstlisting}
Value 列明允许保存的两种形状。当前对象的活动分支是 IntegerValue，因此此次访问调用整数重载。另一个对象可以活动于 BooleanValue，而使用同一份处理规则。

variant 管理活动对象的构造和析构。它不是让两个对象同时共用一片未经管理的原始内存，也不是以字符串猜测当前对象是哪一种形状。普通使用时它保存一个活动分支；标准还允许某些抛异常的更换操作使其进入没有活动值的状态。当前 AST 的正常使用方式是构造完整树后通过 const 路径发布和读取，访问期间不更换节点的活动载荷。

运行时与编译期在这里承担不同任务。运行时需要查看当前对象的活动分支；编译期需要验证传入处理器能否处理 variant 列出的各类载荷。对整数对象调用整数重载，并不表示其他重载可以随意缺失，因为下一次访问可能遇到布尔对象。

若处理过程只想询问某一种形状，可以使用 \texttt{get\_if}。项目在 expr.hpp 中提供以下真实接口：
\begin{lstlisting}[language=C++]
template <class T> const T *get_if(const Expr &expr) {
  return std::get_if<T>(&expr.data);
}
\end{lstlisting}
返回非空指针表示当前载荷恰是 T；返回空指针表示不是。以下是使用该接口的教学代码：
\begin{lstlisting}[language=C++]
if (const auto *call = rx::ast::get_if<rx::ast::CallExpr>(expression)) {
  auto argument_count = call->arguments.size();
  // Use argument_count for this local query.
}
\end{lstlisting}
这种局部查询适合“此处是否为调用”一类问题。若一个过程本来需要处理每种表达式，连续写许多独立 get\_if，再为未匹配情况返回默认结果，就削弱了完整性检查。查询和完整处理需要不同接口，各自说明自己的用途。

\section{owner 与 payload 同时参与访问}
项目的处理函数接收两个只读参数。例如二元表达式处理器的形状是：
\begin{lstlisting}[language=C++]
Result operator()(const rx::ast::Expr &owner,
                  const rx::ast::BinaryExpr &payload);
\end{lstlisting}
这是接口形状的教学示意，其中 Result 由处理任务自行定义。owner 提供这一次表达式出现的 NodeId 和 Span；payload 提供操作符、左右孩子和运算符位置。二者指向同一个语法结构的不同职责，不是两份互不相关的节点。

以 \texttt{1 + 2} 为例，打印器可以从 payload 读取 Add，再从 owner 输出整个表达式范围；类型检查可以从 payload 读取操作数，再使用 owner 的范围报告运算错误；身份关联表可以按 owner.id 保存检查结果。载荷不必重复保存公共字段，处理过程也不必向外猜测它所属节点。

\path{E:/RComplier/Rustless/include/rx/ast/dispatch.hpp} 首先为不同 owner 找到载荷。以下是真实删节摘录，省去其他具有相同形式的重载：
\begin{lstlisting}[language=C++]
template <std::derived_from<Node> T> const T &payload(const T &node) {
  return node;
}
inline const auto &payload(const Expr &node) { return node.data; }
inline const auto &payload(const TypeSyntax &node) { return node.data; }
inline const auto &payload(const Stmt &node) { return node.data; }
inline const auto &payload(const UseTree &node) { return node.target; }
\end{lstlisting}
Expr、TypeSyntax、Stmt 和 UseTree 的 owner 内部有分支联合。Function、Struct、Block 等结构则本身就是具体形状，所以 payload 可以是 owner 自身。访问一个 Function 时，处理器接收 \texttt{(const Function\&, const Function\&)}；两个参数在这种情况引用同一个对象，公共访问协议保持一致。

真正的分派由以下真实实现完成：
\begin{lstlisting}[language=C++]
template <class T, class V>
  requires detail::SyntaxOwners::contains<T> && ExhaustiveVisitor<V, T>
decltype(auto) visit(const T &node, V &&visitor) {
  const auto &value = detail::payload(node);
  if constexpr (requires {
                  std::variant_size<
                      std::remove_cvref_t<decltype(value)>>::value;
                }) {
    return std::visit(
        [&](const auto &p) -> decltype(auto) {
          return std::invoke(visitor, node, p);
        },
        value);
  } else {
    return std::invoke(visitor, node, value);
  }
}
\end{lstlisting}
有 variant 载荷时，先选择活动分支；没有 variant 载荷时，直接调用具体结构处理函数。\texttt{if constexpr} 的判断发生在模板实例化时，编译器不会为每个已知具体类型保留两条待运行时猜测的路径。

Item 又处在另一个层次。Item 是 Use、Function、Struct、Constant、Impl 这些具有身份的具体 owner 之间的联合；ImplMember 是 Function 与 Constant 之间的联合。联合自身不额外增加一层 NodeId。dispatch.hpp 的真实实现先选出其中的 owner，再复用前述协议：
\begin{lstlisting}[language=C++]
template <class... Ts, class V>
  requires ExhaustiveVisitor<V, std::variant<Ts...>>
decltype(auto) visit(const std::variant<Ts...> &nodes, V &&visitor) {
  return std::visit(
      [&](const auto &node) -> decltype(auto) { return visit(node, visitor); },
      nodes);
}
\end{lstlisting}
这使声明联合、表达式联合与普通结构拥有一致入口，同时仍保留准确的具体 owner 类型。统一入口并未把所有数据压成一个失去结构的 Node 指针。

\section{穷尽性与统一返回类型}
完整处理首先要求每个可能分支都能够被调用。项目把这一要求写成 ExhaustiveVisitor concept，而不是依靠运行时到达某个未知分支后再报错。

在 dispatch.hpp 中，以下真实模板检查 variant 的全部载荷及返回类型：
\begin{lstlisting}[language=C++]
template <class V, class Owner, class... Ps>
struct VisitorCoverage<V, Owner, std::variant<Ps...>> {
  static consteval bool compatible() {
    if constexpr ((std::is_invocable_v<V &, const Owner &, const Ps &> &&
                   ...)) {
      using First = std::variant_alternative_t<0, std::variant<Ps...>>;
      using Result = std::invoke_result_t<V &, const Owner &, const First &>;
      return (
          std::same_as<Result,
                       std::invoke_result_t<V &, const Owner &, const Ps &>> &&
          ...);
    }
    return false;
  }
  static constexpr bool value = compatible();
};
\end{lstlisting}
折叠表达式逐一检查“以 const owner 和 const payload 调用是否成立”。只有全部成立，才检查所有调用结果是否与第一个分支完全相同。只接受可变载荷的函数不满足只读协议；缺少一个分支的函数不满足完整覆盖；某些分支返回 int、另一些返回 void 的函数不满足统一结果。

使用 \texttt{std::same\_as} 意味着这里要求准确的同一返回类型，而非仅仅能够转换到某个共同类型。这使调用者知道访问的结果究竟是什么。打印器可以统一返回 void，身份查询可以统一返回 NodeId，表达式检查可以统一返回自己的 ExprInfo。需要多种结果形状时，应由处理任务明确设计自己的结果 variant，而非让每个节点悄然决定不一致的返回类型。

\section{经典 Visitor 的双分派}
另一种标准做法是建立多态节点层次。每种具体节点继承共同基类，并实现 accept；处理过程继承 Visitor 接口，并实现每种节点的 visit。下面是解释调用机制的教学替代方案，不属于 Rustless 当前实现：
\begin{lstlisting}[language=C++]
struct IntegerNode;
struct BinaryNode;

struct ExprVisitor {
  virtual ~ExprVisitor() = default;
  virtual void visit(const IntegerNode &) = 0;
  virtual void visit(const BinaryNode &) = 0;
};
struct ExprNode {
  virtual ~ExprNode() = default;
  virtual void accept(ExprVisitor &) const = 0;
};
struct IntegerNode final : ExprNode {
  int value;
  void accept(ExprVisitor &visitor) const override {
    visitor.visit(*this);
  }
};
struct BinaryNode final : ExprNode {
  void accept(ExprVisitor &visitor) const override {
    visitor.visit(*this);
  }
};
\end{lstlisting}
当调用者持有 \texttt{const ExprNode\&} 与 \texttt{ExprVisitor\&} 时，第一次虚调用 accept 根据节点对象的动态类型进入 IntegerNode 或 BinaryNode 的实现。在 BinaryNode::accept 内，\texttt{*this} 的静态类型已经是 BinaryNode，因此重载解析选中 \texttt{visit(const BinaryNode\&)}。该 visit 又是虚函数，第二次动态选择根据 Visitor 对象的具体类型进入打印器、检查器等实现。

这里有两次动态选择，也有一次静态重载解析。经典双分派的效果是让节点种类与处理过程的动态类型共同确定行为。若只在 ExprNode 上放一个虚 print，则只有节点方向的动态选择；若只是给普通函数写几个重载，调用者静态持有 ExprNode 引用时，也不会自动根据真实派生类型选择 BinaryNode 重载。

\section{两种方案的具体取舍}
对于 Rustless 这种由一个 grammar 明确界定的语言子集，节点集合天然有边界。读者可以在 Expr::Data 中查看全体表达式；修改该集合会让严格处理器重新接受编译检查。variant 很适合表达这样的封闭集合。

虚函数派生让节点对象可以通过共同基类保存，单个对象只需包含自身具体字段与多态支持信息。它提供开放类层次的基础，但经典 Visitor 接口列明所有节点种类，因此“新增派生类很方便”和“所有既有 Visitor 无需改动”不能同时作为经典方案的无条件结论。新增节点通常仍要增加 visit 重载，并更新需要完整处理的 Visitor。

两种方式均能方便地把新处理过程写在节点定义之外。当前 variant 形式允许不同处理过程自然返回各自类型：打印返回 void，查询返回 NodeId，检查返回 ExprInfo。经典的单一虚接口必须确定虚函数签名；若不同过程需要不同结果，可以设计不同 Visitor 接口、通过 Visitor 状态取回结果，或采用其他抽象。各种方案都可成立，但需要明确额外结构的代价。

对象尺寸方面，variant 必须为最大载荷保留足够空间，并保存活动分支信息；派生对象通常按各自字段确定尺寸，但还涉及多态表示及分配方式。当前 AST 的子节点通过 Box 间接存储，所以不能从“使用 variant”推导出“全树连续存储”或“没有堆分配”。父子间接访问、分配数量和遍历局部性仍值得单独观察。

调用成本方面，std::visit 需要依据活动分支选择处理规则，具体实现可以使用条件、跳转表或其他策略。虚调用通常经由间接目标，优化器在已知动态类型时也可能消除间接调用。处理函数可否内联、节点分布、缓存行为以及优化选项都会影响结果。没有以相同工作负载测量，就不能断言 variant 恒定更快，或双分派必然构成可观瓶颈。

模板提供了很强的静态约束，但也使编译器为各种访问器和节点组合实例化代码。严格覆盖会增加编译期检查，错误信息的可读性依赖 concept 与接口组织；二进制体积和编译时间也需要实际评估。虚接口减少部分模板展开，却可能需要更多固定接口和适配状态。优雅的设计应当用合适代价获得明确责任，而不是把某个 C++ 机制本身当作目标。

最后，\texttt{dynamic\_cast} 是带运行时检查的多态转换，并不是未经检查的强制类型转换。对开放层次中的局部查询，它可以合理使用。若一个完整分析反复尝试几十种转换，并在未匹配时默默继续，问题在于规则覆盖没有清楚表达；把 dynamic\_cast 一概称为不安全，并不能指出真实设计缺陷。

\section{严格处理与显式兜底}
ExhaustiveVisitor 检查的是所有分支能否调用。因此，一个接受任意 payload 的泛型函数也满足调用覆盖。以下是真实测试中的身份观察器：
\begin{lstlisting}[language=C++]
struct IdentityVisitor {
  template <class T>
  ast::NodeId operator()(const ast::Node &node, const T &) const {
    return node.id;
  }
};
\end{lstlisting}
它有充分理由忽略具体载荷：每个有身份的 owner 都继承 Node，查询只需要公共 id。新增节点以后，取身份的规则仍成立。在这里，泛型兜底是有语义依据的明确选择。

若任务是运算类型检查，情况不同。新增一种运算节点后，返回“默认 i32”虽然使所有调用成立，却没有解释新结构的合法性。严格处理应当为各具体形状写规则，或者显式写出某个家族为何共享同一规则。概念约束能防止漏掉调用，但不能判断一个泛型兜底是否符合语言含义。

当前打印器的类型打印在 \path{E:/RComplier/Rustless/src/ast.cpp} 中列出 UnitType、PathType、ReferenceType、ArrayType 和 ParenType 五种分支。例如下面的真实摘录专门处理引用：
\begin{lstlisting}[language=C++]

语义过程也使用同样的分派协议，但返回自己的分析结果。\path{E:/RComplier/Rustless/src/semantic.cpp} 中以下两个真实分支，分别为布尔与单元表达式返回 ExprInfo：

对于节点统计、位置收集、身份搜索等观察任务，显式的默认行为很有帮助。下一章将给出 DefaultVisitor，它要求使用者明确继承默认规则，再覆盖自己关心的部分。完整语言处理与选择性观察因而各有清楚的接口；二者不会仅因都使用 visit 就被误认为承担相同责任。

至此，访问一个节点已经能够获得正确形状、公共身份和统一结果。但是，访问 BinaryExpr 不会自动访问它的 left 与 right。处理规则、子节点关系与递归策略仍是三个不同问题，这正是下一章的主题。

\chapter{子节点枚举、遍历策略与头文件边界}
\label{chap:front-traversal}

\section*{导读}
选择一个节点的处理函数，与决定是否访问它的孩子，是两个不同问题。一个打印器可能按固定格式递归，一个观察器希望访问每个节点，一个类型检查器则要在进入某些孩子之前建立作用域或传入预期类型。本章把分派、子节点枚举和整树遍历分别讲解，再阅读它们在头文件中的对应关系。重点是理解通用工具承诺了什么，使用者还需决定什么，以及新增结构时哪些规则应当重新检查。

\section{dispatch、children 与 traversal}
对下面的函数，建树得到的二元根、左整数和右整数是三个表达式节点：
\begin{lstlisting}[language=Rustless]
fn sum() -> i32 {
    1 + 2
}
\end{lstlisting}
调用 ast::visit 访问根，只会选择 BinaryExpr 的处理函数。它不会自动进入 left，也不会自动进入 right。若该处理函数什么也不做，孩子仍未被访问；若处理函数自行访问 left 两次，则左孩子会被处理两次。visit 的承诺是单节点分派，而非遍历策略。

\texttt{for\_each\_child} 提供另一项承诺：按结构规则枚举当前节点的直接、有身份的孩子。对于二元根，它提供左表达式与右表达式；对于整数，它不提供孩子。此接口也不自行递归。调用者可以打印孩子身份，也可以将每个孩子继续交给遍历器。

walk 再组合这两层，提供深度优先的 enter、leave 和控制规则。对于通常的整树观察，它调用 enter，按顺序递归孩子，然后调用 leave。于是三层可以分别回答“这是什么结构”“这个结构有哪些直接孩子”“此次访问怎样沿孩子前进”。

\section{直接子节点与普通记录}
AST 中包含很多不具有独立身份的记录。Identifier 保存文字和范围，PathSegment 保存名字与可选类型实参，DeriveAttribute 保存属性位置与派生项。它们各自具有语法意义，但不一定需要作为整树访问器的独立入口。

这是一项明确的模型选择：NodeId 分配给需要按身份观察或关联事实的 owner，而不是分配给每一个 C++ 字段。访问 Struct 时，可以直接从其属性记录读取 derive 信息；访问 PathExpr 时，可以从 payload.path 读取各段名。通用 walk 不会为每个 Identifier 再调用一次 enter。

不过，没有独立身份的记录仍可能包含有身份的节点。下面的路径含有一个类型实参：
\begin{lstlisting}[language=Rustless]
fn main() {
    let values = Vec::<i32>::new();
}
\end{lstlisting}
PathExpr 内的路径段本身是普通记录；其中 GenericArguments 包含一个指向 TypeSyntax 的类型实参。该 TypeSyntax 有身份，所以子节点枚举穿过路径记录，继续提供 i32 的类型节点。普通记录不是阻断遍历的黑箱，而是可由结构规则展开的组合。

children.hpp 的以下真实实现说明了这一点：
\begin{lstlisting}[language=C++]
void arguments(const std::optional<GenericArguments> &value) {
  if (value)
    for (const auto &argument : value->values)
      std::visit(Overloaded{[&](const TypePtr &p) { recurse_(*p); },
                            [&](const LifetimeName &) {}},
                 argument);
}
void path(const Path &value) {
  for (const auto &segment : value.segments)
    arguments(segment.arguments);
}
\end{lstlisting}
类型实参成为节点边；生命周期名保持普通值，不伪造一个独立 TypeSyntax。类似地，泛型生命周期参数本身具有身份，会被枚举；参数携带的名字与边界名字则由该参数的 payload 读取。

数组类型提供另一个有用例子：
\begin{lstlisting}[language=Rustless]
const SIZE: usize = 3;
fn first(values: [i32; SIZE]) -> i32 {
    values[0]
}
\end{lstlisting}
ArrayType 的 element 是 TypeSyntax，length 是 Expr。它们虽属于不同节点家族，却同样是当前类型节点的结构孩子。整树观察可以访问二者；语义分析则分别解释元素类型和长度常量，不能因为二者都是孩子就以同一规则处理。

\section{子结构集中声明}
\path{E:/RComplier/Rustless/include/rx/ast/children.hpp} 用 ChildEnumerator 为每种载荷显式声明孩子。以下是真实删节摘录，保留四种不同的结构形式：
\begin{lstlisting}[language=C++]
void operator()(const BinaryExpr &p) {
  recurse_(*p.left);
  recurse_(*p.right);
}
void operator()(const ArrayType &p) {
  recurse_(*p.element);
  recurse_(*p.length);
}
void operator()(const Block &p) {
  for (const auto &statement : p.statements)
    recurse_(*statement);
  if (p.tail)
    recurse_(**p.tail);
}
void operator()(const IntegerExpr &) {}
\end{lstlisting}
BinaryExpr 有两个必需孩子；ArrayType 跨越类型和表达式家族；Block 有语句序列与可选尾表达式；IntegerExpr 没有有身份的孩子。空重载是一条明确的结构规则，而不是未匹配到任何规则后的偶然结果。

ChildEnumerator 没有接受任意未知载荷的 catch-all 重载。新增载荷时，如果尚未声明它的孩子，完整访问会发现该载荷无法调用。这有助于避免一种常见遗漏：打印器已识别新节点，但节点统计或身份搜索仍悄悄跳过其所有后代。

声明联合也保持真实顺序。Crate 按 items 的顺序选出具体 owner；Impl 按 members 顺序访问 Function 或 Constant。Function 则先枚举泛型生命周期参数，再枚举 receiver、普通参数、返回注解、where 约束与函数体。语义需要不同顺序时仍可自己控制，结构枚举首先提供确定的源码结构次序。

对结构体构造而言，这一次序尤其不能与布局混淆：
\begin{lstlisting}[language=Rustless]
struct Pair { left: i32, right: i32 }
fn make() -> Pair {
    Pair { right: 2, left: 1 }
}
\end{lstlisting}
StructExpr 的 FieldInit 按 right、left 的源顺序保留和枚举。布局依据声明中的 left、right 决定字段位置。保留初始化顺序让源码观察具有确定性，也为以后明确求值次序提供必要输入；直接按偏移重排孩子，会混合两个不同职责。

公开接口把载荷分派与枚举连接起来，实际代码如下：
\begin{lstlisting}[language=C++]
template <SyntaxRoot T, class Recurse>
void for_each_child(const T &node, Recurse &&recurse) {
  detail::ChildEnumerator<std::remove_reference_t<Recurse>> children(recurse);
  visit(node, [&](const auto &, const auto &p) { children(p); });
}
\end{lstlisting}
其中 recurse 的名字表示调用者可以用它继续递归，并不意味着该接口已经替调用者递归。对每个直接孩子只调用回调，是接口边界；递归、过滤和统计属于调用者策略。

\section{enter、leave 与深度优先遍历}
深度优先遍历先进入一个节点，再完整处理其孩子，最后离开该节点。enter 适合记录开始、设置观察状态或决定跳过；leave 适合记录完成或汇总后代结果。

当前接口定义三种控制和两种结果：
\begin{lstlisting}[language=C++]
enum class WalkControl { Continue, SkipChildren, Stop };
enum class WalkResult { Completed, Stopped };
\end{lstlisting}
Continue 继续当前节点的孩子；SkipChildren 不进入当前节点的孩子，但随后可以继续其他子树；Stop 使整次遍历停止进入新的节点。停止并不删除 AST，也不等价于源程序中的 break。WalkControl 是观察算法的控制，BreakExpr 是被观察语言的结构。

下面的源码含有嵌套分支和块：
\begin{lstlisting}[language=Rustless]
fn choose(flag: bool) -> i32 {
    if flag {
        { 1 + 2 }
    } else {
        3
    }
}
\end{lstlisting}
访问 IfExpr 时，普通 DFS 会依次遍历条件、then 块和 else 块。两个块都会被观察；这不表示程序运行时会执行两条分支。进入 then 中二元表达式时，访问器还会依次进入两个整数，然后离开二元表达式和所在块。

实现来自 \path{E:/RComplier/Rustless/include/rx/ast/traversal.hpp}，以下是 walk 成员函数的真实摘录：
\begin{lstlisting}[language=C++]
template <SyntaxRoot T> WalkResult walk(const T &node) {
  if (stopped_)
    return WalkResult::Stopped;
  auto control = visit(node, detail::EnterAdapter<V>{visitor_});
  if (control == WalkControl::Stop)
    stopped_ = true;
  else if (control == WalkControl::Continue)
    for_each_child(node, [&](const auto &child) { walk(child); });
  // Balance every successful enter, including skip and stop, on unwinding.
  visit(node, detail::LeaveAdapter<V>{visitor_});
  return stopped_ ? WalkResult::Stopped : WalkResult::Completed;
}
\end{lstlisting}
stopped\_ 状态使后续孩子调用立即返回，因此不会产生新的 enter 事件；已有递归层仍会执行 leave。这种受控展开很适合搜索：找到目标之后，已经打开的观察上下文可以正常关闭。

该保证限定于正常返回的控制路径。若 enter、枚举回调或 leave 抛出异常，当前实现没有以 RAII 守卫保证每个已进入节点执行 leave。因此，需要异常安全恢复的分析不能把 leave 当作无条件的析构机制；它应另外设计状态守卫或明确异常策略。把正常 Stop 和 C++ 异常展开混为一谈，会夸大遍历器实际提供的契约。

整树 Visitor 还必须在所有已注册 owner 及载荷上同时提供合法的 enter 和 leave。enter 准确返回 WalkControl，leave 准确返回 void。即使从某个较小子树开始，当前概念仍要求完整的整树协议，从而使该访问器可以在其他合法根上复用，而不随偶然选择的根改变处理能力。

\section{DefaultVisitor 与选择性观察}
对于只统计二元表达式的任务，逐一写出其他所有节点“继续、不记录”很冗长。当前实现提供一份明确可继承的默认规则：
\begin{lstlisting}[language=C++]
struct DefaultVisitor {
  template <class P> WalkControl enter(const Node &, const P &) {
    return WalkControl::Continue;
  }
  template <class P> void leave(const Node &, const P &) {}
};
\end{lstlisting}
它不在每个 Visitor 背后自动存在。使用者必须显式继承，表示选择“不关心的结构继续遍历且不作额外处理”。关键处理器可以不继承默认规则，使新增载荷导致覆盖检查重新失败。

\path{E:/RComplier/Rustless/tests/ast_visitor.cpp} 中的 BinaryObserver 是完整可核对的实际例子：
\begin{lstlisting}[language=C++]
struct BinaryObserver : ast::DefaultVisitor {
  using DefaultVisitor::enter;
  int count{};
  ast::WalkControl enter(const ast::Expr &owner, const ast::BinaryExpr &p) {
    assert(owner.id.value && p.left->id != p.right->id);
    ++count;
    return ast::WalkControl::Continue;
  }
};
\end{lstlisting}
\texttt{using DefaultVisitor::enter} 把基类的 enter 重载引入可见集合。否则，派生类声明一个同名 enter 会隐藏基类同名成员，而不是自动与其全部模板重载组成希望得到的集合。这里的 using 是 C++ 名字查找规则所要求的设计细节。

在如下程序上，该观察器会计数两次：
\begin{lstlisting}[language=Rustless]
fn total() -> i32 {
    (1 + 2) * 3
}
\end{lstlisting}
括号是 ParenExpr，不增加二元计数；括号中的 Add 与外面的 Mul 各有一个 BinaryExpr。观察器没有手写两个孩子的递归，递归由 walk 与 ChildEnumerator 提供。

若只需要搜索身份，可以使用一个接受所有载荷的回调。以下为教学用法，其中 wanted 是已知 NodeId：
\begin{lstlisting}[language=C++]
auto result = rx::ast::walk(
    crate, [&](const rx::ast::Node &owner, const auto &) {
      return owner.id == wanted ? rx::ast::WalkControl::Stop
                                : rx::ast::WalkControl::Continue;
    });
\end{lstlisting}
回调重载是前序观察的简便形式，允许回调统一返回 void 或 WalkControl；前者表示处理后继续。它仍要求回调能接受整树协议中的每种 owner 和 payload。只写一个 BinaryExpr 回调、没有默认规则，不能因为使用 walk 就偷偷跳过其余结构。

相应边界由真实测试检查：
\begin{lstlisting}[language=C++]
static_assert(ast::TraversalVisitor<BinaryObserver>);
static_assert(!ast::TraversalVisitor<MissingBinary>);
static_assert(!ast::TraversalVisitor<MissingLeave>);
static_assert(!ast::TraversalVisitor<WrongControl>);
static_assert(!ast::TraversalCallback<OnlyBinary>);
static_assert(!ast::SyntaxRoot<ast::BinaryExpr>);
\end{lstlisting}
最后一项特别说明载荷不是独立遍历根。BinaryExpr 没有自己的 NodeId，接口要求从 Expr owner 访问它。只把载荷交给遍历器，会失去刚刚解释过的 owner 与 payload 配对关系。

\section{为什么语义检查自行递归}
通用 DFS 能告诉观察器访问顺序，却不能凭结构自动确定所有语义上下文。下面两个相同拼写的整数处于不同预期类型中：
\begin{lstlisting}[language=Rustless]
fn receive(value: u32) -> u32 { value }
fn main() {
    let signed: i32 = 1;
    let unsigned: u32 = receive(1);
}
\end{lstlisting}
第一处初始化可从注解取得 i32 预期类型；调用中的整数可从被调用参数取得 u32 预期类型。单纯进入 IntegerExpr，只知道它的拼写和位置。分析需要在递归调用中把相应预期类型传进去，再决定后缀、默认类型和相容性。

当前 semantic.cpp 的以下真实分支说明了这种显式递归，而完整分析将在下一篇讲解：
\begin{lstlisting}[language=C++]
[&](const ast::Expr &node, const ast::ArrayExpr &array) {
  return check_array(node, array, expected);
},
[&](const ast::Expr &, const ast::BlockExpr &p) {
  return check_block(*p.block, expected);
},
[&](const ast::Expr &node, const ast::IfExpr &p) {
  return check_if(node, p, expected);
}
\end{lstlisting}
数组检查可以把预期元素类型传入每个元素；块检查需要依次处理声明与语句，并把预期结果用于尾表达式；分支检查需要得到两条分支结果，再按规则合并。它们都使用 ast::visit 选择当前结构，却自行决定怎样检查孩子和怎样组合结果。

作用域也有同样要求：
\begin{lstlisting}[language=Rustless]
fn scoped() -> i32 {
    let x = 1;
    ({ let x = 2; x }) + x
}
\end{lstlisting}
进入内层块需要开启局部作用域；内层 let 是否覆盖外层名字、名字在初始化时是否已可见、离开块后查找恢复到何处，都是语言规则。通用 DFS 可以借 enter/leave 辅助维护某种栈，但不会自动给出这些规则，也不会决定应先登记绑定还是先检查初始化。

循环需要维护可 break 的目标以及循环结果信息；return 需要知道正在检查哪个函数和预期返回类型；函数调用需要解析可调用身份并按形参逐个检查参数。这些过程需要上下文和中间结果，显式递归能在调用边界表达输入与输出，比把所有逻辑隐藏在一个巨大观察状态对象中更容易阅读。

因此，通用 walk 很适合结构观察、统计、身份搜索和结构不变量检查。上下文敏感分析仍可使用它，但必须另外设计状态与协议；不能因存在 walk 就认定所有语义分析都应机械改写为 DFS 回调。良好的复用边界，是共享确定的分派与结构事实，同时允许分析表达自己的推导顺序。

\path{E:/RComplier/Rustless/include/rx/ast/visitor.hpp} 为：
\begin{lstlisting}[language=C++]
#pragma once
#include "rx/ast/traversal.hpp"
\end{lstlisting}
只读取结构或自行递归分析的过程，可以引入 ast.hpp；需要整树 walk 的观察器，可以引入 ast/visitor.hpp 或直接引入 traversal.hpp。定义层不反向依赖打印器、语义检查器和 IR，这使语法结构无需知道哪些具体分析过程正在使用它。

这种划分并不保证只引入 ast.hpp 就能获得最小编译时间，因为 dispatch 已包含完整 item 定义，进而引入多种语法家族。它首先提供的是清楚的职责边界和可理解的依赖。若以后需要优化构建时间，可以在保持公开概念一致的前提下测量并调整，而不应把头文件数量本身当作性能证据。

\section{增加一个节点会影响哪些过程}
可以用已存在的重复数组反向做一次设计练习。设想一个只支持列表数组的较早版本，准备增加以下语法：
\begin{lstlisting}[language=Rustless]
fn zeros() -> [i32; 3] {
    [0; 3]
}
\end{lstlisting}
这是当前 Rustless 已支持的语法；以下练习只是追踪若将它作为新结构加入，需要在哪些边界明确作决定，不修改现有代码。

第一步是界定形状。重复数组拥有 element 与 count，而列表数组拥有 elements 序列。因此新增 RepeatArrayExpr 比让 ArrayExpr 使用一个含义随 flag 改变的 vector 更清楚。count 是表达式语法，不应在构树时强行压成一个已验证的整数。

第二步是构造与身份。grammar 必须识别分号分隔的两部分，构造器为它们建立孩子，并为外层 Expr 赋予身份和范围。此时只承诺语法形状成立；长度是否为合适常量、元素是否允许重复，仍由语言规则决定。

第三步是封闭集合与访问。Expr::Data 加入新载荷，所有不带 catch-all 的完整处理器重新进行覆盖检查。owner 注册通常无需为新的表达式载荷再登记一个独立 owner，因为它仍由 Expr 拥有；只有增加新的有身份 owner 家族时，才需要调整 SyntaxOwners。

第四步是声明结构边。当前 children.hpp 为它给出真实规则：
\begin{lstlisting}[language=C++]
void operator()(const RepeatArrayExpr &p) {
  recurse_(*p.element);
  recurse_(*p.count);
}
\end{lstlisting}
有了该规则，共用 walk 的统计器和身份搜索器立即能够进入两个孩子。若元素自身是一个复杂表达式，它的后代也由各自规则继续展开。

第五步是解释具体含义。打印器应能区别列表与重复形式；语义分析应检查元素类型、计数及相关要求；常量求值如果支持此结构，应明确可求值条件。编译期确认“有一个处理函数”，不能代替对这些规则的正确性检查。

第六步是未来的 lowering 与执行表示。AST 的 count 仍是源码表达式，而 IR 或布局阶段可能需要经过验证的长度以及元素初始化方案。类型、求值次数、复制或重复的语言语义都必须在跨阶段边界中明确。当前教程后续将讨论 IR 设计及 lowering 的方向，不能仅凭 AST 已支持重复数组便声称后端完整实现了它。

这个练习说明，新增语法会触及多个相关过程，但触及的位置具有可解释性：grammar 负责识别，构造器负责形状，variant 负责合法结构集合，children 负责结构边，分析负责含义，lowering 负责转成执行所需的表示。边界清楚以后，修改清单不是任意散落的补丁，而是每项语言含义在相应阶段的一次明确表达。

前两篇至此建立了可读、可定位、可拥有和可访问的 AST。它能忠实呈现名字、类型语法与表达式，却尚未独自回答一个名字指向哪个声明、一次运算允许哪些类型、一个块为何具有某种结果。下一篇将从这些问题出发，进入符号身份、语义类型和分析事实的设计。
