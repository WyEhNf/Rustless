\chapter{名字、作用域与分阶段的语义分析}
\label{chap:semantic-names}

\section*{本章导读}
解析器能够把 \lstinline[language=Rustless]|x + 1| 识别为一个二元表达式，却还不能说明 \lstinline[language=Rustless]|x| 指向哪一个变量。读懂一个程序，需要把文字名称与实际声明连接起来。本章从最小的变量例子开始，解释声明身份、作用域和关联成员，再说明为何应先认识整个程序的声明，随后检查函数体。读完本章，读者应能区分名字的拼写、一次语法出现和一个被引用的声明，也能说明各个分析步骤的先后关系来自哪些信息依赖。

\section{名字的拼写与名字的含义}
考虑下面的程序。这里的 \lstinline[language=Rustless]|x| 出现三次：一次声明，两次使用。
\begin{lstlisting}[language=Rustless]
fn main() {
    let x = 3;
    printInt(x);
    printInt(x + 1);
}
\end{lstlisting}
三次出现各有自己的源码范围，也分别构成不同的语法节点。因而它们需要三个节点身份。与此同时，两次使用都指向同一个变量声明。这个共同的含义需要另一种身份来表达。Rustless 将语法节点身份称为 \texttt{NodeId}，将声明身份称为 \texttt{SymbolId}。这两种身份解决的问题不同，不能因为它们都可由整数表示，就让它们彼此替代。

\texttt{include/rx/symbol.hpp} 给出了声明身份的类型：
\begin{lstlisting}[language=C++]
struct SymbolTag;
using SymbolId = ast::Id<SymbolTag>;
\end{lstlisting}
\texttt{Id} 的模板参数使节点身份与符号身份成为不同的 C++ 类型。把一个节点号误传给符号查询时，编译器可以发现这种混用。这种设计不需要额外的运行时标签：身份的类别由静态类型表达，运行时保存的仍是编号。

名字的字符串仍然有价值。诊断需要告诉读者未定义的名字是什么，初次解析也需要用名字寻找声明。但是，已经解析过的引用应当保存找到的身份。后续过程若再次用字符串寻找声明，就必须重新理解遮蔽、关联成员和内建名称的规则。这会使一次已经完成的判断散布到更多地方，也给规则修改增加负担。

\section{符号记录与所属关系}
在当前 \texttt{include/rx/semantic.hpp} 中，一个符号记录保存如下信息：
\begin{lstlisting}[language=C++]
struct SymbolRecord {
  SymbolId id{};
  SymbolKind kind;
  std::string name;
  std::optional<SymbolId> owner;
  ast::NodeId declaration;
};
\end{lstlisting}
\texttt{kind} 区分结构体、函数、常量、字段、参数、接收者和局部变量。\texttt{declaration} 连接回源程序中的声明节点。\texttt{owner} 表达所属关系，例如字段属于结构体，参数属于函数。所属关系不能用名字中的冒号完整代替；字符串适合展示限定名称，身份适合建立可检查的连接。

可以把符号记录看作关于声明的最小知识。它不直接承担表达式类型推断，也不保存机器地址。这样，名字解析、类型检查和后续布局都可以引用同一声明，而不要求符号对象理解每个阶段的全部内容。新增一种处理过程时，通常增加相应的结果表即可。

\texttt{src/semantic.cpp} 的 \texttt{symbol\_for} 为声明分配稳定的身份：
\begin{lstlisting}[language=C++]
SymbolId symbol_for(ast::NodeId node) {
  auto [entry, inserted] =
      declaration_symbols_.try_emplace(node, next_symbol_);
  if (inserted)
    ++next_symbol_.value;
  return entry->second;
}
\end{lstlisting}
同一声明被查询多次时，返回的是同一符号。新声明才消耗新的编号。这里没有把节点编号直接强制转换为符号编号；语法树中很多节点根本不是声明，二者的数量与用途都不同。

\section{作用域：从内层向外层寻找声明}
名字的含义还依赖它所在的区域。下面两个 \lstinline[language=Rustless]|x| 拼写相同，类型却不同。
\begin{lstlisting}[language=Rustless]
fn main() {
    let mut x = 1;
    {
        let x = true;
        if x { printInt(2); }
    }
    x = x + 1;
}
\end{lstlisting}
内层的 \lstinline[language=Rustless]|if x| 使用布尔变量；退出内层块之后，最后的加法使用外层整数变量。把所有局部名字保存到同一个永不恢复的表中，就会失去这种关系。

当前分析器使用一组作用域表。进入块时压入一个表，退出块时移除它。查找从最内层开始，只有在该层找不到名字时才继续向外。下面是 \texttt{src/semantic.cpp} 中 \texttt{lookup} 的实际实现：
\begin{lstlisting}[language=C++]
Binding *lookup(const std::string &name) {
  for (auto it = scopes_.rbegin(); it != scopes_.rend(); ++it)
    if (auto found = it->find(name); found != it->end())
      return &found->second;
  return nullptr;
}
\end{lstlisting}
这个短小算法直接对应词法作用域的含义。每层散列表使常见情况下的单层查找较快，整体查找次数仍与嵌套深度有关。不能仅因为使用散列表，就把整个作用域查找称为常数时间。对于当前语言子集，层数通常有限，这种明确的结构比过早引入复杂缓存更容易理解。

下图追踪同名变量在内外层块中的查找，说明退出内层后为何恢复外层声明。箭头表示一次名字查找访问的方向，而不是程序执行的控制流。

\section{初始化表达式与绑定建立的顺序}
\lstinline[language=Rustless]|let x = x + 1;| 中，右侧的 \lstinline[language=Rustless]|x| 应当在新绑定建立之前解释。假设外层已经有一个 \lstinline[language=Rustless]|x|，右侧就可以使用它。若先插入新名字再检查初始化表达式，就会让一个尚未得到类型和值的声明遮蔽所需的旧声明。

\texttt{check\_block} 因而先解析可选类型注解，再检查初始化表达式，确定绑定类型，最后记录符号并将绑定放入当前作用域。每个步骤需要的信息由前一步提供。这是一个小规模的例子，却揭示了分析顺序的一般原则：先后次序应当由含义的依赖决定，不能只由实现中调用哪个函数方便决定。

局部遮蔽与重复参数还需要分别处理。局部变量可以依据语言规则遮蔽已有名字，函数签名却不能让两个同名参数同时占据同一参数位置。当前实现对参数名与关联成员重复进行检查。这些规则应当在负责相应声明的地方明确给出，不能依赖散列表覆盖旧值后的偶然结果。

\section{先认识声明，再检查函数体}
下面的函数调用写在定义之前。
\begin{lstlisting}[language=Rustless]
fn main() { printInt(twice(3)); }
fn twice(x: i32) -> i32 { x + x }
\end{lstlisting}
逐行读源码当然可以建立语法树，但如果逐行完成全部语义检查，就会在检查 \lstinline[language=Rustless]|main| 时尚不知道 \lstinline[language=Rustless]|twice| 的签名。语言若允许这样的定义顺序，分析器必须先获得完整声明信息。

当前 \texttt{Analyzer::run} 按信息依赖安排主要步骤。下面摘录其中负责顺序的部分；其他结果整理代码在原函数中。
\begin{lstlisting}[language=C++]
collect_items();
resolve_declarations();
// Callable declarations are indexed before bodies are checked.
validate_constants();
validate_layouts_and_derives();
validate_entry();
check_functions();
\end{lstlisting}
声明收集只回答有哪些名字及其所属关系。声明类型解析回答参数、返回值与字段具有什么类型。常量求值补足数组长度等编译时知识。有限布局与派生能力检查处理声明整体的要求。函数体检查再使用这些已准备的信息。把这些任务分开，使单个步骤拥有明确输入，也使错误较容易回到应负责的规则。

\section{关联声明与上下文中的 Self}
\begin{lstlisting}[language=Rustless]
struct Counter { value: i32 }
impl Counter {
    const STEP: i32 = 1;
    fn new() -> Self { Self { value: 0 } }
    fn get(&self) -> i32 { self.value }
}
fn main() {
    let c = Counter::new();
    printInt(c.get());
}
\end{lstlisting}
\lstinline[language=Rustless]|Counter::new| 是关联函数，\lstinline[language=Rustless]|get| 带有接收者，因而可以用方法形式调用。\lstinline[language=Rustless]|Self| 的含义来自当前结构体或实现块；它不是任意位置都可使用的普通名字。分析器保存这一上下文，并把关联函数、关联常量的所属关系连接到结构体符号。

当前初次查找仍使用限定名字组成的字符串，例如 \texttt{Counter::get}。这种做法对于有限的子集较直观。完成解析之后，函数类型与调用目标已经保存符号身份，因此后续过程可以依赖身份，而无需再从字符串的冒号中恢复所属关系。字符串展示与身份连接各承担合适的职责，是清晰设计的重要组成部分。

\section{模块解析的后续问题}
AST 中已经保存 \lstinline[language=Rustless]|use| 声明及其树状结构，但当前声明收集并没有完成导入绑定和完整模块解析。保存一种语法，并不等于已经赋予它全部语义。读者应当把这项边界与已经支持的局部作用域区别开来。

将来引入模块时，需要回答路径从哪个模块开始、别名建立何种绑定、通配导入如何处理冲突、导入是否参与不同名字空间等问题。现有 \texttt{SymbolId} 和所属关系可以继续使用，初次名字查找则需要增加模块环境。由于下游依赖的是解析后的身份，这类扩展不必让类型检查之后的每个步骤都理解导入语法。

\paragraph{本章小结与下一章。}
名字的拼写用于寻找与展示，节点身份用于回到源码，符号身份用于连接声明。作用域决定查找的范围，分阶段分析使定义顺序不再偶然决定是否能够找到声明。找到声明之后，还需要解释其中的类型写法。下一章将从类型语法走向语义类型，并研究字面量与常量如何补足这些含义。

\chapter{语义类型、字面量与常量}
\label{chap:semantic-types}
\section*{本章导读}
\lstinline[language=Rustless]|[i32; N]| 在语法树中保存了类型名和一个长度表达式。类型检查真正需要的则是元素类型和已经确定的长度。本章解释这两种表示的联系，并区分严格的类型相等、上下文中的可转换关系与错误恢复。随后，读者将看到不可变的具体类型对象和 \texttt{TypeContext} 如何使类型的形状、身份与共享关系清楚可控。这些设计关系到规则的一致性，也关系到重复类型的保存与比较成本。

\section{类型写法与类型含义}
\begin{lstlisting}[language=Rustless]
const N: usize = 3;
fn first(values: &[i32; N]) -> i32 { values[0] }
fn main() { printInt(first(&[1, 2, 3])); }
\end{lstlisting}
语法类型 \texttt{TypeSyntax} 需要保留括号、路径、生命周期名字及数组长度表达式等源码信息。语义类型不需要把同一个名字查找多次，也不需要在每次比较数组时重新计算 \lstinline[language=Rustless]|N|。因此，类型解析把这些语法节点解释为另一组对象：引用包含其所指类型，数组包含元素类型与长度，结构体类型包含对应声明的身份。

\texttt{include/rx/semantic.hpp} 中的连接结构很小：
\begin{lstlisting}[language=C++]
struct TypeResolution {
  ast::NodeId node{};
  SemanticTypePtr type;
};
\end{lstlisting}
它说明某一个类型语法节点已经被解释成哪个语义类型。保留这项连接可以同时满足两种需求：诊断仍可回到读者写下的位置，后续过程则直接查询含义。无需让一个类型对象同时承担语法细节和机器表示。

\section{结构相等、声明身份与特殊类型}
两个数组类型相等，需要元素类型相等并且长度相等。两个引用类型相等，还需要引用可变性一致。对于结构体，仅比较字段形状则不够：两个分别声明的结构体即使字段相同，也不应自动成为同一种类型。当前结构体类型以 \texttt{SymbolId} 表达这种名义身份。

\begin{lstlisting}[language=Rustless]
struct Meter { value: i32 }
struct Second { value: i32 }
fn take(x: Meter) {}
fn main() {
    let s = Second { value: 1 };
    // take(s);  // A different declaration, hence a different type.
}
\end{lstlisting}
注释中的调用是本节的错误例子，不是应当通过检查的程序。结构相似并没有抹去声明所赋予的含义。函数项也保存声明身份；一个局部变量可以保存某个函数项，但局部绑定身份与那个函数的身份仍然不同。

这里的声明身份有明确的适用范围。当前命令行一次分析一个 Crate，\texttt{SymbolId} 的含义限定在这次编译的声明身份域内。另一次独立分析可能再次分配相同的编号；两个结构体都编号为 7，不能据此认定它们来自同一声明。跨 \texttt{TypeContext} 的名义类型比较，只有在两个上下文共享同一个声明身份域时，才能使用相同 SymbolId 表示同一类型；\texttt{same\_type} 本身没有记录或验证这个前提。若将来支持分别编译与跨模块导入，应当引入包含来源的 \texttt{DefId}，例如以 \texttt{CrateId} 和该 Crate 内的声明编号共同标识声明，再把这项身份贯穿名字解析、类型与调用事实。

当前 \texttt{same\_type} 是严格相等判断，不进行隐式转换，也不为了诊断而把 Error 当作任何类型。分析器另有 \texttt{same}，仅在错误恢复时放宽关系：
\begin{lstlisting}[language=C++]
bool same(const TyPtr &lhs, const TyPtr &rhs) {
  return lhs && rhs && (lhs->kind() == Ty::Kind::Error ||
                        rhs->kind() == Ty::Kind::Error ||
                        same_type(lhs, rhs));
}
\end{lstlisting}
将这两种关系分开很重要。严格相等回答对象代表的类型是否相同；恢复兼容只为了避免在一个已知错误后不断报告重复后果。Never 也不能混入普通相等：它没有正常产生结果，因而可以在某些期待其他类型的上下文中使用，这是控制流与转换规则，而不是说 Never 就等于那个类型。

\section{数值拼写与整数类型的决定}
\begin{lstlisting}[language=Rustless]
fn main() {
    let decimal = 10;
    let binary: u32 = 0b1_010;
    let octal = 0o12usize;
    let hexadecimal = 0xai32;
    printInt(decimal + hexadecimal);
}
\end{lstlisting}
词法阶段已经说明一个整数字面量使用什么进制以及是否带有后缀。语义阶段应使用这些已确定的信息来解码，不能在不同表达式规则中各写一份猜测字符串的算法。\texttt{integer\_magnitude} 验证后缀和进制前缀、去除分隔符，再使用 \texttt{from\_chars} 得到幅值。

数值解码回答字面量表示哪个数，类型决定回答它以什么类型参与程序。当前 \texttt{literal\_type} 优先使用明确后缀；没有后缀时，若存在整数预期类型，就使用该类型；再没有这样的上下文，则默认 i32。因而 \lstinline[language=Rustless]|let x = 1;|、\lstinline[language=Rustless]|let x: u32 = 1;|、\lstinline[language=Rustless]|let x = 1usize;| 在类型决定上具有不同信息来源。

\section{局部预期类型的传递}
预期类型可以来自类型注解、函数参数、返回值和数组元素。考虑：
\begin{lstlisting}[language=Rustless]
fn take(x: u32) {}
fn answer() -> usize { 3 }
fn main() {
    take(1);
    let values: [u32; 2] = [1, 2];
}
\end{lstlisting}
检查 \lstinline[language=Rustless]|take(1)| 时，参数签名把 u32 传给字面量；检查函数 \lstinline[language=Rustless]|answer| 的尾表达式时，返回注解把 usize 传给它；检查数组时，外层数组注解将元素预期类型传给各元素。

这种方式使上下文传递可见，适合当前子集。它不是完整的约束求解式类型推断。当前实现没有为每个未知类型建立推断变量，再统一求解跨表达式的约束。教材可以从这个较小模型讲清上下文如何流动，随后再讨论更一般的推断器为什么需要额外表示。

预期类型也不能成为掩盖不兼容类型的工具。带后缀的 \lstinline[language=Rustless]|1i32| 仍保留明确类型，把它传给期待 u32 的参数，应当由兼容规则判断能否使用。括号表达式需要特别谨慎：上下文可以穿过括号帮助内部字面量决定类型，而实际使用时的转换应记录在所使用的括号表达式上，避免内外两层重复执行转换。

\section{常量依赖与计算状态}
\begin{lstlisting}[language=Rustless]
const N: usize = M;
const M: usize = 3;
fn main() {
    let values: [i32; N] = [0; N];
    printInt(values[0]);
}
\end{lstlisting}
常量不能简单按源码顺序计算，因为 \lstinline[language=Rustless]|N| 先出现却依赖 \lstinline[language=Rustless]|M|。当前实现对常量类型与值分别保存访问状态。尚未处理的常量开始计算后进入“计算中”；依赖完成后进入“完成”；发生错误则进入“失败”。若再次访问一个仍在计算中的常量，就说明当前依赖路径形成了环。

\section{当前常量表达式的范围}
当前语法允许整数、布尔字面量、路径、负号和括号作为常量表达式。例如 \lstinline[language=Rustless]|const NEG: i32 = -1;| 与 \lstinline[language=Rustless]|const N: usize = (M);| 在这一范围内。\lstinline[language=Rustless]|const N: usize = 1 + 2;| 则不能用来展示已经支持的通用常量折叠，因为该写法不在当前 \texttt{constValue} 规则中。

常量求值使用 AST 的具体载荷 Visitor。整数分支解码幅值，布尔分支得到真假值，路径分支查询已有常量，括号分支递归，负号分支检查带符号类型并取负。它们仍记录表达式事实，因此常量不是游离于语义结果之外的另一套未检查语法。

扩大常量子集时，需要决定算术溢出、除零、移位及允许副作用的规则。较清楚的方向是让常量解释器消费已经确定的运算含义，与运行时代码生成共享语言规则。否则，同一表达式可能在编译期与运行期产生不同结果。是否需要完整解释器，应由支持的常量语法决定，而不必为了形式上的完整立即增加大型机制。

\section{为什么语义类型也需要具体形状}
语法节点已经使用具体载荷表达形状，语义类型也需要同样清楚的结构。若类型对象只有 \texttt{kind}、\texttt{name}、\texttt{element}、\texttt{length} 和一个布尔标志，就必须依赖约定说明哪些字段有效。一个缺少元素的 Array 或同时带着无关长度的 Bool，仍可能由普通构造产生。

当前 \texttt{include/rx/semantic\_type.hpp} 已把这些形状分开。下面是其中的实际定义：
\begin{lstlisting}[language=C++]
struct StructType {
  SymbolId symbol;
  std::string name;
};
struct ArrayType {
  SemanticTypePtr element;
  std::uint64_t length;
};
struct RefType {
  SemanticTypePtr element;
  ast::Mutability mutability;
};
struct FunctionType {
  SymbolId symbol;
  std::string name;
};
\end{lstlisting}
具体载荷说明每种类型需要什么信息。结构体与函数项使用声明身份；数组使用元素和长度；引用使用所指类型和引用可变性。读取一个错误类别的查询，例如对 Bool 调用 \texttt{element()}，不会悄悄返回一个默认空字段，而会指出调用者使用了不适用的操作。

类型对象的构造也受到约束。\texttt{SemanticType} 的构造函数是私有的，\texttt{TypeContext} 提供分别对应这些形状的构造函数。元素不能为空，引用可变性必须是合法枚举值，名义类型必须有非零身份和名字。这使类型形状的检查集中在创建时，而不必让每个消费者都写一份防御性的字段解释。

\section{不可变类型与 TypeContext 唯一化}
当前类型句柄为：
\begin{lstlisting}[language=C++]
class SemanticType;
using SemanticTypePtr = std::shared_ptr<const SemanticType>;
\end{lstlisting}
这里的 const 作用于所指对象，而不只是指针变量。查询拿到句柄之后不能把已经确认的 i32 数组改成布尔数组。不可变性因此保护了先前判断的含义，而不只是让接口看起来只读。

\texttt{TypeContext} 还将相同类型归并为共享的对象。数组的键包含元素身份和长度，引用的键包含元素身份和可变性，结构体和函数项的键包含声明身份。元素先被归并，外层对象的键便可以引用已经稳定的元素对象。相同上下文中反复出现的 \lstinline[language=Rustless]|&i32| 不必每次都创建一个新对象。

下面摘录 \texttt{src/semantic\_type.cpp} 的键构造与复用逻辑中的代表性部分：
\begin{lstlisting}[language=C++]
if (key.kind == K::Array)

\paragraph{本章小结与下一章。}
类型语法保存写法，语义类型保存可比较的含义。具体载荷和受控构造限制了非法形状，不可变性保证已有判断不会被查询者修改，唯一化管理重复类型。预期类型与常量补足局部上下文和编译时知识。下一章将在这些类型之外，继续解释表达式的存储位置、可变权限和有序转换。

\chapter{表达式规则、存储位置与隐式转换}
\label{chap:semantic-expressions}
\section*{本章导读}
知道 \lstinline[language=Rustless]|x| 的类型是 i32，并不能判断 \lstinline[language=Rustless]|x = 2| 是否合法：还需要知道它是否代表一个位置，以及是否允许修改。本章把类型判断扩展为表达式属性判断，介绍位置、可变性和转换序列。随后讨论为何普通运算与复合赋值应共享规则，以及为何接收者的转换必须与表达式结果的转换分开。读者将看到，优雅的表达式设计不仅有清楚的节点类型，还应当把已经作出的语义决定保存为下一阶段能够直接使用的知识。

\section{具体载荷与类型规则的组织}
可以用 $\Gamma\vdash e:T$ 表示“在环境 $\Gamma$ 中，表达式 $e$ 具有类型 $T$”。这里的环境包含局部绑定、声明签名、当前函数和循环上下文。对于整数加法，规则需要先知道两个子表达式的类型；对于函数调用，规则需要知道被调用函数的签名。语法形状决定采用哪种规则，环境则为规则提供必要信息。

当前 \texttt{check\_expr} 使用 AST Visitor 将具体载荷交给相应规则。下面是 \texttt{src/semantic.cpp} 中两个相邻分支的实际摘录：
\begin{lstlisting}[language=C++]
[&](const ast::Expr &, const ast::BooleanExpr &) -> ExprInfo {
  return {ty(Ty::Kind::Bool)};
},
[&](const ast::Expr &, const ast::UnitExpr &) -> ExprInfo {
  return {ty(Ty::Kind::Unit)};
},
\end{lstlisting}
布尔载荷可以直接得到 Bool；Unit 载荷可以直接得到 Unit。二元、数组、调用等更复杂载荷则调用专门函数递归处理子节点。这些分支共同返回 \texttt{ExprInfo}，统一入口随后记录结果。Visitor 的覆盖检查要求每种载荷得到处理，但不会自动证明其类型规则正确。结构覆盖与语义正确是两个层次。

这种分工使新增规则较容易定位。若语言新增一种表达式，AST 的形状和 Visitor 的覆盖要求会提醒读者补上处理；若已有加法规则改变，则应修改负责运算含义的规则，而无需把通用遍历器变成类型检查器。遍历机制与领域规则相互配合，同时保持各自职责清楚。

\section{值与 place：能否定位到存储位置}
\begin{lstlisting}[language=Rustless]
struct Packet { count: i32, bits: [bool; 2] }
fn main() {
    let mut packet = Packet { count: 1, bits: [false, false] };
    packet.count = 2;
    packet.bits[1] = true;
    printInt(packet.count + 1);
}
\end{lstlisting}
\lstinline[language=Rustless]|packet.count| 与 \lstinline[language=Rustless]|packet.bits[1]| 表示可以定位到的存储位置，称为 place 表达式。\lstinline[language=Rustless]|packet.count + 1| 表示计算结果。两者都可以有类型，却对赋值具有不同意义。错误例子 \lstinline[language=Rustless]|(1 + 2) = 3| 的问题是左侧没有可写入的目标位置。

位置与可变性也不同。\lstinline[language=Rustless]|let x = 1;| 建立的 \lstinline[language=Rustless]|x| 是位置，却不允许直接赋值。因而 \texttt{is\_place} 与 \texttt{is\_mutable} 需要分别表达。\texttt{access\_locked} 进一步记录访问路径是否已经经过不能再恢复写权限的共享层。

\texttt{check\_assignment\_target} 的实际代码体现了这两个问题的顺序：
\begin{lstlisting}[language=C++]
void check_assignment_target(const ast::ExprPtr &target,
                             const ExprInfo &destination) {
  if (!destination.is_place)
    report(target->span, "assignment destination is not a place");
  else if (!destination.is_mutable)
    report(target->span, "assignment destination is immutable");
}
\end{lstlisting}
先确认目标是位置，再确认权限。这也让诊断能够指出真正的原因。把二者合成一个名为“可赋值”的布尔标志，可能足以阻止错误，却会丢失字段访问、借用和方法接收者需要继续使用的区别。

\section{绑定可变性与引用可变性}
\begin{lstlisting}[language=Rustless]
fn main() {
    let mut x = 1;
    let r = &mut x;
    *r = 2;
    printInt(x);
}
\end{lstlisting}
这里 \lstinline[language=Rustless]|r| 的绑定没有 \lstinline[language=Rustless]|mut|，但它保存的是可变引用。因此不可直接把另一个引用赋给 \lstinline[language=Rustless]|r|，却可以经由 \lstinline[language=Rustless]|*r| 修改所指对象。绑定是否可替换与所指对象是否可修改，属于两个不同层面。

反过来，一个可变绑定保存共享引用，并不会使共享引用所指对象变得可写。若访问路径已经经过共享引用，后续遇到某个可变引用也不能随意撤销先前的限制。字段和索引规则据此传播访问属性，\texttt{check\_borrow} 则在建立可变引用时检查目标权限。

Box 与引用也应分别解释。Box 表示拥有间接存储的容器，显式 \lstinline[language=Rustless]|*boxed| 得到其中的位置；共享引用限制访问权，不能只因为二者后端都可能表现为指针而套用同一权限规则。机器表示相似，不代表源语言含义相同。

\section{相等、可转换与有序转换步骤}
\begin{lstlisting}[language=Rustless]
fn read(value: &i32) -> i32 { *value }
fn main() {
    let mut x = 1;
    let r: &mut i32 = &mut x;
    printInt(read(r));
}
\end{lstlisting}
可变引用与共享引用不是严格相同的类型，但在这个调用位置可以把可变引用作为共享引用使用。类型相等、是否允许使用以及如何实现这种使用，需要三个分别明确的回答。\texttt{same\_type} 回答严格相等，\texttt{coercible} 回答上下文兼容，\texttt{Adjustment} 保存所需步骤。

当前 \texttt{include/rx/semantic\_operation.hpp} 的定义为：
\begin{lstlisting}[language=C++]
struct Adjustment {
  enum class Kind {
    Dereference, BorrowShared, BorrowMutable,
    MutToShared, NeverToAny
  } kind{Kind::Dereference};
  SemanticTypePtr target;
};
struct OperandSemantics {
  ast::NodeId node;
  SemanticTypePtr effective_type;
  std::vector<Adjustment> adjustments;
};
\end{lstlisting}
表达式的内在类型说明它本身产生什么；一次使用的有效类型说明完成转换后，当前操作看到什么。转换序列按执行顺序排列，每一步保存完成后的目标类型。读取一个 \texttt{OperandSemantics}，后续过程就能从原始表达式沿这些步骤获得有效操作数，无需再猜测检查器剥离了几层引用。

转换链也可以逐步验证。解引用步骤的来源必须是 Ref 或 Box，目标必须是其元素；共享借用的目标必须是相应共享 Ref；可变转共享不能改变所指类型；Never 转换的来源必须确实是 Never。最终类型还必须等于保存的有效类型。这比仅验证每个目标类型非空更强，因为合法的类型对象也可能被排列成没有含义的转换序列。

Rust 编译器的 \href{https://rustc-dev-guide.rust-lang.org/hir-typeck/coercions.html}{转换设计说明}介绍了检查阶段记录 adjustments、后续表示将其显式化的思路。Rustless 采用相同的分工原则，并只实现当前子集需要的转换类别。

\section{运算符怎样选择其类型规则}
运算符并不只表示一个语法标记。相同的除法写法要结合类型选择带符号或无符号含义；相等比较可能是标量比较，也可能是逐字段或逐元素比较；逻辑运算还规定右侧是否执行。下面按类别归纳当前设计。
\begin{longtable}{p{0.20\textwidth}p{0.32\textwidth}p{0.39\textwidth}}
\toprule
类别 & 示例 & 必须保存的含义 \\
\midrule
算术 & \lstinline[language=Rustless]|x + y|、\lstinline[language=Rustless]|x / y| & 同类整数操作数、运算类别与结果类型。\\
位运算 & \lstinline[language=Rustless]|x & y|、\lstinline[language=Rustless]|a ^ b| & 匹配的整数或 bool；不能因此允许 bool 加法。\\
移位 & \lstinline[language=Rustless]|x << count| & 整数操作数、左右方向与计数规范化规则。\\
相等 & \lstinline[language=Rustless]|x == y| & 标量或结构相等，及 PartialEq 能力要求。\\
排序 & \lstinline[language=Rustless]|x < y| & 匹配的有效标量与关系类别。\\
短路 & \lstinline[language=Rustless]|ready && test()| & bool 操作数，右侧有条件执行。\\
一元 & \lstinline[language=Rustless]|-x|、\lstinline[language=Rustless]|!flag|、\lstinline[language=Rustless]|*r| & 取负、取反或显式解引用的具体含义。\\
转换 & \lstinline[language=Rustless]|x as u32| & 显式目标类型及允许的转换关系。\\
\bottomrule
\end{longtable}
当前算术、位运算、移位和一元标量运算允许一层共享引用的自动解引用。因而 \lstinline[language=Rustless]|&x + &x| 可以形成整数加法，而不能据此推断任意层的 \lstinline[language=Rustless]|&&x + &x| 都被允许。排序比较按现行子集规则处理成对引用层，并保留左右引用可变性的限制。自动解引用的深度与权限是语言规则的一部分，不能为了让记录转换步骤更方便而扩大可接受语法。

\texttt{ResolvedOperation} 将已决定的含义分成整数算术、位操作、移位、标量比较、结构相等和逻辑操作。它不直接保存 LLVM 操作码。这样，源语言规则可以独立于机器表示表达：移位保存计数策略，结构相等保持内容含义，短路保持控制流含义。后端再选择如何实现它们。

\section{赋值与复合赋值}
\begin{lstlisting}[language=Rustless]
fn main() {
    let mut x = 8;
    x += 2;
    x -= 1;
    x *= 3;
    x /= 2;
    x %= 5;
    x &= 7;
    x |= 1;
    x ^= 2;
    x <<= 1;
    x >>= 1;
    let mut flag = true;
    flag &= false;
}
\end{lstlisting}
十类复合赋值共享相应二元运算的类型要求，但还需要一个可写目标。赋值表达式本身产生 Unit；内部运算则产生将要写回目标的类型。当前 \texttt{compound} 事实保存内部运算结果类型，表达式事实保存 Unit，二者不应混为一项。

复合赋值也不能总是把源码文字替换为 \lstinline[language=Rustless]|target = target + value|。若目标包含索引函数或其他有副作用的计算，重复定位目标可能重复执行这些计算。语义设计应保留“定位目标一次，读取旧值，完成运算，写回”的结构。具体求值顺序将在 lowering 章节展开，此处先明确这项必须延续的含义。

\section{集中表达共同规则}
假设普通加法只允许整数，复合赋值却只检查目标是“整数或 bool”。这会出现 \lstinline[language=Rustless]|b + false| 被拒绝，而 \lstinline[language=Rustless]|b += false| 被接受的矛盾。节点载荷再类型安全，也不能自动防止规则在不同函数中发生分歧。

当前设计通过 \texttt{resolve\_operation} 统一选择运算类别，复合赋值先将自身运算符对应到二元运算符，然后使用同一规则。因此 bool 的位运算赋值可以被接受，bool 算术和移位赋值会被拒绝。这里的集中并不是建立一个接受所有节点的巨大函数，而是把真正相同的语言决定放在共同位置。

下面是 \texttt{src/semantic\_operation.cpp} 中算术分支的节选：
\begin{lstlisting}[language=C++]
case A::Add: case A::Sub: case A::Mul: case A::Div: case A::Rem:
  if (!integers || !equal) return {};
  switch (op) {
  case A::Add: return IntegerArithmetic{ArithmeticOp::Add};
  case A::Sub: return IntegerArithmetic{ArithmeticOp::Sub};
  case A::Mul: return IntegerArithmetic{ArithmeticOp::Mul};
  case A::Div: return IntegerArithmetic{ArithmeticOp::Div};
  default: return IntegerArithmetic{ArithmeticOp::Rem};
  }
\end{lstlisting}
调用者仍负责环境、源码诊断和目标权限，共同函数负责运算类型与类别。这样的接口使新增运算规则容易找到，也让成功结果发布时可以检查保存的操作是否与 AST 运算符和有效类型一致。

\section{输入转换与结果转换的不同范围}
考虑 \lstinline[language=Rustless]|p.get() + 1|。方法 \lstinline[language=Rustless]|get| 可能需要先把 \lstinline[language=Rustless]|p| 借用为共享引用，但调用结果仍然是 i32。若把接收者的借用步骤放入调用结果的转换序列，后续加法就可能把 i32 误当成结构体引用。接收者转换与结果转换必须分别保存。

当前 \texttt{ExpressionSemantics} 中，\texttt{adjustments} 只描述表达式结果在使用位置的转换；\texttt{receiver} 保存方法、字段和索引的输入转换；\texttt{binary}、\texttt{compound}、\texttt{unary} 保存相应运算的操作数使用事实。不同转换范围有各自的身份和有效类型，因此可以分别验证。

括号是另一个容易混淆的地方。\lstinline[language=Rustless]|(x + y)| 的内层仍有二元操作事实，但外层括号不能复制一份“自己的二元操作”，因为外层载荷是 ParenExpr，操作数结构属于内层节点。当前检查器保留外层结果类型和可调用身份，同时清除不属于外层载荷的操作、接收者事实。形状与语义记录因此一一对应。

\section{访问检查的边界}
当前实现检查位置、引用可变性、共享层限制和容器的可变访问条件。它没有完整的移动状态、析构插入、别名借用冲突、区域推断和生命周期证明。因此，本章关于 \lstinline[language=Rustless]|&mut| 的说明不能被读作已经实现完整 Rust 借用检查器。

若未来语言要求禁止同时存在的可变借用，需要先确定借用的有效区间以及哪些路径可能重叠，再选择合适的数据流表示。若要求 move 与 drop，则需要明确所有权转移和离开作用域时的行为。这些扩展与当前 place 信息有联系，却不是增加一个布尔字段就能完成。优雅的扩展首先要求规则清楚，其次才是表示与算法。

\paragraph{本章小结与下一章。}
表达式规则依赖类型，也依赖位置、访问权和使用上下文。具体载荷选择规则，有序转换记录步骤，已解析运算保持源语言含义，接收者转换与结果转换分开。下一章将这些局部判断放回数组、结构体、函数调用和控制流，说明它们怎样共同决定完整程序的类型。

\chapter{声明、调用与控制流的类型}
\label{chap:semantic-control}
\section*{本章导读}
数组元素、结构体字段、函数参数和条件分支都会向内部表达式提出类型要求。一个表达式还可能通过 return 或 break 结束当前路径，根本不在原位置产生正常结果。本章将前面的局部规则组合起来，介绍聚合值、递归能力、方法和内建调用，再用 Unit 与 Never 解释块、分支和循环。学习重点是这些信息如何相互连接，而不是逐个记忆检查函数的名字。

\section{数组与重复数组}
\begin{lstlisting}[language=Rustless]
fn main() {
    let values: [i32; 2] = [1, 2];
    let zeros: [i32; 3] = [0; 3];
    let empty: [i32; 0] = [];
    printInt(values[0] + zeros[0]);
}
\end{lstlisting}
普通数组需要确定所有元素的共同类型和元素数量。已有注解可以提供元素预期类型；没有注解时，检查器尝试从已有元素得到合适的共同类型。空数组没有元素提供类型信息，因此需要外部上下文。长度属于数组类型，\lstinline[language=Rustless]|[i32; 2]| 与 \lstinline[language=Rustless]|[i32; 3]| 是不同类型。

重复数组保存一个元素表达式和一个常量计数表达式。类型检查不仅确认计数可作为 usize，还检查重复元素满足 Copy 要求。不能因为 AST 只有一个元素节点，就认为生成代码时可以随意重复计算这个节点。语言必须明确初始化表达式的求值次数，以及重复的是值还是计算；后续转换要延续这个决定。

当前数组规则在合并元素类型时可以记录必要转换，重复数组则查询元素能力。两者的载荷不同，因而各自的检查入口能够直接看到需要的信息。将它们都放进“操作数 vector 加一个 flag”的表示，会使计数、元素顺序与复制要求依赖额外约定。

\section{结构体构造与三种字段顺序}
\begin{lstlisting}[language=Rustless]
struct Pair { left: i32, right: i32 }
fn main() {
    let p = Pair { right: 2, left: 1 };
    printInt(p.left + p.right);
}
\end{lstlisting}
构造检查要确认结构体存在、每个字段有效、没有重复字段、没有缺失字段，并用声明中的字段类型检查初始化表达式。字段初始化按源码顺序保存，却通过字段名字连接到声明。这使初始化书写顺序不必与字段声明顺序相同。

这里有三个不同顺序。初始化源码顺序用于保留读者写下的表达式顺序；声明字段顺序用于保存类型定义；存储偏移则由布局规则决定。它们有联系，却不能让某个散列表的迭代顺序偶然承担三种职责。当前 \texttt{StructSemantics} 显式保存声明顺序：
\begin{lstlisting}[language=C++]
struct StructSemantics {
  SymbolId symbol;
  // Preserve declaration order for aggregate layout, not hash-table order.
  std::vector<SymbolId> fields;
};
\end{lstlisting}

下面第一个声明是应当被拒绝的例子，第二个声明以间接层打断内嵌尺寸递归。

// Invalid: a complete Bad must contain another complete Bad.

派生能力也按字段递归判断：
\begin{lstlisting}[language=Rustless]
#[derive(Clone, Copy, PartialEq, Eq)]
struct Pair { left: i32, right: i32 }

    let p = Pair { left: 1, right: 2 };
    let q = p.clone();
    let equal = p == q;
}
\end{lstlisting}
当前 Copy 要求显式 Clone，Eq 要求显式 PartialEq。Box 与 Vec 不因其间接表示可复制就自动拥有 Copy；它们的内容能力参与 Clone 与相等判断。数组能力依赖元素能力，结构体能力依赖字段能力。此处实现的是固定的派生能力检查，并没有完整 trait 定义、用户实现选择或通用 trait solver。

循环检测与能力递归还须区分。一个间接递归类型可以具有有限存储，但递归检查某种能力时仍需要处理再次访问。不能把“有限尺寸”直接理解为“所有能力都自动成立”。每一种递归算法都应明确自身沿哪些边展开，以及再次遇到节点时意味着什么。

\section{函数签名与方法接收者}
\begin{lstlisting}[language=Rustless]
struct Counter { value: i32 }
impl Counter {
    fn new() -> Self { Self { value: 0 } }
    fn add(&mut self, amount: i32) { self.value += amount; }
    fn get(&self) -> i32 { self.value }
}
fn main() {
    let mut c = Counter::new();
    c.add(2);
    printInt(c.get() + 1);
}
\end{lstlisting}
普通函数调用按签名检查参数数量与类型。方法调用还需要解析接收者类型、寻找对应成员、形成所需 receiver，并检查可变访问。\lstinline[language=Rustless]|c.add(2)| 对应可变引用接收者，\lstinline[language=Rustless]|c.get()| 对应共享引用接收者。关联函数 \lstinline[language=Rustless]|Counter::new()| 没有 receiver，因此不应以对象点语法冒充方法调用。

当前函数事实将 receiver 与普通参数分开：
\begin{lstlisting}[language=C++]
struct FunctionSemantics {
  SymbolId symbol;

  std::vector<ParameterSemantics> parameters;

\section{Box、Vec 与具体的调用目标}
\begin{lstlisting}[language=Rustless]
fn main() {
    let boxed = Box::<i32>::new(1);
    let copy = boxed.clone();
    let equal = boxed == copy;
    let mut values = Vec::<i32>::new();
    values.push(*boxed);
    let n: usize = values.len();
    printInt(values.remove(0));
}
\end{lstlisting}
内建构造需要明确元素类型。\lstinline[language=Rustless]|push| 与 \lstinline[language=Rustless]|remove| 需要可变容器访问；\lstinline[language=Rustless]|len| 和 \lstinline[language=Rustless]|is_empty| 只查询容器；\lstinline[language=Rustless]|clone| 需要相应能力。Box 的 clone 接收者应是 Box 自身，而不是为了查找方法就把 Box 完全解引用到 i32 后借用该整数。

两个保存相同内容的 Box 是否相等，属于内容语义。它们的存储地址可以不同，但结构相等仍应根据所指内容判断。当前语义操作将这类比较表示为 \texttt{StructuralEquality}。后端可以决定调用辅助函数或递归生成比较，却不能仅因为 Box 以指针表示，就生成地址相等比较。

调用目标也有不同来源。用户函数具有 \texttt{SymbolId}，内建操作具有 \texttt{BuiltinId}，当前定义如下：
\begin{lstlisting}[language=C++]
struct FunctionTarget { SymbolId symbol; };
struct BuiltinTarget { BuiltinId builtin; };
using CallTarget = std::variant<FunctionTarget, BuiltinTarget>;
\end{lstlisting}
内建身份说明语言操作的类别，不伪装成某个没有源码声明的用户符号。I/O 的 \lstinline[language=Rustless]|getInt|、\lstinline[language=Rustless]|printInt|、\lstinline[language=Rustless]|printlnInt| 也通过这种身份解释签名。展示名称可以保留别名，后续转换依据已确定的类别选择运行时操作。

当前函数项别名也保留原函数身份：\lstinline[language=Rustless]|let g = f; g();| 的局部符号是 g，调用目标却是 f。这里并没有实现任意函数指针签名与动态间接调用。将来支持这类调用时，应当增加相应的类型和目标表示，不应把任意函数值都重新解释成名称字符串。

\section{块的 tail、Unit 与 if 结果}
\begin{lstlisting}[language=Rustless]
fn main() {
    let value: i32 = { let x = 1; x + 1 };
    let nothing: () = { printInt(value); };
    let chosen: i32 = if true { 1 } else { 2 };
    printInt(chosen);
}
\end{lstlisting}
块的尾表达式没有分号时，提供块的结果；带分号的表达式作为语句执行，通常不提供该值。没有尾表达式的正常块结果为 Unit。AST 已将语句序列与可选 tail 分开，语义规则因而能够直接表达这个区别。

if 的条件需要 bool。带 else 时，两条正常分支需要形成共同结果类型，可以依据预期类型或允许的转换得到一致含义。没有 else 的 if 在条件为假时仍会正常继续，却没有另一个值，因此正常结果要求 Unit。当前共同类型选择基于可转换关系，不是为任意类型层次求一般最小上界的复杂算法。

若一条分支没有正常结果，它不需要提供与另一条分支相同的值。这将把我们带到 Never。这里也应注意，类型检查仍然可以检查源码中的两条分支；运行时代码生成只执行实际选择的那一条。

\section{Never 与函数退出}
\begin{lstlisting}[language=Rustless]
fn select(flag: bool) -> i32 {
    if flag { return 1; }
    2
}
fn main() { printInt(select(false)); }
\end{lstlisting}
\lstinline[language=Rustless]|return 1| 检查返回值是否适合函数结果，然后离开函数。它不会在该表达式原来的位置正常产生一个值。因此这个表达式具有 Never，而不是 i32，也不是 Unit。i32 是函数交给调用者的结果类型，Never 是当前源码位置没有正常续行的描述。

Unit 与 Never 的差别可以从执行行为理解：Unit 表示正常完成却不携带普通数据；Never 表示没有正常完成这一步的路径。后端 Void 则是机器接口中的“无普通返回值”表示。即使一个后端类型函数把 Unit 与 Never 都映射到 Void，控制流仍必须保留两者的区别，否则可能在 return 之后继续生成普通指令，或给合流点制造并不存在的输入。

\section{loop、while 与跳转上下文}
\begin{lstlisting}[language=Rustless]
fn main() {
    let answer: i32 = loop { break 42; };
    let mut n = 0;
    while n < 3 {
        n += 1;
        if n == 2 { continue; }
        printInt(n);
    }
    printInt(answer);
}
\end{lstlisting}
loop 的结果由离开它的 break 值决定。没有 break 的 loop 不会正常结束，因而结果是 Never。多个 break 的值需要满足共同结果要求，外部注解可以提供预期类型。break 表达式自身仍然是 Never，因为它离开当前路径；其携带值才成为循环的正常结果。

while 的条件是 bool，循环整体正常结束时产生 Unit，因而不允许带有普通值的 break。continue 跳到最近相关循环的下一次迭代，不在原位置正常产生结果。当前分析器以循环上下文栈记录预期类型与 break 类型，并在进入和离开循环时维护这项信息。

嵌套循环中，一个 break 必须归属正确循环；在循环之外出现 break 或 continue 则应报告错误。当前 while 条件还有明确的上下文边界：条件中的跳转只能针对在该条件内部建立的循环，而不能任意跳向包围的循环。这样的规则需要在条件检查前后处理循环上下文，不能只看是否存在某个全局“当前正在循环”的布尔值。

\section{入口、整体声明与生命周期边界}
当前可执行程序要求顶层 \lstinline[language=Rustless]|main|，其普通参数列表为空，结果为 Unit，并满足子集关于泛型参数的入口限制。重复参数、重复字段与重复关联成员也在声明检查中报告。入口规则属于程序整体要求，不是某个局部表达式的类型规则。

生命周期和 where 语法仍需要准确限定。下面的生命周期写法可以被语法树保存：
\begin{lstlisting}[language=Rustless]
fn read<'a>(x: &'a i32) -> i32 { *x }
fn main() { printInt(read(&1)); }
\end{lstlisting}
保存生命周期名字不代表当前类型检查已经证明引用存活时间。当前语义类型没有完整区域模型，where 类型约束没有获得完整语义解释。用户定义泛型声明也不能与 Box、Vec 的具体元素参数混为一谈。当前泛型声明语法主要保存生命周期参数，不能把它介绍为已经支持任意用户类型泛型。

这些边界并不妨碍清楚的结构设计。保留源码语法可以为以后扩展提供位置与形状，语义结果则应明确哪些部分确实经过判断。下一章将说明这种区别怎样落实到成功结果的完整性检查中。

\paragraph{本章小结与下一章。}
聚合声明提供成员要求，函数签名提供参数与返回上下文，内建身份提供语言操作类别，控制流决定哪些路径会正常产生结果。有限布局、派生能力和访问权限都必须按自身含义处理递归与间接层。下一章将讨论怎样把这些判断保存为稳定的语义知识，使后续转换能够直接依赖它们。

\chapter{语义事实、诊断恢复与阶段边界}
\label{chap:semantic-boundary}
\section*{本章导读}
名字解析与类型检查已经确定了程序的许多含义，后续生成指令时应能够使用这些决定，而不必重新猜测它们。本章介绍语义副表、不可变结果和查询索引，解释“已有条目合法”为什么还不足以保证结果完整，也说明对象寿命与来源身份怎样保护查询。最后，读者将比较直接从已检查 AST 转换和增加显式语义中间层的两种路径。清楚的边界应当使每个阶段知道自己获得了什么，以及可以据此省去哪些重复工作。

\section{为什么单独保存语义事实}
AST 保存源程序的结构。它需要说明某处是 BinaryExpr、左右子表达式是什么、运算符写在哪里，却不应为了每个分析过程不断添加一批可选字段。一个按节点身份保存的语义副表，可以说明这个节点得到什么类型、引用哪个声明、需要哪些转换，同时保持语法树的含义稳定。

这种分开不是唯一正确方案。另一种方案是建立 typed AST，在新树中直接嵌入检查后的类型与操作。但如果简单把类型字段塞进原 AST，就还需要说明树何时完全检查、字段何时有效、错误状态怎样表示，以及同一树能否在不同环境中重新分析。副表把一次分析的结果归属于一次分析过程，适合当前已有的身份体系。

分开也带来成本。AST 与事实之间需要可靠身份，事实应完整对应节点，两个对象的寿命需要协调。查询需要索引，构造成功结果时需要检查关联关系。因此，副表的优点不是“完全没有额外工作”，而是把这项工作放在清楚的位置，让每个语法节点不必了解所有下游用途。

\section{语义结果包含哪些知识}
当前结果先由可构建的 \texttt{SemanticData} 汇集，再由 \texttt{SemanticResult} 包装为不可变快照。下面按主键说明各组事实的用途：
\begin{longtable}{p{0.23\textwidth}p{0.20\textwidth}p{0.47\textwidth}}
\toprule
事实组 & 主键 & 保存的知识 \\
\midrule
\texttt{symbols} & SymbolId & 声明类别、展示名、所属符号、对应声明节点。\\
\texttt{expressions} & NodeId & 内在类型、位置与权限、转换、可调用目标与已解析操作。\\

表达式事实中的可调用身份尤其需要与局部符号区别开来：
\begin{lstlisting}[language=Rustless]
fn emit() { printInt(1); }
fn main() {
    let g = emit;
    g();
}
\end{lstlisting}
路径 \lstinline[language=Rustless]|g| 引用局部声明，因而其符号可以是局部 g；该值的函数项类型和调用目标却指向 emit。若只保存一个字符串 target，局部绑定、函数声明和内建别名很容易被混为一类。当前具体 \texttt{CallTarget} 保存原函数身份或内建身份，使这两层含义分别存在。

\section{Error 与诊断恢复的含义}
\begin{lstlisting}[language=Rustless]
fn main() {
    let x = missing;
    printInt(x);
}
\end{lstlisting}
这是一个错误程序。检查器首先应指出 missing 没有定义。如果随后为 x 产生一个恢复用的 Error 类型，可以继续检查其余结构，并避免把每次使用 x 都报告成一个独立根本错误。否则，读者可能得到大量由同一原因派生的诊断，反而难以找到应当修正的位置。

恢复兼容允许带有 Error 的某些比较暂时通过，只为了继续分析。它不能成为成功程序的事实。当前正常发布会拒绝 Error 及含有 Error 的嵌套类型；失败结果由另一个冻结入口保存，\texttt{success()} 为 false，不能建立正常的语义查询索引供后续转换使用。

因此，错误类型与 Never 需要严格区分。Error 说明分析没有得到有效类型；Never 说明程序在该处没有正常续行，是有效的控制流知识。将两者都当作“特殊类型”而在所有地方宽容处理，会使真实失败混进合法发散路径。

还应区分源程序错误与实现自身的不一致。未知名字、类型不匹配应当通过带源码位置的诊断解释给读者；成功事实缺少字段、链接到不存在的符号、来源节点不匹配，则说明当前表示违背了已经声明的内部要求。后者不应该被悄悄降级为某个默认类型继续生成代码。

\section{查询索引、快照所有权与 AST 寿命}
\texttt{SemanticIndex} 为按身份保存的结果建立查询表。表达式查询返回 \texttt{ExpressionSemantics}，声明查询返回 \texttt{SymbolRecord}，函数与结构体查询返回完整签名和成员序列。它拥有一个 \texttt{shared\_ptr<const SemanticData>}，因而即使外部 \texttt{SemanticResult} 包装对象已被销毁，索引指向的事实仍然存活。

AST 的情况不同。索引借用原来的 Crate，并不拥有或复制整个语法树。调用者必须让 AST 在索引使用期间存活且保持不变。后续桥接对象又借用索引，因而它的寿命必须包含在索引寿命内。拥有快照与借用语法树分别说明了哪些资源由对象负责保存，不能用一个模糊的“所有对象都要活得更久”替代这项关系。

借用接口也应尽可能在编译期排除明显的寿命错误。单独使用 const 左值引用参数，会允许临时 Crate 绑定到该参数；一旦构造表达式结束，索引借用的对象便已销毁。当前接口因此显式删除两个右值重载，包括 const 右值：
\begin{lstlisting}[language=C++]
SemanticIndex(const ast::Crate &crate, const SemanticResult &result);
SemanticIndex(ast::Crate &&, const SemanticResult &) = delete;
SemanticIndex(const ast::Crate &&, const SemanticResult &) = delete;
\end{lstlisting}
这种限制使直接传入临时语法树的调用无法通过重载解析。它并不是完整的寿命证明：一个命名的 Crate 仍可能在索引之前离开作用域，调用者依然需要遵守借用关系。优雅的接口应当消除能够可靠识别的误用，同时准确说明其余条件。

身份查询还需要考虑不同语法树可能重复使用相同编号。两个分别解析的 Crate 都可以有编号为 7 的表达式；不能因此让它们互用语义事实。构造索引时检查原 Crate 身份，对对象形式的查询还同时检查节点地址。当前实现的 \texttt{require\_node} 为：
\begin{lstlisting}[language=C++]
void SemanticIndex::require_node(const ast::Node &node) const {
  const auto found = nodes_.find(node.id);
  if (found == nodes_.end() || found->second != &node)
    throw std::invalid_argument("semantic query uses a foreign AST node");
}
\end{lstlisting}
同一 AST 内的 ID 查询仍然方便；跨对象入口则应使用对象重载，以获得来源检查。这种约束允许编号保持紧凑，而不要求每个 NodeId 成为全局唯一的巨大标识。其前提仍然是 AST 不被移动、修改或提前销毁，地址检查不能使已经悬空的 C++ 引用恢复安全。

\section{完整性与对应关系}
假设一个结构体声明了两个字段，而导出列表只保留一个。保留下来的字段可能拥有合法身份、正确 owner 和有效类型，但布局仍会遗漏另一个字段。函数参数也是如此：现存参数全部合法，并不能证明原签名没有被截短。

成功发布因此检查完整对应，而不只检查现存条目。当前结构体验证的代表性代码如下：
\begin{lstlisting}[language=C++]
if (fact.fields.size() != node.fields.size())
  throw std::invalid_argument("semantic struct field count mismatch");
for (std::size_t i = 0; i < node.fields.size(); ++i) {
  const auto &field = node.fields[i];
  const auto field_id =
      require_symbol(field, SymbolKind::Field, id, field.name.text);
  if (fact.fields[i] != field_id)
    throw std::invalid_argument("semantic struct field order mismatch");
  require_equivalent(symbol_type(field_id), type(*field.type));
}
\end{lstlisting}
数量、顺序、身份、所属关系与类型共同构成对应。函数还核对接收者存在与否、参数序列、返回注解、参数事实和声明类型。局部声明、常量、类型语法、表达式也具有相应的形状和覆盖要求。类型对象内部的元素、名义身份及内建类别同样需要有效。

表达式的操作事实也需要对应具体载荷。BinaryExpr 必须有 Binary 的已解析操作，保存的左右 NodeId 必须对应真实子表达式，操作类别必须适合有效类型，结果类型必须与表达式一致。Unary、Compound、Method receiver 同样如此。一个有效的 \texttt{ResolvedBinary} 若附着在 ParenExpr 上，仍然是错误事实。

调用事实同样不能只检查目标符号存在。对于用户函数，调用记录还要与目标签名的结果类型、显式参数数量以及每个实参的有效类型一致；方法调用则另外核对已经调整的接收者。这里使用实参在该调用位置的有效类型，才能正确容纳可变引用到共享引用等合法转换。如果一个返回 i32 的函数被记录成返回 bool，即使这两个类型对象本身都合法，这份调用事实仍然不成立。调用别名也必须回到原函数身份，而不能把局部变量的身份当作函数定义。

完整性要求还必须诚实反映语义范围。AST 遍历可以覆盖 where 约束的所有节点，当前语义分析却没有为 TypePredicate 内部提供完整解释；查询验证因而明确跳过这部分语义覆盖要求，同时保留语法身份与源码范围检查。遍历覆盖不能被介绍为已经完成约束求解。

这些检查验证表示关系，并不取代语言规则本身。一个任意编造的、内部一致的类型判断，不能仅靠结构检查证明其语义正确。分析器仍然需要正确实现名字和类型规则；发布检查的作用是发现遗漏、错位、重复和相互矛盾的记录，防止这种不一致无声进入下游。

\section{从可构建数据到不可变成功结果}
检查期间需要逐步积累事实，因此 \texttt{SemanticData} 保持可构建。成功之后，消费者应看到不可变数据。当前 \texttt{SemanticResult} 的私有构造接收 const 快照，公开成功入口先完成验证：
\begin{lstlisting}[language=C++]
SemanticResult SemanticResult::publish(const ast::Crate &crate,
                                       SemanticData data) {
  data.source_crate = &crate;
  data.success = true;
  auto snapshot = std::make_shared<const SemanticData>(std::move(data));
  SemanticIndex validated(crate, snapshot, SemanticIndex::ValidationTag{});
  return SemanticResult(std::move(snapshot));
}
\end{lstlisting}
构造验证使用的 Index 拥有快照，完成全部检查之后才返回结果。如果某项检查失败，就不会产生可供正常转换使用的成功包装。失败冻结入口则明确保存失败状态。默认结果也不是一个凭空检查成功的程序。

这里的不可变性有两层。const 数据快照保护 vectors 中的事实；const 类型对象保护指针所指的类型图。只把外层 \texttt{SemanticResult} 声明为 const，而内部仍保存可修改类型对象，并不能保证先前的布局和操作决定保持稳定。

完整验证应在少数明确边界进行，不应在每次查询时遍历全部 AST。当前发布时检查，公开构造 Index 时也进行一次检查与索引建立，随后查询只查相应映射。这样，额外验证成本集中在创建阶段。若将来需要大量索引，可以在受控的成功结果内部复用索引或验证标记，但必须保持来源与不可变性要求，不能以减少检查为由允许可变数据绕过边界。

\section{下游应当直接获得哪些决定}
\begin{lstlisting}[language=Rustless]
struct Pair { value: i32 }
impl Pair { fn get(&self) -> i32 { self.value } }
fn main() {
    let p = Pair { value: 1 };
    let result = p.get() + 2;
    printInt(result);
}
\end{lstlisting}
转换这个加法时，下游应能直接知道：调用目标是哪一个方法；接收者怎样形成共享引用；调用结果的内在类型是 i32；加法两个使用的有效类型是 i32；已解析操作是整数加法；结构体字段及方法签名完整。它不需要再次用名称查找 \lstinline[language=Rustless]|get|，也不需要猜测接收者借用是否会改变调用结果。

与此同时，语义事实不必提前决定一切机器细节。字段存储偏移、聚合间接参数、隐藏返回地址、机器指令和目标寄存器属于后续表示选择。语义阶段需要保留内容相等、有符号运算、短路和正常续行等含义，布局与后端再依据这些含义形成实现。

这种边界同时有利于维护与运行效率。规则改变主要影响负责规则的地方，消费者使用统一结果；重复的名字查找与类型推断可以避免；不变量检查又能在造成后续错误之前发现遗漏。其代价是保存事实和建立索引的空间与时间，不能假设所有程序都因增加副表而自动更快。清楚的设计先使工作不会重复，再根据实际规模评估表示成本。

\section{是否需要增加语义中间层}
一种路径是继续使用原 AST，加上已检查事实直接进行 lowering。它保留完整源码结构，现有 Visitor 与身份查询可以复用。另一种路径是在检查之后建立较小的显式语义树，把隐式转换变成明确节点，再从这棵树生成计算表示。后者可以减少 lowering 对语法细节和副表的反复组合，但需要构造新表示并维护来源信息。

是否增加层次，应根据重复推断、转换复杂度和语法差异的实际负担判断。层数多并不自动使设计优雅，直接转换也不自动使设计简单。当前已经保存具体操作、独立输入转换和调用身份，可以先检验这些事实是否足以支持清楚的 lowering；当转换代码不得不多次重新解释同一含义时，再引入适当的语义中间层。

\paragraph{本章小结与下一篇。}
语义副表使结构与判断分开，不可变类型与快照保持判断稳定，完整对应检查防止遗漏，来源和寿命约束保护查询。成功结果交给下游的是已经确定的语言含义，而不是要求下游再次运行一套类型检查。下一篇将把这些含义组织成显式计算，研究 IR 指令、控制流、布局和调用表示如何延续前端的决定。
